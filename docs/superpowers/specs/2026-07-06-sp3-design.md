# Sub-project 3 — Learning-log timeline, outcome history, calibration readout

**Date:** 2026-07-06
**Status:** Design — approved in session
**Scope:** The learning loop's memory and honesty layer. Builds on SP1 (honest scoring), SP1.5 (hardened signals), SP2 (check proposals + panel fidelity). Completes the SP1 spec's §9 sequence.

---

## 1. Problem

Three gaps:

1. **The loop has no memory.** The proposal row is mutable: `rollbackAppliedProposal` overwrites `decidedAt` (apply.ts), supersede transitions stamp nothing, and once a rollback lands the falsifier evidence that motivated it (`targetDelta`, version pair, invalid-output rate) evaporates as the metrics window moves on. The paper requires harness changes *"recorded with auditable rationales"* (§3.5.3) and names replayability — *"the full trajectory can be reconstructed and audited from logs and artifacts"* — as an evaluation dimension (§5.2.1 vi). FUTURE_ARCHITECTURE states the repo invariant outright: *"Append-only event spine + projections — reconstruct history by replaying events; clients read projections."* The learning loop currently violates all three.
2. **Loop decisions hide in daemon logs.** SP2's R4 skip (invalid current schema) and safeParse-net skip emit `console.warn` — invisible to the product. Comparative diagnosis needs the negative space: "the loop looked and found nothing / skipped X because Y" is telemetry, not a log line (paper p.33).
3. **The confidence coefficients are stated priors with no measurement.** SP1's spec (§7) promised calibration against the measured false-acceptance rate. Nothing surfaces whether `TIER_CONFIDENCE` (1.0 / 0.7 / 0.55 / 0.3) matches reality.

Plus small carried follow-ups from the SP1.5/SP2 ledgers (§6).

## 2. Goals / Non-goals

**Goals**
- Append-only `learning_events` (migration 0056): one row per loop transition, written in the same transaction as the state change, by deterministic code only.
- **Outcome history survives rollback**: the `rolled_back` event freezes the falsifier snapshot at rollback time.
- **Negative space is auditable**: an `analyzed` event per analyze run records what was diagnosed, created, and skipped (with reasons).
- **Every event stamps `templateVersion` at event time** — the trajectory is replayable against version history without joins through mutable rows (paper p.33: signals linked to concrete artifacts, comparable across harness versions).
- **Calibration readout, display-only**: per-tier assumed vs measured, three honest states; divergence beyond a margin feeds the existing deterministic `insights` channel. `TIER_CONFIDENCE` stays fixed constants — the score's replayability invariant is untouched.
- Timeline UI replaces the rail's thin activity log; jargon-free (five-term ban), plain-language event copy.
- Close the carried follow-ups (§6).

**Non-goals (explicit)**
- Auto-adjusting coefficients (breaks score comparability; noise-driven at current volume). Versioned/per-version calibration splits. Coefficient-change proposals.
- New revision targets; cross-template/owner learning; real replay execution.
- Backfilling events for pre-SP3 proposals (the timeline starts when the spine starts; pre-existing proposals appear via a synthesized `created` marker derived from the row — see §3.4 — nothing else is invented).

## 3. The model

### 3.1 `learning_events` (migration 0056)

```sql
CREATE TABLE learning_events (
  seq INTEGER PRIMARY KEY AUTOINCREMENT,
  id TEXT NOT NULL UNIQUE,
  template_id TEXT NOT NULL,
  proposal_id TEXT,                -- null for analyzed events
  step_template_id TEXT,           -- null for template-level events (baseline_restored)
  event_type TEXT NOT NULL,        -- created|judged|applied|dismissed|rolled_back|superseded|baseline_restored|analyzed
  template_version INTEGER NOT NULL, -- version at event time
  payload_json TEXT NOT NULL,      -- typed per event_type, bounded
  created_at TEXT NOT NULL
);
CREATE INDEX idx_learning_events_template ON learning_events (template_id, seq DESC);
```

Payloads (zod-typed in `packages/contracts/src/learning/index.ts`, each bounded ≤ 4 KiB serialized):
- `created`: `{ component, rule, failureCode | null }`
- `judged`: `{ verdict, solvedSampleSize, failureSampleSize }`
- `applied`: `{ appliedAsVersion, humanEdited }`
- `dismissed`: `{}` · `superseded`: `{ by: "apply" | "staleness" | "restore" }`
- `rolled_back`: `{ outcome: { targetDelta, targetDeltaVersions, invalidOutputRateDelta, regressionDetected } }` — **computed immediately before the rollback lands** (one metrics recompute in the route path; control-plane cheap) so the motivating evidence is frozen.
- `baseline_restored`: `{ supersededCount }`
- `analyzed`: `{ stepsDiagnosed, proposalsCreated, skips: { stepTemplateId, reason }[] }` — reasons include the R4 invalid-schema skip and the safeParse-net skip (which keep their `console.warn` too; the event is the product-visible record).

Writers: a small `learning/events.ts` store module (`recordEvent`, `listEventsByTemplate` capped 100 newest-first). Emission inside the existing transactions in `apply.ts` (applied/rolled_back/superseded-on-apply/baseline_restored) and alongside the store writes in `usecases.ts` (created, judged, analyzed) — always deterministic code, never LLM output.

### 3.2 Events API
`GET /v1/learning/templates/:id/events?limit=N` (default 50, max 100) → `{ events: LearningEvent[] }` (additive contract type). Read-only projection; no enrichment.

### 3.3 Calibration readout
Computed in the metrics layer as a pure projection over the window's final completions, per tier:
- `passes(T)` = final completions at tier T that passed (non-vFail); `overturned(T)` = final completions at tier T with `refute.verdict === "refuted"` (these classify as failures, so they are disjoint from `passes`). `claims(T) = passes(T) + overturned(T)` — the completions where an independent check reached a conclusion about a success claim.
- `measured(T) = passes(T) / claims(T)` — survival rate among independently-concluded claims.
- States: **measured** (`claims ≥ CALIBRATION_MIN = 5` AND, for evidence tiers, a refute actually ran on ≥ half the tier's passes — otherwise the measurement doesn't cover the tier; `ai_reviewed` has refute coverage by construction), **insufficient** (below floor), **unmeasurable** (`self_reported` always — its refutes were inconclusive by construction; evidence tiers whose refute coverage < 0.5 render "checks rarely run at this tier").
- Contract (additive): `TemplateMetricsSummary.calibration: { tier, assumed, measured: number | null, sampleSize, state: "measured" | "insufficient" | "unmeasurable" }[]` (one entry per non-unverified tier).
- **Divergence insight**: when `state === "measured"` and `|measured − assumed| > CALIBRATION_DIVERGENCE = 0.2` with `sampleSize ≥ 10`, `deriveInsights` emits a templated line on each step whose own `verification.tier` is the divergent tier (per-step, via the existing insights channel — template-level insights have no rendering surface): *"Independent review upholds N% of this step's passes; the score assumes M% — scores here may be too {pessimistic|optimistic}."* Deterministic, display-only, no coefficient change.
- Constants live beside `SAMPLE_MIN` in the metrics layer, single table, commented as designed priors.

### 3.4 Timeline UI
The rail's `Activity log (N)` `<details>` becomes the **learning log**: newest-first event list, grouped by proposal (the `analyzed` events interleave chronologically), plain-language one-liners:
- created → "Proposed {a tighter output check | an instruction edit} for *{step}* — targets {readable failure label}."
- judged → "Independent evaluation: {verdict label} ({s} solved · {f} failure cases)."
- applied → "Applied as v{N}{ by {who}}{ (edited before applying)}."
- rolled_back → "Rolled back — {target step didn't improve ({pts} points, vX→vY) | new checks were rejecting output (+N%) | invariant regressed}." derived from the frozen outcome snapshot; falls back to "rolled back by {who}" when the snapshot has no tripped signal.
- analyzed → "Reviewed {n} steps — {created m proposals | nothing to propose}{; skipped {step}: {reason}}."
Pre-SP3 proposals (no events) render a single synthesized "Proposed … ({status})" line from the row so the log isn't misleadingly empty; synthesized lines are visually marked "(before the learning log existed)".
Calibration panel: a second collapsed section "How well-calibrated are the scores?" rendering §3.3 per the approved mock. All copy passes the five-term jargon guard.

### 3.5 What stays untouched
Score math, coefficients, whitelist, routing, judge, canary, apply/rollback semantics — SP3 adds memory and measurement around them, not behavior. The only behavioral additions are event emission and the insight line.

## 5. Edge cases
- Event write fails inside a transaction → the whole transition rolls back (atomicity is the point; no state change without its record).
- `analyzed` with zero steps eligible → still recorded (`stepsDiagnosed: 0`) — "the loop ran" is information.
- Rollback outcome snapshot when metrics have no data (e.g., version pair absent) → snapshot fields null; UI falls back to the generic line.
- Events cap: `listEventsByTemplate` caps at 100; older history remains in the table (no pruning in SP3).
- Calibration when a tier has passes but zero refutes ran → "unmeasurable — checks rarely run at this tier", never `measured: 1.0` by absence (absence-of-check ≠ evidence, same principle as SP1).

## 7. Alignment
- **Paper §3.5.3** ("recorded with auditable rationales") + **§5.2.1 (vi)** (trajectory reconstructable from logs/artifacts): the events table is the record; version stamps link events to concrete artifacts (p.33) for cross-version comparison.
- **Paper §5.2.2** (feedback calibration, epistemically aware): three-state readout; divergence routed into the insight channel; coefficients remain declared priors — no silent drift.
- **Paper p.33** (telemetry not anecdote): skips and no-op analyses become product-visible events.
- **FUTURE_ARCHITECTURE line 98**: append-only spine + projections, verbatim. Retained-outcome-data destination (lines 80/118) realized per-template inside the owner wall; deterministic-only writers; human approval untouched.
- **Replayability invariant preserved**: scores remain pure functions of transitions with fixed coefficients; SP3 adds measurement *about* the coefficients, never through them.

## 8. Success criteria (verifiable)
1. Every proposal transition (created/judged/applied/dismissed/rolled_back/superseded/baseline_restored) emits exactly one event in the same transaction; a forced mid-transaction failure emits nothing and changes nothing.
2. The `rolled_back` event's frozen snapshot matches the enrichment computed immediately before rollback (test with a regressed fixture); after further version churn the event still returns the frozen values.
3. `analyzed` events record zero-proposal runs and skip reasons (R4 invalid-schema fixture produces a skip entry).
4. All events carry the correct `template_version` at event time (apply bumps: created@v1, applied@v1→payload v2, rolled_back@v2).
5. Events route returns newest-first, capped, contract-parsed.
6. Calibration: fixture with 13 ai_reviewed passes / 2 refuted → measured ≈ 0.85, state measured; self_reported always unmeasurable; zero-refute evidence tier → unmeasurable with the coverage reason; divergence fixture emits the templated insight; no-refute tier never reads measured 1.0.
7. Timeline renders all event types in plain language (five-term guard extended); synthesized pre-SP3 lines marked; calibration panel renders all three states.
8. Carried follow-ups: each closed with its named test/comment; `evidence_veto` renders as its readable label in the rail.
9. Full sweeps green; purity test holds; migration snapshot lists updated.
