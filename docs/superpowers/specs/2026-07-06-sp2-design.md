# Sub-project 2 — Check proposals (output-schema tightening) + Self-improvement panel fidelity

**Date:** 2026-07-06
**Status:** Design — approved in session
**Scope:** The propose-and-confirm loop's second revision target and its human surface. Builds on SP1 (honest scoring substrate) and SP1.5 (scoring-plane hardening: honest diagnosis inputs, infra gate, pair-gated falsifier, judge hold-out). SP3 (learning-log timeline, coefficient calibration) stays separate.

---

## 1. Problem

Two gaps remain between the learning loop and something worth trusting:

1. **The loop has one lever, and it's the wrong one for its sharpest diagnosis.** `diagnoseTemplate`'s R4 rule ("false confidence": high pass rate, weak/absent oracle) names a *verification* deficiency, but the only proposal component is `step_instructions` — a prompt edit cannot add a check. The paper names the right lever directly: an Evolution Agent's output may be *"an added validator"* (§3.5.2). Orca's deterministic completion validator — the step `outputSchema` enforced by `validateStepOutput` — is exactly that, and it works for reasoning steps, where R4 actually fires.
2. **The panel under-serves the signals we now persist.** SP1.5 added `targetDelta`/`targetImproved` + the compared version pair (the falsifier's "did the targeted step improve") and the judge has persisted `reasoning` since 5.5 — none of it renders. The pending card's strikethrough-plus-textarea is below the fidelity the SP1 spec's mock called for (before→after diff, confidence, predicted lift).

## 2. Goals / Non-goals

**Goals**
- R4 diagnoses produce **check proposals**: a tightened `outputSchema` for the step, deterministically validated, human-confirmed, applied through the same privileged-write/rollback machinery as instruction edits.
- The **mutation operator is whitelisted and deterministically enforced** — a harness mutation is treated as a change to a safety-critical runtime (paper §5.2.3).
- A **schema-specific canary** watches the one way a tightening goes wrong (completion-validation failures spike) and arms the existing regression/rollback affordance.
- The Self-improvement panel reaches mock fidelity and **surfaces the falsifier and judge honestly**: no invented confidence numbers — verdicts, sample sizes, and measured deltas only.
- Zero jargon in all new copy (five-term ban: oracle/sensor/verdict/refute/veto).

**Non-goals (explicit)**
- Auto-apply / autonomous self-modification (L5 non-goal; FUTURE_ARCHITECTURE: "under human approval").
- Coefficient calibration against false-acceptance rate (SP3; live volume ~6 runs is far below signal).
- Learning-log timeline & applied-change outcome history (SP3).
- Other revision targets (topology, retry limits, gates, guardrail configs). The widened `component` enum is the seam; adding them later is additive.
- Real replayed execution in the judge — imagined execution over persisted outputs remains the documented deferral to the execution-plane split.

## 3. The model

### 3.1 Component widening
`TemplateInstructionProposal.component`: `z.literal("step_instructions")` → `z.enum(["step_instructions", "step_output_schema"])`. For schema proposals, `beforeInstructions`/`afterInstructions` carry the **canonical serialized schema** (`JSON.stringify(schema, null, 2)` of the `WorkflowStepOutputSchema` field list). Reusing the existing columns keeps store, judge, apply, staleness, supersede, and baseline machinery intact. A contract `superRefine` requires both sides to parse as `WorkflowStepOutputSchema` when `component === "step_output_schema"`. No migration (the store already persists the component value; new enum member is additive).

### 3.2 Deterministic routing
`chooseRule` output gains the component: **R4 → `step_output_schema`; R1/R2/R3 → `step_instructions`**. The deterministic core owns which lever is pulled; the LLM only fills the proposal's content. `DiagnosisBundle` gains `component` and, for schema bundles, the step's current serialized schema.

### 3.3 The mutation-operator whitelist (deterministic)
A pure function `validateSchemaTightening(before, after)` in the learning module enforces, at broker `validateProposal` time (before any human sees the proposal):

| Allowed | Banned |
|---|---|
| add a new field (required or optional) | delete a field |
| flip an existing field optional→required | rename a field (delete+add of same type counts as rename only if keys differ — key identity is the test) |
| add/extend a `description` | change a field's `type` or `itemType` |
| | narrow, widen, or otherwise alter an existing field's `enum` |
| | flip required→optional (weakening — never a "tightening") |

Rationale: additive-plus-strictening edits cannot break downstream consumers — splitter `branchKey` routing, gate context reads, and delegate `writes` mappings all reference existing keys/enum values, which the whitelist freezes. Combined with the existing staleness guard (apply refuses if the template version moved since proposal), the **composition contract is invariant under learned schema mutations** (FUTURE_ARCHITECTURE: templates compose by contract). A test asserts the whitelist bans every operation that could invalidate a `branchKey`/`writes` reference.

### 3.4 Propose (R4 prompt)
The R4 propose payload sends: current serialized schema, the step's honest evidence (`falseAcceptanceRate`, `recentRefuteReasons`, tier), and an instruction to produce a **minimal additive tightening** — add checkable fields that force the step to show its work (evidence references, risks, acceptance-criteria mapping), never restructure. New contract `ProposeSchemaRevisionProposal` (`proposedOutputSchema: WorkflowStepOutputSchema`, `predictedImprovement`, `invariantsPreserved: DimensionKey[]`, `rationale`), broker-validated then whitelist-checked; violations reject with a named reason (the broker's retry loop handles resubmission).

### 3.5 Apply / rollback / edit
`apply.ts` gains `setStepOutputSchemaInPlace` (sibling of the instructions writer; same privileged-write discipline, transaction, baseline capture on first built-in edit, supersede, version bump). `applyLearnedInstructionEdit` branches on `component`. Human edits to a pending schema proposal remain possible (the serialized JSON is editable); apply parses + whitelist-validates the edited text and refuses with a readable error on violation — an invalid template can never be written. Rollback restores the `beforeInstructions` serialization; restore-to-default is untouched.

### 3.6 Judge
The counterfactual judge reuses `JudgeInstructionEditRequest` — the schema JSON rides `currentInstructions`/`proposedInstructions`; the request's `step` object gains optional `component` so the judge prompt frames the question correctly: *would the failing outputs have been caught or improved by the tighter required structure?* Corpus, hold-out discipline, minimums, write-once persistence: unchanged.

### 3.7 Falsifier + schema canary
The pair-gated `targetDelta`/`targetImproved` (SP1.5) applies to schema proposals unchanged — the expected movement is verification-strength: tighter schemas push completions out of bare self-report territory, which the honest score rewards. Added for the schema failure mode: the per-step version comparison also emits `versionInvalidOutputRateDelta: number | null` (share of final completions with `failure_code: invalid_output`, latest minus prior version, same `VERSION_MIN` gating). For applied `step_output_schema` proposals, canary flags regression when this delta exceeds `SCHEMA_INVALID_OUTPUT_THRESHOLD = 0.2` (tunable constant beside `REGRESSION_THRESHOLD`) — the "too tight, everything bounces" alarm, with the same rollback affordance. Both deltas remain pure projections; no new storage.

### 3.8 Panel fidelity
- **Pending card → diff modal.** Instructions: line-level before→after diff. Schema: field-level chips — added fields (green, "+ evidence_refs (required list)"), strictened fields (amber, "risks: now required"). Predicts/Preserves retained. Editing stays (textarea in the modal), validation per §3.5.
- **Confidence, honestly.** No invented percentage. The card shows: judge verdict + `addressesFailureMode` + solved/failure sample sizes, and (when applied) the falsifier line. Judge `reasoning` renders as an expandable detail.
- **Falsifier line on applied cards.** "Target step: improved +20 (v3→v4)" / "not improved (−8, v3→v4)" / "awaiting data — needs 2 scored runs on each version." Schema proposals add the canary state when tripped: "New checks are rejecting output (invalid-output rate +N%) — consider rollback."
- All copy passes the five-term jargon guard; the no-jargon test extends over the new strings.

## 5. Edge cases

- **Step already has a maximal schema (32 fields):** whitelist addition would exceed contract caps → propose validator rejects; R4 bundle for that step is skipped with a logged reason (not silently dropped).
- **R4 fires but the step's schema is the terminal interface of a composed template:** allowed — whitelist guarantees `writes` compatibility; version pin on running compositions keeps in-flight runs on the old schema.
- **Human edits the schema JSON into invalid syntax:** apply refuses with the parse error; proposal stays pending.
- **Stale proposal (template moved):** existing supersede-on-apply guard, unchanged.
- **Judge on a schema proposal with < 2+2 corpus:** `insufficient_evidence`, unchanged.
- **invalid-output delta with thin samples:** null below `VERSION_MIN` per side; canary stays quiet — same designed-floor stance as `versionScoreDelta`.

## 6. Alignment

- **Paper §3.5.2:** the new component is the named "added validator" revision target; routing/diagnosis/propose/evaluate/promote stages all map 1:1 onto the Evolution-Agent loop, with promote human-gated.
- **Paper §5.2.3:** the change contract fields all carry over to the new component; the whitelist realizes "defining mutation operators for harness components"; the invalid-output canary realizes "canary deployment" against this operator's specific failure shape (the inverse of "a new verifier may improve pass rate by accepting underspecified solutions").
- **FUTURE_ARCHITECTURE:** control-plane-pure throughout (ShadowAsk/broker + privileged in-place write + projections); proposals remain per-template inside the owner wall; human approval invariant intact; the composition contract (marketplace seam) is provably preserved by the whitelist + staleness guard. The `component` enum is the documented seam for later revision targets.
- **Known deviation (documented, deliberate):** judge = imagined execution over persisted outputs, not replayed execution — deferred to the execution-plane split, per both documents.

## 7. Success criteria (verifiable)

1. An R4-eligible step (fixture: verdictPassRate ≥ 0.8, weak oracle, n ≥ 5) yields a `step_output_schema` proposal; R1/R2/R3 fixtures still yield `step_instructions`.
2. `validateSchemaTightening` accepts each whitelisted op and rejects each banned op (table-driven test); a proposal deleting/renaming/retyping a field never reaches a human.
3. A test proves the whitelist bans every operation that could break a `branchKey` or delegate `writes` reference.
4. Apply on a schema proposal bumps the version and the step's `outputSchema` round-trips; rollback restores the prior schema; an edited-to-invalid JSON is refused with a readable error and the proposal stays pending.
5. The judge runs on a schema proposal (2+2 corpus) and persists a verdict; the request carries `component`.
6. `versionInvalidOutputRateDelta` computes per the same `VERSION_MIN` gating (fixture with an invalid-output spike on the latest version); canary flags regression for an applied schema proposal above threshold, and does not flag instruction proposals on that signal.
7. The panel renders: the before→after diff modal (both components), the falsifier line in all three states, judge reasoning expandable, schema field chips — and the no-jargon guard passes over all of it.
8. Full suites green (contracts, daemon, desktop) and the metrics recompute-twice purity test still holds.
