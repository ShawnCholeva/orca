# Orca — Milestone 3: Goal Creation and Workspaces
## Principal Engineer Architecture and Execution Plan

**Status:** Ready for execution
**Scope:** Milestone 3 only
**Builds on:** Milestone 1 (local runtime, Goal CRUD, event store) and Milestone 2 (internal plugin/skill registries, Quick Goal skill, `skill.invoked` event)
**Primary target:** Prove the refined-Goal + multi-workspace operating loop on top of the existing M1/M2 runtime
**Non-target:** Do not build PTY/session runtime, agent adapters, memory engine, recommendation engine, task graph, workflow engine, file watching, indexing, or Level 4/5 automation

---

## 1. Milestone Purpose

### 1.1 What M3 proves

M1 proved the local runtime loop. M2 proved that a user action can be routed through an internal skill and persisted as an event in the same transaction. M3 must prove exactly one additional product loop:

```text
User starts a Goal creation flow
  -> daemon auto-selects the internal Goal refinement skill
  -> enters a rough Goal
  -> attaches one or more local workspaces
  -> daemon validates paths and inspects basic git metadata
  -> daemon commits refined Goal + workspace attachments in one transaction where applicable
  -> daemon broadcasts the new domain events
  -> UI opens a Goal detail view showing refined Goal fields and attached workspaces
  -> refined Goal and workspaces survive daemon restart
```

Everything else (sessions, memory engine, recommendations, task graph, supervised execution) is out of scope.

### 1.2 Why refined Goal creation is the product entry point

Orca is a Goal-centric coordinator. Every later subsystem — task decomposition, context assembly, memory promotion, recommendations, supervised execution — is **scoped to a Goal**. Until a Goal has structured fields beyond a free-text description, there is nothing for those subsystems to reason about. A "refined" Goal in M3 is intentionally narrow: a Goal that has been processed by a `goal.refine` skill that produces a small, structured object (success criteria, constraints, assumptions). This is the minimum structure the future memory engine, context assembler, and task generator need to operate without parsing free text.

### 1.3 Why Workspaces are required before PTY/session execution

A Session runs an agent against a working directory. Before M4 can spawn a PTY, M3 must:

- give the user an explicit way to declare which local paths are part of a Goal,
- canonicalize and persist those paths,
- prove the path actually exists and is readable,
- record whether the path is a git repo and capture its current branch and dirty status.

Sessions in M4 will accept a `workspaceId` and use its canonical path as `cwd`. Without M3, M4 would either invent ad-hoc path inputs per session or silently bind sessions to arbitrary directories — neither is acceptable for a tool that promises local-first user control.

### 1.4 How Goal-scoped memory remains future-facing without building the memory engine yet

The MVP spec lists "initial Goal memory" as part of M3. The right interpretation is **not** "build the memory extraction/promotion/canonical pipeline". The right interpretation is **"persist the first structured per-Goal facts that the memory engine will later promote to canonical memory items"**.

M3's `goal_refinements` table holds exactly those facts: `successCriteria`, `constraints`, `assumptions`. M5 will introduce the memory engine and its tables; during that migration, refinement fields will be backfilled as `canonical` memory items with `source: goal.refined`. M3 ships no extractor, no promotion rules, no memory tables, no extraction events, no AI inspection loops.

This keeps M3 honest about what it is (Goal-scoped structured fields) and avoids paying for a memory engine that has no second consumer yet.

### 1.5 How M3 prepares for M4 sessions without importing `node-pty` or launching agents

M3 establishes the four pieces M4 needs from the Goal/Workspace domain:

| M4 dependency | What M3 provides | What M3 deliberately does **not** do |
|---|---|---|
| Goal identity for session scoping | Stable `goalId` + Goal detail endpoint | No session lifecycle, no role concept |
| Working directory for a session | Canonical workspace path + `workspaceType` | No `cwd` resolution helper, no cwd validation at spawn time |
| Workspace git context for agent prompts | `branch` + `isDirty` metadata snapshot | No live status streaming, no file watching, no diff |
| Per-Goal structured facts for context injection | `goal_refinements` row | No context assembly, no memory injection, no token budgeter |

There is **no** `node-pty` dependency added in M3, no `Session` type, no `Adapter` interface beyond M2's metadata-only descriptor.

## 2. Scope Review And Simplification

This section locks scope by deciding each candidate feature explicitly.

| Candidate | M3 decision | Why |
|---|---|---|
| Quick Goal improvements | **Keep as-is.** Quick Goal remains the deterministic `goal.create` skill from M2. | M3 introduces a separate refinement path; mutating Quick Goal creates regressions in the M2 loop. |
| Guided Goal Refinement (new skill) | **Include, deterministic only.** New skill `guided-goal-refinement` on a new extension point `goal.refine`. | Establishes the `goal.refine` extension point and the draft-then-commit flow without AI cost. |
| Multi-step refinement UI | **Include, three steps.** Rough input → refinement review → workspace attach/create. | Minimum UX that proves the loop without becoming a wizard framework. |
| Skill picker | **Defer.** The daemon auto-selects the single registered `goal.refine` skill. | Avoids a fake choice and a pseudo-generic skill invocation surface until a second refinement skill exists. |
| Workspace attach during create | **Include.** Required for the exit criteria. | Direct product requirement. |
| Workspace attach to existing Goal | **Include.** | Required to handle the "I forgot a repo" flow without rebuilding the Goal. |
| Workspace remove | **Include.** | Symmetric with attach; trivial cost given the event/projection model. |
| Workspace list | **Include via `GET /v1/goals/:id`.** No standalone workspace-list endpoint in M3. | One detail call returns Goal + refinement + workspaces; a separate list route is redundant before sessions exist. |
| Path validation | **Include.** Must-exist, must-be-directory, must-be-readable. | Without this, M4 sessions silently bind to invalid paths. |
| Git repo detection | **Include, shell-out.** `.git/` presence + `git rev-parse` round-trip. | Required for branch/dirty metadata. Library dependency rejected (see §5). |
| Branch detection | **Include.** | One-line `git rev-parse --abbrev-ref HEAD`. Cheap and necessary. |
| Dirty status | **Include, single porcelain call.** `git status --porcelain` → empty/non-empty. | Bounded cost, deterministic. |
| Initial Goal memory items | **Deferred as a system; the refinement output serves as the seed.** No memory table in M3. | See §1.4. M5 will promote refinement fields into canonical memory. |
| Initial workstreams/tasks | **Deferred.** | Task graph is M7. No M3 dependency. |
| Initial recommendations | **Deferred.** | Recommendation engine is M7. |
| Per-workspace command context | **Deferred.** No per-workspace shell config in M3. | Belongs with sessions (M4). M3 stores only metadata. |
| AI-backed refinement | **Deferred.** Deterministic only in M3. | Token efficiency, reproducibility, and no model-provider dependency yet. The skill interface is shaped so AI variants can ship later without API/event changes. |
| Workspace re-inspection / refresh | **Deferred.** Inspection happens at attach time only. | File watching, polling, and refresh UX are M4+. |
| Workspace tags, descriptions, color | **Deferred.** | Not required by the exit criteria. |
| Workspace types beyond `repo`/`folder` | **Deferred.** `docs`/`tooling` heuristics shipped later. | No reliable deterministic rule yet. |

**Net M3 surface:** one new skill, one new extension point, three new event types, two new tables, five new endpoints (plus one extended), one focused desktop Create Goal flow, one new Goal detail view.

### 3.3 Key flow: attach workspace to existing Goal

```text
UI  POST /v1/workspaces/inspect ─► daemon (pure compute) ─► UI preview
UI  POST /v1/goals/:id/workspaces ─► daemon
                                       ├ inspect again (authoritative)
                                       ├ check duplicate (per canonical path)
                                       ├ TX: INSERT event + INSERT row
                                       └ publish workspace.attached
```

### 3.4 Key flow: remove workspace from Goal

```text
DELETE /v1/goals/:id/workspaces/:wsId
   ├ verify workspace.goal_id === :id (404 otherwise)
   ├ TX: INSERT workspace.removed event, DELETE FROM workspaces WHERE id = ?
   └ publish workspace.removed
```

Removal is a hard delete from the projection but a soft event in history. Future M5 reconstruction can reproduce historical state from events; M3 projection-level deletion is acceptable because M3 has no consumer that needs the historical row.

### 3.5 Key flow: list Goal details

```text
GET /v1/goals/:id
   ├ SELECT goal
   ├ SELECT refinement
   └ SELECT workspaces
   → 200 { goal, refinement|null, workspaces }
```

One round-trip returns everything the Goal detail view needs. The UI does not assemble it from three calls.

### 3.6 Key flow: restart and reload

Daemon boot runs migrations, opens DB, registers plugins/skills (M2), starts HTTP/WS. UI loads `GET /v1/goals` for the list and `GET /v1/goals/:id` when a Goal is opened. WebSocket replays nothing — events are not replayed; the projection is authoritative state. Event ordering is preserved by `seq` for any consumer that needs it (none in M3).

## 5. Technology Decisions

| Decision | Choice | Rationale |
|---|---|---|
| **Path validation** | `node:fs/promises` — `realpath` + `stat` + `access(R_OK)` | Standard library; deterministic; no dep. `realpath` canonicalizes symlinks so duplicate detection is correct. |
| **Path normalization** | Require an absolute input path and store only the canonical realpath in `workspaces.path`. | The canonical path is the identity. Preserving the original input adds privacy and schema surface without serving M3 or M4. |
| **Git detection** | `.git` presence check (`stat` is fine; works for both repos and worktrees because `.git` can be a directory or a file). | Cheap, reliable across worktrees and submodules at the level we care about. |
| **Git CLI vs library** | Shell out to `git` via `node:child_process.execFile` with a 2s timeout and explicit `cwd`. **No** `simple-git`, `isomorphic-git`, `nodegit`. | Two commands total (`rev-parse --abbrev-ref HEAD`, `status --porcelain`). Adding a library buys nothing for that surface and adds a transitive maintenance burden. Users without `git` get a graceful degraded `repo` workspace (path detected, branch/dirty `null` with `gitProbe: 'unavailable'`). |
| **Sync vs async inspection** | Async via `fs/promises` and `execFile`. Inspection runs on the request handler, **awaited before responding**. | Inspection is bounded (<2s typical, hard 5s ceiling per workspace) so synchronous-from-the-caller-perspective is fine. A background pipeline would be premature. |
| **Refinement: deterministic vs AI** | Deterministic only in M3. The skill normalizes whitespace, splits description on conventional cues (`Goals:`, `Out of scope:`, `Constraints:`, bullet lists) and produces empty arrays where no signal exists. | AI introduces token cost, model dependency, non-determinism, and prompt management before there is a memory engine to feed. The `goal.refine` extension point allows an AI variant later without API or event changes. |
| **Zod schema location** | All M3 schemas in `packages/contracts/src/index.ts` — same file as M1/M2 schemas. | Single source of truth for API + WebSocket. Splitting becomes worthwhile when the file passes ~600 lines. |
| **UI state for create flow** | `useReducer` with a tagged-union state in `create-goal-flow/state.ts`. Tested in isolation. | The flow has 4 steps and several async sub-states (inspecting/refining/submitting). `useState` sprawl is the alternative; Redux/Zustand are overkill for one modal. |
| **Test filesystem isolation** | `node:fs/promises.mkdtemp` under `os.tmpdir()`; tests own cleanup with `try/finally`. | No new dep. Avoids polluting `process.cwd()`. |
| **Test git fixtures** | Real `git init` in a temp dir, configured with a per-test name/email. Same `git` binary the daemon uses. | The thing under test is exactly the git interaction; mocking it loses test value. CI must have `git`. |
| **CI git availability** | Document that git-backed tests require `git ≥ 2.20`; runtime handles missing `git` lazily during workspace inspection. | Keeps daemon boot independent of local developer tooling while still making CI requirements explicit. |

### What we are not adding

- `simple-git`, `isomorphic-git`, `nodegit`, `dugite`
- `chokidar` or any FS watcher
- `glob`, `fast-glob`, `ignore`
- `chrono-node`, NLP libraries, embeddings, model SDKs
- Any IPC layer beyond the existing HTTP+WS
- Any state library on the frontend

## 6. Runtime Lifecycle

### 6.1 Daemon boot

Boot sequence (additions over M1/M2 in **bold**):

1. Load config (M1).
2. Open SQLite (M1).
3. Run migrations (M1). **Now applies `0002_workspaces_refinements.sql` on first M3 boot.**
4. Bootstrap registries (M2). **Now registers `guided-goal-refinement` on extension point `goal.refine` under plugin `orca.default-skills`.**
5. Freeze registries (M2).
6. Start HTTP/WS server (M1).
7. Emit `daemon.ready` log line.

`createGoal` and the workspace usecases reference `skillRegistry.byId(...)` and treat a missing skill as a non-recoverable bootstrap error (same pattern as M2 Quick Goal lookup).

### 6.2 Skill registry availability before Goal creation

Skills are registered and frozen **before** the HTTP listener accepts connections. No code path can hit `createGoal` while the registry is still mutable. This invariant from M2 is preserved.

### 6.3 Workspace inspection timing

- `POST /v1/workspaces/inspect` runs inspection on the request thread, awaits all FS/git operations, returns the snapshot. No persistence.
- `POST /v1/goals` (with workspaces) and `POST /v1/goals/:id/workspaces` re-run inspection at commit time. The UI's pre-inspection is treated as an optimistic preview only. Pre-commit re-inspection guards against TOCTOU races (a path deleted between preview and commit must be rejected).
- A per-workspace hard ceiling of 5 seconds applies. Exceeding it returns `inspection_timeout` and aborts the entire request without partial commit.

### 6.4 UI handles disconnected daemon during Goal creation

The existing M1 connection banner remains the source of truth. When connection drops mid-flow:

- The flow does **not** auto-close. Local state (typed title, pasted paths, accepted refinement) is preserved.
- Buttons that require a daemon round-trip (`Refine`, `Inspect`, `Create`) are disabled while `connectionStatus !== 'open'`.
- Once reconnected, the user re-clicks `Refine` / `Inspect` / `Create`. M3 does not implement optimistic submission or retry queues.

### 6.5 Workspace inspection failure

| Failure | Behavior |
|---|---|
| Path missing or unreadable | 400 `workspace_invalid` with code `not_found` / `not_readable`. UI shows inline error on that workspace row. |
| Path is a file, not a directory | 400 `workspace_invalid` code `not_a_directory`. |
| `.git` present but `git` binary unavailable | Accept the workspace as `type: 'repo'`, `branch: null`, `isDirty: null`, `gitProbe: 'unavailable'`. UI shows a non-blocking warning. |
| `git` available but `rev-parse` fails (e.g., bare repo, unborn HEAD) | Accept with `branch: null`, `isDirty: null`, `gitProbe: 'errored'`, payload includes the captured stderr first line for diagnostics. |
| Inspection timeout | 504 `inspection_timeout`. UI shows retry. No partial commit. |
| Multi-workspace commit where one inspection fails | Entire commit rejected with 400. No workspaces persisted, no events emitted. |

### 6.6 Daemon restart

- Projections (goals, goal_refinements, workspaces) reload directly from SQLite. No event replay.
- WebSocket reconnects via existing M1 retry loop.
- UI calls `GET /v1/goals` and (if a Goal detail view was open) `GET /v1/goals/:id` on reconnect.
- Workspace metadata (branch, isDirty) is the snapshot from attach time; it is **not** re-checked on boot. Refreshing workspace metadata is explicitly an M4+ feature.

## 7. Event System Design

### 7.1 New event types

```ts
type DomainEventType =
  | "goal.created"        // M1
  | "goal.updated"        // M1
  | "goal.archived"       // M1
  | "skill.invoked"       // M2
  | "goal.refined"        // M3
  | "workspace.attached"  // M3
  | "workspace.removed";  // M3
```

### 7.2 Payload shapes

```ts
// goal.refined
{
  skillId: string;              // "guided-goal-refinement"
  successCriteria: string[];    // 0..20 entries, each ≤ 200 chars
  constraints: string[];        // 0..20 entries
  assumptions: string[];        // 0..20 entries
}

// workspace.attached
{
  workspaceId: string;          // uuid
  path: string;                 // canonical (realpath)
  name: string;                 // inferred (see §11)
  workspaceType: "repo" | "folder";
  branch: string | null;
  isDirty: boolean | null;
  gitProbe: "ok" | "unavailable" | "errored" | "not_a_repo";
}

// workspace.removed
{
  workspaceId: string;
}
```

`skill.invoked` payload is unchanged from M2: `{ skillId, extensionPoint, durationMs }`.

### 7.3 Persistence rules

- All events append-only into the existing `events` table. No schema change.
- Payloads serialize to JSON; the table already stores `payload TEXT`.
- `goal_id` column is populated for all M3 events (refinement, workspace attach/remove all reference a Goal).

### 7.4 Ordering rules

For a `POST /v1/goals` with refinement + N workspaces, events insert in this fixed order within one transaction:

1. `skill.invoked` (refinement skill)
2. `goal.created`
3. `goal.refined` (only if a refinement payload was produced)
4. `workspace.attached` × N (in user-supplied workspace order; stable on retry)

For a `POST /v1/goals/:id/workspaces`: a single `workspace.attached` event.
For a `DELETE /v1/goals/:id/workspaces/:wsId`: a single `workspace.removed` event.

`seq` (autoincrement) guarantees global linearization; consumers that need causal order use `seq`.

### 7.5 Projection updates

| Event | Projection |
|---|---|
| `goal.created` | `goals` row insert (M1 behavior, preserved) |
| `goal.updated` | `goals` row update (M1) |
| `goal.archived` | `goals` row archive (M1) |
| `skill.invoked` | none (event-only) |
| `goal.refined` | `goal_refinements` row insert-or-replace (latest wins per goalId) |
| `workspace.attached` | `workspaces` row insert |
| `workspace.removed` | `workspaces` row delete |

Projection writes happen inside the same SQLite transaction as the event insert, by the same usecase. M3 does not introduce a "projection runner" or a separate consumer process — that is a Level 4/5 concern.

### 7.6 UI subscription behavior

The UI's existing WebSocket listener (M1) treats incoming events as cache-invalidation hints:

| Event seen | UI reaction |
|---|---|
| `goal.created` / `goal.updated` / `goal.archived` | refetch `GET /v1/goals` (existing M1/M2 behavior) |
| `goal.refined` / `workspace.attached` / `workspace.removed` | if Goal detail view is open for that `goalId`, refetch `GET /v1/goals/:id`; otherwise ignore |
| `skill.invoked` | ignore (M2 behavior preserved) |

Events are signals; the projection is the source of truth. UI never reconstructs state from events directly.

## 8. Database Design

### 8.1 Migration `0002_workspaces_refinements.sql`

```sql
CREATE TABLE goal_refinements (
  goal_id            TEXT PRIMARY KEY,
  skill_id           TEXT NOT NULL,
  success_criteria   TEXT NOT NULL,     -- JSON array<string>
  constraints        TEXT NOT NULL,     -- JSON array<string>
  assumptions        TEXT NOT NULL,     -- JSON array<string>
  refined_at         TEXT NOT NULL,
  FOREIGN KEY (goal_id) REFERENCES goals(id) ON DELETE CASCADE
);

CREATE TABLE workspaces (
  id              TEXT PRIMARY KEY,
  goal_id         TEXT NOT NULL,
  path            TEXT NOT NULL,        -- canonical realpath
  name            TEXT NOT NULL,
  workspace_type  TEXT NOT NULL,        -- 'repo' | 'folder'
  branch          TEXT,                 -- null when unknown
  is_dirty        INTEGER,              -- 0|1|null; null when unknown
  git_probe       TEXT NOT NULL,        -- 'ok' | 'unavailable' | 'errored' | 'not_a_repo'
  attached_at     TEXT NOT NULL,
  FOREIGN KEY (goal_id) REFERENCES goals(id) ON DELETE CASCADE
);

CREATE UNIQUE INDEX idx_workspaces_goal_path
  ON workspaces(goal_id, path);

CREATE INDEX idx_workspaces_goal_attached
  ON workspaces(goal_id, attached_at);
```

### 8.2 Design rationale

| Decision | Rationale |
|---|---|
| `goal_refinements` is a separate table, not columns on `goals` | Refinement is optional, may change shape (success criteria, constraints, assumptions today; risks, glossary tomorrow), and is replaced wholesale on re-refinement. A nullable JSON column on `goals` would conflate concerns. |
| Refinement arrays stored as JSON TEXT, not normalized rows | Each array has tight per-Goal bounds (≤20 items) and is always read/written together. Normalization adds joins for no query benefit at MVP scale. |
| `workspaces.path` is canonical | Identity. Duplicate detection uses the unique index `(goal_id, path)`. |
| `goal_id` is FK with `ON DELETE CASCADE` | If a Goal is hard-deleted later, its refinement and workspaces go with it. M1 only archives Goals; no hard delete path exists today, but the FK is correct. |
| `idx_workspaces_goal_path` is UNIQUE | Enforces "no duplicate path per Goal" at the DB level (defense in depth alongside usecase check). |
| `idx_workspaces_goal_attached` | Supports workspace ordering inside `GET /v1/goals/:id`. |
| No `memory` / `memory_items` table | See §1.4. Refinement fields serve as the seed; M5 introduces memory storage and migrates these. |
| No `sessions`, `tasks`, `recommendations`, `workflows` tables | Out of M3 scope by constraint. |
| No `workspace_metadata_json` blob beyond the JSON arrays in `goal_refinements` | Workspace columns are typed and queried directly; nothing else is structured enough to require a JSON blob yet. |

### 8.3 Migration strategy

- New file `0002_workspaces_refinements.sql` added; existing M1 `0001_init.sql` is untouched.
- The existing `runMigrations()` (M1) handles sorted application and idempotency via `_migrations` table.
- Migration tests (existing `migrations.test.ts` pattern) extended to assert: applying `0002` creates the new tables/indexes; reapplying is a no-op; applying against a fresh DB applies both `0001` and `0002` in order.
- No data migration is needed because there is no existing M2 data shape for refinement or workspaces.

## 10. Skill And Refinement Design

### 10.1 New extension point

```ts
// apps/daemon/src/registry/types.ts
export type SkillExtensionPoint = "goal.create" | "goal.refine";
```

`goal.create` (M2) remains for one-shot creation. `goal.refine` (M3) is for the new draft-and-review flow.

### 10.2 New skill: `guided-goal-refinement`

**Identity**

```ts
{
  id: "guided-goal-refinement",
  pluginId: "orca.default-skills",
  extensionPoint: "goal.refine",
  title: "Guided Goal Refinement",
  description: "Deterministic structuring of a rough Goal into success criteria, constraints, and assumptions."
}
```

**Input schema (zod)**

```ts
GuidedRefinementInput = z.object({
  title: z.string().min(1).max(200),
  description: z.string().max(4000).default("")
});
```

**Output schema (zod)**

```ts
GuidedRefinementOutput = z.object({
  skillId: z.literal("guided-goal-refinement"),
  title: z.string().min(1).max(200),
  description: z.string().max(4000),
  successCriteria: z.array(z.string().min(1).max(200)).max(20),
  constraints:     z.array(z.string().min(1).max(200)).max(20),
  assumptions:     z.array(z.string().min(1).max(200)).max(20)
});
```

### 10.3 Deterministic refinement rules

Input description is split into sections by case-insensitive headers (regex-anchored on line start):

- `Goals?:` / `Success criteria:` / `Outcomes?:` → `successCriteria`
- `Constraints?:` / `Requirements?:` / `Must:` → `constraints`
- `Assumptions?:` / `Given:` → `assumptions`

Inside a section, items are extracted by:

1. Bullet lines (`- `, `* `, `• `, `1.` etc.) → one item per bullet.
2. Otherwise, one item per non-empty line.

Items are trimmed, deduplicated by case-folded equality, truncated to 200 chars, and capped at 20 per array. Anything not matched by a section header is left in `description` verbatim (after collapsing 3+ blank lines).

This is intentionally crude: a deterministic placeholder that gives the memory engine (M5) clean structure to work with. The next iteration of the skill — AI-backed or template-driven — will replace this implementation behind the same input/output contract.

### 10.4 Mapping refined output into persistence

| Output field | Storage |
|---|---|
| `skillId` | `goal_refinements.skill_id` |
| `title` | `goals.title` (Quick Goal normalization still applies as final check) |
| `description` | `goals.description` |
| `successCriteria` | `goal_refinements.success_criteria` (JSON) |
| `constraints` | `goal_refinements.constraints` (JSON) |
| `assumptions` | `goal_refinements.assumptions` (JSON) |

### 10.5 User approval / revision flow

1. UI calls `POST /v1/goals/refine`; the daemon auto-selects `guided-goal-refinement` and returns a draft with editable arrays.
2. User adds/removes bullet points in each array directly in the UI.
3. User confirms → UI calls `POST /v1/goals` with the (possibly edited) `refined` payload.
4. Server validates `refined` against `GuidedRefinementOutput` zod schema; commits if valid.

The server treats the user-edited draft as authoritative. M3 does not implement "regenerate" — the user re-runs the skill from the rough input if they want a fresh suggestion.

### 10.6 Token efficiency posture

- The refinement skill executes in <1ms (pure string ops). No model call.
- Refinement output cap is 60 items × 200 chars ≈ 12KB worst case; typical is <2KB. Suitable for direct inclusion in future context assembly.
- The `goal.refined` event payload mirrors output size (~2KB typical, ~12KB ceiling) and is stored once per Goal-refinement event.

The `goal.refine` extension point reserves space for a future AI-backed skill that is bounded by the same schema (≤20 items × ≤200 chars). Even if M5 introduces an AI variant, output size is hard-capped by schema validation — there is no path to unbounded AI output from this surface.

## 11. Workspace Management Design

### 11.1 Domain model

```ts
interface Workspace {
  id: string;                 // uuid
  goalId: string;
  path: string;               // canonical (realpath)
  name: string;               // inferred or user-supplied
  workspaceType: "repo" | "folder";
  branch: string | null;
  isDirty: boolean | null;
  gitProbe: "ok" | "unavailable" | "errored" | "not_a_repo";
  attachedAt: string;         // ISO timestamp
}
```

### 11.2 Path validation pipeline

In strict order, short-circuiting on failure:

1. Type check: `inputPath` is a non-empty absolute path string ≤ 1024 chars. Relative paths are rejected with `invalid_input`.
2. `await fs.realpath(inputPath)` — canonicalize symlinks. Errors → `not_found`.
3. `await fs.stat(canonical)` — must be a directory. Errors → `not_found`. Non-directory → `not_a_directory`.
4. `await fs.access(canonical, R_OK)` — must be readable. Errors → `not_readable`.

The canonical path becomes `workspaces.path`. The user's original string is not persisted.

### 11.3 Name inference

`name` is `path.basename(canonicalPath)` unless the request explicitly provides a non-empty `name` (≤ 100 chars after trim). Conflict resolution is **not** applied — duplicate names across workspaces of the same Goal are allowed (the canonical path is the identity).

### 11.4 Type inference

`workspaceType` is:

- `'repo'` if `<canonical>/.git` exists (file or directory, `fs.stat`).
- `'folder'` otherwise.

M3 does **not** infer `docs` or `tooling`. Both heuristics are unreliable without more signal than M3 has, and the UI does not yet have surfaces that depend on them.

### 11.5 Git inspection

Only runs when `workspaceType === 'repo'`.

```ts
// Pseudocode
async function inspectGit(cwd: string): Promise<GitMetadata> {
  try {
    const branchProc = await execFile('git', ['rev-parse', '--abbrev-ref', 'HEAD'], { cwd, timeout: 2000 });
    const branch = branchProc.stdout.trim();   // 'main' or 'HEAD' (detached)
    const branchSafe = branch === 'HEAD' ? null : branch;

    const statusProc = await execFile('git', ['status', '--porcelain'], { cwd, timeout: 2000 });
    const isDirty = statusProc.stdout.length > 0;

    return { gitProbe: 'ok', branch: branchSafe, isDirty };
  } catch (err) {
    if (isMissingGitBinary(err)) return { gitProbe: 'unavailable', branch: null, isDirty: null };
    return { gitProbe: 'errored', branch: null, isDirty: null };
  }
}
```

Missing `git` is detected lazily from the bounded `execFile` call. There is no boot-time git probe.

### 11.6 Handling non-git folders

Accepted normally. `workspaceType: 'folder'`, `branch: null`, `isDirty: null`, `gitProbe: 'not_a_repo'`. No warning. The UI displays "Folder" instead of a branch chip.

### 11.7 Handling missing / inaccessible paths

The validation pipeline (§11.2) maps each FS failure to a structured `code` in the 400 response. The UI surfaces these inline on the workspace row in the create flow. No retry happens server-side.

### 11.8 Duplicate prevention

Enforced at two layers:

1. **Usecase check**: before insert, `SELECT id FROM workspaces WHERE goal_id = ? AND path = ?`. If a row exists, return 409 `workspace_duplicate`.
2. **Unique index** `idx_workspaces_goal_path` (§8.1) is the final guarantee against race conditions between concurrent attach requests.

Within a single `POST /v1/goals` request body, duplicate workspaces (same canonical path) are rejected with 400 `duplicate_workspace_in_request` before any DB write.

### 11.9 Path storage policy

- Canonical realpath stored in `path` (identity).
- The original user input is not persisted.
- Tilde expansion is **not** performed server-side. The daemon requires an absolute path. The desktop UI may expand `~` before calling the daemon.

### 11.10 Security / privacy considerations

| Concern | Mitigation |
|---|---|
| The daemon has access to arbitrary local paths | M1 already requires bearer-token auth on all endpoints; only the local desktop app and CLI tools holding the token can attach paths. No remote attacker can attach paths without local file access. |
| A malicious workspace path could escape into other directories | The daemon never executes code from the workspace in M3. `cwd` is set for `git` subprocess calls; `git` itself respects `safe.directory` config and the daemon does not override it. |
| Symlinks could point at restricted paths | `realpath` canonicalization happens once at attach; the canonical path is what is stored. Users see the canonical path in the UI before commit. |
| Path logging | Paths are not logged at INFO. DEBUG logs include the canonical path; `Authorization` header redaction is already configured (M1). |
| `git status` output could leak file names into logs | Captured stdout/stderr from `git status` is **not** logged. Only success/failure + dirty boolean are surfaced. |

### 11.11 Out of scope (workspace)

- File watching, debounced status refresh, "is dirty now?" polling.
- File indexing, full-text search, embedding.
- Per-workspace command/env configuration.
- Workspace tags, colors, descriptions.
- Cross-Goal workspace listing.
- Removing a workspace from disk (we only detach).

## 12. UI Architecture

### 12.1 Create Goal flow

A modal/dialog mounted from the existing M1 goal list. Three logical steps backed by a single reducer:

```text
Step 1 — Rough Goal
  title (required) + description (optional)
  primary: "Refine" → POST /v1/goals/refine → advance with draft

Step 2 — Refinement review
  editable arrays for successCriteria / constraints / assumptions
  add/remove bullet rows inline
  primary: "Continue"
  secondary: "Back"

Step 3 — Workspace attach and create
  list of pending workspaces (initially empty)
  input: paste/type a path, click "Inspect" → POST /v1/workspaces/inspect
  preview chip shows name / type / branch / dirty / probe status
  "Remove" on a pending row
  primary: "Create Goal" (enabled when ≥0 workspaces; allow zero — see §12.5)
  secondary: "Back"
```

Submit collects: `{ title, description, refined, workspaces[] }` → `POST /v1/goals` → on 201, call `GET /v1/goals/:id`, close modal, and navigate to `GoalDetailView(goal.id)`.

### 12.2 Refinement skill auto-selection

No picker renders in M3. The daemon auto-selects the single registered `goal.refine` skill. A picker can be added when a second refinement skill ships; until then, exposing a one-item choice creates avoidable UI and API complexity.

### 12.3 Refinement review UX

The draft is presented as three columns or stacked sections — one per array. Each item is a one-line text input with a delete affordance. An "Add" button appends an empty row to that array. The skill itself is **never re-run** as the user edits; the user's edits are authoritative.

### 12.4 Workspace attach UX

- Input: a single-line text field for absolute path entry. Tilde may be expanded client-side using a Tauri command if running in Tauri; the daemon rejects relative paths.
- "Inspect" debounces 250ms after blur or Enter.
- Loading state shows a spinner on the row.
- On success, the row shows name (editable), type chip (`repo`/`folder`), branch (if any), a dirty dot, and a "Remove" affordance.
- On failure, the row shows an inline error (`not found`, `not readable`, `timeout`, etc.) and a "Retry" affordance.
- Allow up to 8 pending workspaces in a single create request (soft UI cap; server has no cap in M3).

### 12.5 Allowing zero workspaces

The exit criterion is "user can create a refined Goal spanning multiple workspaces", but the daemon does **not** require ≥1 workspace at creation time. Rationale: the user may attach workspaces after creation (`POST /v1/goals/:id/workspaces`). Forcing workspaces at create time blocks valid flows. The UI surfaces a soft warning ("This Goal has no workspaces yet") but allows submit.

### 12.7 Runtime diagnostics

The M2 diagnostics panel (plugins + skills) is preserved verbatim. It lives outside the Goal-scoped views and is reachable from the main shell.

### 12.8 Event subscription / refresh behavior

The single WebSocket listener (M1) dispatches by event type. Refresh decisions are made at the view layer:

- `GoalDetailView` refetches `GET /v1/goals/:id` on any `goal.refined`, `workspace.attached`, or `workspace.removed` whose `goalId === currentGoalId`.

M1 ships a single `App.tsx`. M3 introduces minimal routing: a `mode` state on `App` (`'list'` or `'detail'`) plus a `currentGoalId`. No routing library is added. URL fragments are not maintained for M3; deep-linking is M4+.

### 12.10 Styling

`styles.css` is extended in place. No new CSS-in-JS, no styled-components, no Tailwind in M3. Existing M1 design language is preserved.

| Desktop components | `apps/desktop/src/goal-detail/*.test.tsx` etc. | testing-library with mocked api |

### 14.2 Coverage checklist mapped to the spec section 14 list

| Spec item | How it's covered |
|---|---|
| M1/M2 regression safety | `m1-017.integration.test.ts` and `m2-loop.test.ts` remain unmodified and must pass at every commit. Server test asserts the M2 minimal `{title, description}` create body still works. |

| Attach git and non-git folders | Integration test creates one of each. |

| Reject missing/inaccessible paths | Inspect tests + server test for 400 paths. |

| Event persistence & ordering | Integration test asserts the exact event sequence by `seq`. |

| WebSocket / UI refresh | Server test confirms bus emission post-commit; desktop component test asserts refetch on event. |
| Restart persistence | Integration test closes and reopens the daemon, then re-reads detail. |
| Desktop flow end-to-end | Manual dev-server smoke in M3-011; documented per CLAUDE.md "test UI in browser" rule. |

### 14.3 Determinism rules

- All filesystem fixtures use `fs.mkdtemp(path.join(os.tmpdir(), 'orca-m3-'))`.
- Each test owns cleanup via `afterEach`. No reliance on `process.cwd()`.
- Git fixtures set `user.email`/`user.name` per-test before commit to avoid `commit -m` failures on CI runners without global git config.
- Branch name is read from the result, not hard-asserted — accept `main` or `master` to tolerate environments with different `init.defaultBranch` settings.
- Time-dependent fields are compared structurally (`expect.any(String)` ISO format), not literally.

### 14.4 What is **not** validated in M3

- Behavior with >100 workspaces per Goal (not a real workload; soft UI cap is 8).
- Cross-platform symlink edge cases beyond `realpath` correctness.
- Concurrent attach against the same `(goal_id, path)` from two clients — the unique index is the contract; an explicit test is not added in M3.
- Refinement output stability across locales — refinement is ASCII-pattern based; locale invariance is by construction, not by test.

## 15. Risks and Simplifications

### 15.1 Top technical risks

| Risk | Impact | Mitigation |
|---|---|---|
| `createGoal` becomes async and existing call sites silently drop the promise | High — would cause silent data loss in the M2 path | Change is mechanical; typecheck catches missing `await`; M2 regression test must remain green. |
| Workspace inspection blocks the request handler too long | Medium — UX feels frozen during create | Hard 5s per-workspace ceiling; UI runs inspect step-by-step before commit so the user has visibility. |
| TOCTOU between inspect-preview and commit-time re-inspect | Low — user could delete the path between preview and confirm | Commit-time re-inspect is authoritative; UI surfaces the 400. |
| `git` not present on a developer's machine | Medium — degraded UX | Lazy inspection maps missing binary to `gitProbe: 'unavailable'`; documented in README. |
| FK + cascade interactions with archived goals | Low — M1 only archives, never deletes | M3 keeps the FK because hard-delete may land later; archive flow is unchanged. |
| Unique index race on concurrent attach | Low — single-user local app | Index is the final guard; usecase pre-check minimizes 409 noise. |
| Reducer state divergence across re-renders | Low | All async results flow through reducer actions, never set state directly. |

### 15.2 Product scope risks

| Risk | Mitigation |
|---|---|
| Scope creep into a full Goal command center (panels for sessions, memory, tasks) | Detail view explicitly renders only refinement + workspaces; reviewer rejects new panels in M3 PRs. |
| AI refinement smuggled in | The skill module is named `guided-goal-refinement` and is deterministic; an AI variant must be a new skill with a different id, deferred to M5+. |
| File watching / re-inspection sneak-in | Reviewer rejects any `chokidar` / `fs.watch` import in M3. |

### 15.3 Privacy / security risks

| Risk | Mitigation |
|---|---|
| Local path enumeration via daemon API | M1 bearer-token auth is mandatory; CORS list unchanged. |
| Sensitive file names leaked through `git status` | `git status --porcelain` output is **never** logged or returned; only the boolean `isDirty` surfaces. |
| Symlink traversal | `realpath` is the stored identity; users see canonical paths before commit. |
| Workspace path in logs at INFO | Paths are DEBUG-level only; M1 redaction config preserved. |

### 15.4 Git portability risks

| Risk | Mitigation |
|---|---|
| Different `git` versions behave inconsistently | We use only `rev-parse --abbrev-ref HEAD` and `status --porcelain`, stable since git 2.x. |
| Windows path separators / drive letters | `path.isAbsolute` + `fs.realpath` normalize absolute paths. Acceptance tests on Windows are out of M3 explicit coverage; document as "best-effort." |
| Detached HEAD / unborn HEAD | Treated as `branch: null` with `gitProbe: 'errored'`; not an error to the user. |
| Worktrees and submodules | `.git` may be a file (worktree) or directory (regular); `fs.stat` handles both. Deeper submodule inspection is out of scope. |

### 15.5 Refinement / AI cost risks

- M3 has **zero** AI cost (deterministic skill).
- The schema cap (20 items × 200 chars) is a hard wall that survives the introduction of an AI-backed variant.
- No background reasoning loop. No timers. No queues.

### 15.6 Database migration risks

| Risk | Mitigation |
|---|---|
| `0002` applied to an unmigrated DB | `runMigrations` applies in sorted order; `_migrations` table prevents replay. |
| Mid-migration crash | Migration is a single `db.transaction()` (M1 behavior); SQLite atomicity guarantees all-or-nothing per file. |
| Schema drift between dev DBs and CI | Test fixtures always start from `migrations/` directory; no hand-edited DBs. |

### 15.7 UI complexity risks

| Risk | Mitigation |
|---|---|
| Wizard framework creep | One reducer, three step components, no library. |
| Routing growth | Only `mode`/`currentGoalId` state on `App.tsx`. No URL routing. |
| Style regression | Additive CSS only. Existing M1/M2 selectors untouched. |

### 15.8 Overengineering traps explicitly rejected

| Trap | Why rejected |
|---|---|
| `WorkspaceProvider` interface for pluggable workspace sources | Single consumer (local FS). |
| Generic skill invocation endpoint | One refinement endpoint covers the only M3 use case. |
| Workflow engine for the create flow | A three-step reducer is not a workflow engine. |
| Memory table + extraction stubs | Refinement fields are the seed; M5 owns the engine. |
| `SessionDescriptor` / `AdapterRuntime` types | M4 owns these against real PTY pressure. |
| `FileWatcher` / `WorkspaceRefresher` | Re-inspection is M4+. |
| WebSocket message envelopes / typed broadcast channels | The existing single-event-stream channel is sufficient. |
| Event sourcing reconstruction utility | Projections are the source of truth; no consumer needs replay. |

### 15.9 Things intentionally deferred

- AI-backed refinement.
- Workspace metadata refresh (branch/dirty are attach-time snapshots).
- Workspace tags, descriptions, colors.
- Per-workspace command/env config.
- Cross-Goal workspace listing.
- Memory tables and extraction pipeline.
- Sessions, agent adapters, PTY runtime.
- Task graph, recommendations, workflows.
- Generic `/v1/skills/:id/invoke`.
- URL routing / deep-linking in the desktop app.

## 16. Definition of Done

Milestone 3 is complete when **all** of the following are true:

### 16.1 Functional

1. A user can open the desktop app, click **Create Goal**, enter a rough title and description, click **Refine**, edit the resulting refined draft, attach one or more local workspaces (mixing git and non-git folders), and submit.
2. After submit, the user lands on a Goal detail view that displays:
   - Title and description.
   - Refinement section with success criteria, constraints, and assumptions arrays (if refinement was applied).
   - Workspace list with name, canonical path, type, branch, and dirty status (where applicable).
3. From the detail view, the user can:
   - Attach an additional workspace.
   - Remove a workspace.
4. Closing and reopening the desktop app and daemon leaves the Goal, its refinement, and its workspaces visible in the same state.
5. The M2 minimal create flow (`POST /v1/goals` with `{title, description}` only) still works unchanged, returns the existing create response shape, and produces only the M2 events.

### 16.2 Architectural

6. The following domain events are persisted and broadcast (and only these are new in M3): `goal.refined`, `workspace.attached`, `workspace.removed`. Event ordering within a `createGoal` transaction is: `skill.invoked`, `goal.created`, `goal.refined?`, `workspace.attached*`.
7. The `goal_refinements` and `workspaces` tables exist with the schema in §8.1.
8. The `guided-goal-refinement` skill is registered on extension point `goal.refine` under plugin `orca.default-skills` and remains deterministic.
9. No `node-pty`, no agent process spawn, no Claude Code/opencode adapter code, no FS watcher, no memory extraction engine, no task graph, no recommendation engine, no Level 4/5 supervised execution code has been added.
10. No new top-level package has been introduced; M3 lives under `apps/daemon/src/`, `apps/desktop/src/`, and `packages/contracts/src/index.ts`.

### 16.3 Quality gates

11. `pnpm -r typecheck` is green.
12. `pnpm -r test` is green, including:
    - The M1 integration test `apps/daemon/test/m1-017.integration.test.ts`.
    - The M2 loop test `apps/daemon/src/m2-loop.test.ts`.
    - The new M3 integration test `apps/daemon/test/m3-create-goal-with-workspaces.integration.test.ts`.
    - All new unit tests for the refinement skill, inspection helper, projections, usecases, and reducer.
13. The desktop app has been manually exercised end-to-end with at least one git repo and one non-git folder, and the developer recording the verification has noted the outcome per CLAUDE.md.
14. `README.md` reflects M3 endpoints and the Create Goal flow at a high level.

### 16.4 Non-goals confirmed

15. There is **no** introduction of: PTY/session runtime, agent adapters, memory extraction, recommendation generation, workflow engine, task graph, workspace indexing, workspace file watching, Level 4 approval gates, Level 5 autonomy, AI-backed refinement, cloud sync, or any network call beyond the existing local daemon API.

Only when all fifteen conditions hold is Milestone 3 complete and the codebase ready to enter Milestone 4 (Embedded Sessions).
