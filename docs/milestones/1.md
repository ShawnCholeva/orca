# Orca — Milestone 1: Local Runtime Foundation
## Simplified MVP Execution Plan

**Status:** Ready for execution  
**Scope:** Milestone 1 only  
**Primary target:** Prove the local operational loop quickly  
**Non-target:** Do not build plugin, skill, PTY, memory, recommendation, workflow, or AI reasoning systems in this milestone

---

## 1. Milestone Purpose

Milestone 1 exists to prove the smallest real Orca runtime loop:

```text
Tauri app opens
  -> local Node daemon starts/responds
  -> SQLite opens and migrates
  -> UI creates a Goal through the daemon API
  -> daemon appends a durable event
  -> daemon updates a queryable projection
  -> UI receives a live event and refreshes
  -> Goal survives daemon restart
```

This milestone should optimize for operational learning, not architectural completeness.

The long-term platform remains:

- local-first
- Tauri v2 desktop app
- Node.js/TypeScript daemon
- event-driven
- plugin-oriented later
- skill-oriented later
- PTY/session-based later
- Goal/memory/reasoning-centric later

Milestone 1 proves only the runtime substrate those later systems will use.

### M1 Fitness Function

M1 succeeds if a developer can run the app, create a Goal, observe a persisted event, see the UI update from daemon state, restart the daemon, and still see the Goal.

Do not optimize M1 for hypothetical future scale. Optimize it for proving the local app/daemon/storage/event loop.

## 3. Simplifications Applied

The previous M1 plan was directionally correct but too broad for its exit criteria. These simplifications improve implementation velocity without damaging the future architecture.

| Simplification | Why It Improves Velocity | Why It Is Future-Safe |
|---|---|---|
| Use direct route-to-usecase calls instead of a command bus | Removes dispatch indirection while there is only one domain | Usecase functions can become command handlers when workflows/plugins need interception |
| Keep SQLite internal for M1 instead of a full storage-provider abstraction | Avoids designing for Postgres before there is pressure | SQLite access remains isolated and can be wrapped by a provider in M2+ |
| Keep at most one shared package, `packages/contracts` | Reduces monorepo/package overhead | Contracts remain the future API/schema boundary |
| Defer `core-types` package | Avoids package churn for a tiny domain model | Types can move out once there are multiple domains |
| Defer shared ESLint package | Avoids tooling work before code volume exists | A shared config can be introduced later without app changes |
| Defer plugin and skill directories | Avoids implying unsupported extension points | M2 can introduce real registries and directories together |
| Start with create/list Goals only | Proves the full runtime loop with minimum API surface | Edit/archive endpoints are additive |
| Make WS replay optional/stretch | Avoids reconnection protocol complexity before live events work | Persisted `seq` keeps replay straightforward later |
| Defer daemon auto-restart | Avoids early supervisor state-machine complexity | Failure detection can become restart behavior later |
| Defer production sidecar hardening until after standalone loop | Avoids packaging/native-binding issues blocking product learning | Daemon API and process boundary stay unchanged |
| Keep UI diagnostic and Goal-only | Avoids fake Workspaces/Sessions/Memory panels | Goal command center can emerge when those domains exist |

## 5. High-Level Runtime Architecture

```text
Tauri v2 Desktop App
  - Rust shell starts or connects to local daemon
  - React renderer displays minimal UI
  - Renderer calls daemon HTTP API
  - Renderer listens to daemon WS events

Node.js/TypeScript Daemon
  - owns SQLite database
  - exposes local HTTP API
  - appends Goal events
  - updates Goal projection in same transaction
  - broadcasts committed events to WS clients

SQLite
  - events table
  - goals projection table
  - migrations table
```

### Create Goal Flow

```text
UI submits title/description
  -> POST /v1/goals
  -> daemon validates payload
  -> daemon opens SQLite transaction
  -> append goal.created event
  -> insert goal projection
  -> commit transaction
  -> publish committed event to in-process subscribers
  -> WS sends goal.created to renderer
  -> renderer refetches GET /v1/goals
  -> UI shows new Goal
```

The HTTP response may return the created Goal, but the UI validation path should prove the event-driven refresh works.

### Repository Structure Decisions

| Decision | Rationale |
|---|---|
| Keep `apps/daemon` and `apps/desktop` separate | Preserves the process boundary |
| Keep only `packages/contracts` | UI and daemon need shared wire schemas, but no broader package split yet |
| No `packages/core-types` in M1 | The domain model is too small to justify another package |
| No `packages/eslint-config` in M1 | Root config is sufficient until tooling complexity exists |
| No empty `plugins/` or `skills/` dirs | M2 should introduce real plugin/skill structure with behavior |
| Slightly flatter daemon structure | Faster navigation while there is only one domain |

If the implementation grows beyond this structure during M1, that is a signal the milestone is drifting.

## 7. Technology Decisions

| Concern | M1 Choice | Notes |
|---|---|---|
| Package manager | pnpm | Workspaces without heavier monorepo tooling |
| Monorepo pipeline | pnpm scripts | Defer `turbo` until build time warrants it |
| Daemon runtime | Node 20 LTS + TypeScript | Matches long-term stack |

| WebSocket | Fastify websocket plugin or `ws` | Choose the lower-friction option during implementation |
| Validation | zod | Shared request/response/event schemas |
| DB | better-sqlite3 | Simple synchronous transactions fit local daemon use |
| ORM | None | Raw prepared statements are sufficient |
| Migrations | Numbered SQL files + tiny runner | No down migrations in M1 |
| UI build | Vite | Tauri default path |
| UI state | React state plus simple fetch/refetch | Defer Zustand/TanStack Query unless needed |
| Logging | Console or pino basic logger | File rotation can wait |
| IDs | `crypto.randomUUID()` or ULID | Use built-in UUID unless sortable IDs are needed immediately |
| Production daemon bundle | Stretch | Do not let packaging block proving the loop |

Avoid adding tools solely because later milestones may need them.

## 8. Runtime Lifecycle

### M1 Baseline

1. Tauri app launches.
2. Rust shell starts the daemon or connects to a dev daemon.
3. Daemon reads data directory and port from environment/defaults.
4. Daemon opens SQLite and runs migrations.
5. Daemon starts HTTP/WS server.
6. Renderer obtains daemon endpoint.
7. Renderer calls `GET /v1/health`.
8. Renderer calls `GET /v1/goals`.
9. Renderer opens WS `/v1/events`.

### M1 Daemon Failure Behavior

Baseline behavior:

- detect daemon exit
- show disconnected/down state in UI
- preserve user-visible error state
- allow manual app restart or daemon restart during development

Stretch behavior:

- Tauri restarts daemon once after unexpected exit
- renderer reconnects to new endpoint

Do not implement complex restart backoff, endpoint-change eventing, or replay/catch-up until the basic loop is stable.

### Shutdown

On app close:

- ask daemon to terminate if it was started by Tauri
- close HTTP server
- close SQLite connection
- exit within 5 seconds

Do not require WAL checkpointing as a correctness condition in M1.

## 9. Database Design

One migration is enough.

```sql
CREATE TABLE IF NOT EXISTS _migrations (
  id          INTEGER PRIMARY KEY,
  name        TEXT NOT NULL UNIQUE,
  applied_at  TEXT NOT NULL
);

CREATE TABLE events (
  seq         INTEGER PRIMARY KEY AUTOINCREMENT,
  id          TEXT NOT NULL UNIQUE,
  type        TEXT NOT NULL,
  goal_id     TEXT,
  payload     TEXT NOT NULL,
  created_at  TEXT NOT NULL
);

CREATE INDEX idx_events_goal_seq ON events(goal_id, seq);
CREATE INDEX idx_events_type_seq ON events(type, seq);

CREATE TABLE goals (
  id              TEXT PRIMARY KEY,
  title           TEXT NOT NULL,
  description     TEXT NOT NULL DEFAULT '',
  status          TEXT NOT NULL,
  autonomy_level  INTEGER NOT NULL DEFAULT 1,
  created_at      TEXT NOT NULL,
  updated_at      TEXT NOT NULL,
  archived_at     TEXT
);

CREATE INDEX idx_goals_updated_at ON goals(updated_at);
CREATE INDEX idx_goals_status ON goals(status);
```

### SQLite Rules

- Enable WAL mode.
- Enable foreign keys even if M1 has no foreign keys yet.
- Keep all event append + projection update logic inside one transaction.
- Do not write projections outside the Goal usecase functions.
- Do not add empty future tables.

### Explicitly Deferred Tables

- workspaces
- sessions
- session_events
- tasks
- memory_items
- decisions
- recommendations
- plugins
- skills
- workflows
- user feedback signals

## 10. Event System Scope

M1 needs a durable event log and a live committed-event notification path. It does not need a generalized event framework.

### M1 Event Shape

```ts
type DomainEvent = {
  seq: number;
  id: string;
  type: 'goal.created' | 'goal.updated' | 'goal.archived';
  goalId: string | null;
  payload: Record<string, unknown>;
  createdAt: string;
};
```

Required event:

- `goal.created`

Optional if edit/archive is implemented:

- `goal.updated`
- `goal.archived`

### Deferred Event Fields

| Field | Why Deferred |
|---|---|
| `sessionId` | No sessions exist in M1 |
| `taskId` | No tasks exist in M1 |
| `causationId` | Useful for workflows later, not Goal CRUD |
| `correlationId` | Useful for multi-step orchestration later |

### Event Publish Rule

Only publish events after the SQLite transaction commits.

```text
begin transaction
  append event
  update projection
commit
publish committed event to WS subscribers
```

### Replay

M1 baseline does not require WS replay.

Future replay remains easy because every event has a monotonically increasing `seq`.

Optional stretch:

```text
GET /v1/events?sinceSeq=N
```

Do not build a complex subscribe/caught-up protocol unless needed before M4 session streaming.

### Defer

- cursor pagination
- status filters
- status transition matrix
- daemon restart endpoint
- diagnostics endpoint
- plugin/skill listing endpoints
- workspace/session/memory/recommendation endpoints

### Auth

M1 may use an ephemeral loopback token.

Rules:

- HTTP uses `Authorization: Bearer <token>` if auth is enabled.
- Browser WebSocket cannot reliably set custom headers, so WS may use `?token=<token>` in M1.
- Never log the token.
- Do not build user accounts or identity.

## 12. UI Scope

M1 UI is diagnostic and utility-grade.

Required UI:

- daemon connection status
- create Goal form
- Goal list
- visible error state if daemon is unavailable

Optional UI after the loop works:

- edit Goal title/description
- archive Goal
- basic Goal detail view

Do not build placeholder panels for:

- Workspaces
- Sessions
- Memory
- Decisions
- Recommendations

Those panels should appear when their backing systems exist.

### UI State Rule

For M1, prefer simple state and refetching over complex client-side projections.

On `goal.*` WS event:

```text
refetch GET /v1/goals
```

This is intentionally simple. It proves daemon ownership and avoids duplicate client state logic.

## 13. Execution Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Tauri sidecar packaging with Node and native SQLite binding | High: can block the milestone on packaging instead of product loop | Prove daemon standalone first; make production sidecar packaging late M1 hardening or stretch |
| Browser WS auth headers | High: browser `WebSocket` cannot set arbitrary headers | Use query token for WS in M1; keep token ephemeral and unlogged |
| Event/projection drift | High: undermines event-driven foundation | One transaction owns event append and projection update |
| Over-abstracted storage transaction API | Medium: awkward async/sync boundaries and harder debugging | Keep DB transactions synchronous and local to usecase functions |
| UI double-updates from HTTP response and WS event | Medium: stale or duplicate state | UI refetches on WS event; keep client state simple |
| Custom migration runner bugs | Medium: failed boot or partial migration | Tiny runner, one migration, temp DB test |
| Daemon readiness race | Medium: renderer may call before daemon is ready | Renderer waits for endpoint/health success before enabling UI |
| CORS/dev-origin mismatch | Medium: Vite dev app may fail API calls | Allow local dev origin explicitly in daemon dev mode |
| SQLite native binding mismatch | Medium: install/build friction | Pin Node 20 and document setup |
| Auto-restart/reconnect complexity | Medium: can consume M1 time quickly | Defer auto-restart; detect failure first |

## 14. Implementation Sequence

Build in small executable increments. Each step should leave the system runnable or testable.

### Phase A — Minimal Scaffold

#### A1. Initialize Workspace

Output:

- root `package.json`
- `pnpm-workspace.yaml`
- `tsconfig.base.json`
- `.gitignore`

Validation:

- `pnpm install` succeeds
- `pnpm -r typecheck` runs, even if packages are minimal

#### A2. Add Minimal Packages

Output:

- `apps/daemon`
- `apps/desktop`
- `packages/contracts`

Validation:

- package scripts resolve
- TypeScript project references or workspace imports work

### Phase B — Daemon Loop

#### B1. Daemon Health Server

Output:

- Node daemon starts
- `GET /v1/health` returns `{ status: 'ok' }`

Validation:

- daemon boots locally
- health endpoint responds

#### B2. SQLite Open + Migration

Output:

- data directory creation
- SQLite connection
- migration runner
- `0001_init.sql`

Validation:

- empty data dir creates DB
- reboot does not reapply migration
- expected tables exist

#### B3. Create/List Goals

Output:

- `POST /v1/goals`
- `GET /v1/goals`
- zod request/response validation
- direct usecase function for `createGoal`

Validation:

- POST creates a row in `goals`
- GET returns created Goal

#### B4. Event Append + Projection Transaction

Output:

- `goal.created` event constructor
- append event in same transaction as projection insert
- event `seq` assigned by SQLite

Validation:

- POST creates one `events` row and one `goals` row
- transaction rollback leaves neither row if projection fails

#### B5. Live Event Stream

Output:

- in-process committed-event subscribers
- `WS /v1/events`
- committed `goal.created` event sent to connected clients

Validation:

- connect WS
- create Goal through HTTP
- observe `goal.created` over WS

### Phase C — Desktop Integration

#### C1. Minimal Tauri Shell

Output:

- Tauri app opens a React window
- renderer can display static UI

Validation:

- `pnpm --filter desktop tauri dev` opens a window

#### C2. Daemon Endpoint Wiring

Output:

- renderer receives or is configured with daemon endpoint
- connection status calls `GET /v1/health`

Validation:

- UI shows connected/down accurately

#### C3. Goal UI

Output:

- create Goal form
- Goal list from `GET /v1/goals`
- WS listener refetches list on `goal.*`

Validation:

- create a Goal from UI
- Goal appears in list from daemon state
- UI refresh path works from WS event

### Phase D — Runtime Hardening

#### D1. Restart Persistence

Output:

- documented daemon stop/start flow
- app reload shows existing Goals

Validation:

- create Goal
- stop daemon
- start daemon
- `GET /v1/goals` still returns Goal

#### D2. Graceful Shutdown

Output:

- daemon closes HTTP server and SQLite connection on SIGTERM
- Tauri closes child daemon if it started it

Validation:

- app close does not leave orphan daemon process in normal path

#### D3. Optional Goal Edit/Archive

Only start after the create/list/event/restart loop is stable.

Output:

- optional `PATCH /v1/goals/:id`
- optional `POST /v1/goals/:id/archive`
- optional `goal.updated` / `goal.archived`

Validation:

- edits persist across restart
- archive hides from default list if implemented

#### D4. CI + README

Output:

- CI runs install, typecheck, test, daemon build
- README explains dev startup and data reset

Validation:

- fresh clone reaches running app using README

### Stretch Only

- production daemon bundle
- robust Tauri sidecar packaging
- daemon auto-restart
- WS replay/catch-up
- diagnostics panel

Stretch items must not block M1 completion.

## 15. Validation Strategy

Use scenario gates instead of test-count targets.

Required validation scenarios:

| Scenario | Pass Criterion |
|---|---|
| Daemon boots | `GET /v1/health` returns ok |
| DB initializes | SQLite file exists with `_migrations`, `events`, `goals` |
| Create Goal | `POST /v1/goals` returns created Goal |
| Event persisted | `events` contains one `goal.created` row |
| Projection updated | `goals` contains matching row |
| List Goals | `GET /v1/goals` returns created Goal |
| WS live event | WS receives `goal.created` after HTTP create |
| UI create/list | Desktop UI creates and displays Goal |
| Restart persistence | Goal remains after daemon restart |
| Graceful shutdown | Daemon exits cleanly on SIGTERM |

Optional validation scenarios:

- edit persists after restart
- archive hides Goal from default list
- missing token rejected if auth is enabled
- invalid payload returns 400
- WS reconnects after manual daemon restart

Do not require crash-stress testing, concurrent write stress testing, or full replay validation in baseline M1.

## 16. Definition Of Done

Milestone 1 is complete when all baseline items are true:

1. `pnpm install && pnpm dev` starts the local development environment.
2. The Tauri app opens.
3. The local daemon responds to `GET /v1/health`.
4. SQLite database is created in the configured Orca data directory.
5. Migrations apply once and are tracked.
6. The UI can create a Goal.
7. Creating a Goal appends a `goal.created` event.
8. Creating a Goal updates the `goals` projection in the same transaction.
9. The UI lists Goals from the daemon API.
10. The daemon broadcasts committed Goal events over WS.
11. The UI refreshes after receiving a Goal event.
12. Created Goals survive daemon restart.
13. Daemon shutdown closes cleanly in normal operation.
14. Core typecheck and tests pass in CI.
15. README documents how to run, where data lives, and how to reset local data.
16. No plugin, skill, PTY, memory, recommendation, workflow, or AI reasoning code exists in M1.

### Explicit Non-Requirements For Done

These are not required for M1 completion:

- production-grade sidecar packaging
- daemon auto-restart
- WS replay/catch-up
- full Goal CRUD
- pagination
- diagnostics popover
- cross-platform packaging CI
- crash-stress tests
- plugin/skill placeholders

## 17. Final M1 Statement

Milestone 1 should produce a thin but real runtime spine.

It should not produce a generalized framework for future systems that do not exist yet.

The right M1 outcome is boring and operational:

```text
Open app. Daemon runs. Create Goal. Event persists. UI updates. Restart works.
```

That loop is the foundation every later milestone extends.
