# Orca - Milestone 5: Shared Memory

## Principal Engineer Review and Simplified Execution Plan

**Status:** Complete (M5-017 — 2026-05-19)  
**Scope:** Milestone 5 only  
**Builds on:** M1 local daemon/event loop, M2 internal plugin/skill registries, M3 refined Goals and Workspaces, M4 PTY sessions with capped output tails  
**Proof point:** A user opens a Goal with completed or stopped sessions, the daemon extracts bounded evidence from eligible sessions, commits durable Goal-scoped memory and decisions atomically with domain events, and the Goal detail UI shows those artifacts after live refresh and daemon restart.

Milestone 5 adds one product foundation: durable Goal-scoped memory and decisions extracted from bounded existing evidence. It must not become context assembly, recommendations, workflow automation, transcript analytics, generic skill execution, or a cross-Goal knowledge system.

---

## 1. MVP Product Loop

```text
User opens a Goal with completed or stopped sessions
  -> daemon detects eligible sessions without scanning the workspace
  -> daemon reads Goal/refinement/session metadata and capped M4 output tail
  -> daemon runs one daemon-local extraction job
  -> extractor returns summary, memory candidates, and decision candidates
  -> daemon validates output with zod and normalizes/redacts candidate text
  -> daemon commits summary, memory, decisions, extraction state, and events in one SQLite transaction
  -> daemon broadcasts committed events only after commit
  -> Goal detail UI refetches memory, decisions, sessions, and summaries
  -> user can review, edit, promote/archive memory, and confirm/archive decisions
  -> all committed rows survive daemon restart
```

Everything else is deferred.

## 2. Review Findings: Overengineering To Remove

### Generic extraction and skill infrastructure

Reject generic skill invocation APIs, public extractor invocation endpoints, multi-extractor routing, provider selection, prompt-management frameworks, and model SDK integration in M5.

Why premature: M5 has one extraction shape: convert one Goal-scoped session tail into a summary, memory candidates, and decision candidates. A generic skill or extraction engine creates public API commitments before the deterministic extraction loop has proven useful.

Simpler path: one daemon-local extractor interface with one deterministic implementation and one fake for tests. Keep the input/output shape skill-like so it can become a plugin extension later.

Deferred owner: external plugin ecosystem and AI-backed extraction after deterministic M5 is proven.

### Background queues, workers, schedulers, and workflow engines

Reject worker processes, distributed queues, worker pools, schedulers, workflow engines, and job dashboards.

Why premature: this is a local-first desktop daemon with one user and one SQLite database. Extraction can run serially in-process. Queue durability comes from `memory_extractions`, not infrastructure.

Simpler path: insert a `pending` extraction row, process one row at a time in-process, mark stale `pending`/`running` rows failed on boot, and let the user retry.

Deferred owner: future performance work only if measured extraction volume requires it.

### AI/provider configuration

Reject OpenAI/Anthropic SDKs, API key storage, provider config UI, model selection, prompt template libraries, token accounting beyond hard byte/char caps, and raw prompt/response persistence.

Why premature: provider plumbing adds security, billing, latency, retry, logging, and UX risk before the product proves that extracted memory is useful. It also makes boot/session completion behavior surprising if model calls happen automatically.

Simpler path: deterministic extractor for M5. It cannot hallucinate, is cheap, testable, and enough to prove storage, events, UI, source attribution, and retry behavior.

Deferred owner: post-M5 AI extractor plugin or M6/M7 follow-up, not the core M5 loop.

### Context assembly and prompt injection

Reject context packages, context scoring, prompt bundles, prompt injection into new sessions, sibling-session startup awareness, and context preview UI.

Why premature: M5 creates source material. M6 decides what to inject, how to fit token budgets, and how to expose context to session startup.

Simpler path: expose Goal-scoped memory/decision reads only. Do not build any "assemble context" code or contracts.

Deferred owner: M6 Context Assembly.

### Recommendations, tasks, decisions-as-advice, and autonomy

Reject recommendation generation, task/work-unit generation, task graphs, decision impact analysis, conflict detection, workflow automation, supervised execution, continuous reasoning loops, and autonomous launch controls.

Why premature: decisions in M5 are records to review, not recommendations to act on. M7 needs real memory and decisions before it can generate next steps.

Simpler path: first-class `goal_decisions` with `proposed`, `confirmed`, and `archived` states. Confirmation is manual and has no downstream automation in M5.

Deferred owner: M7 Recommendations; Level 4 supervised execution; Level 5 autonomy.

### Cross-Goal memory and search systems

Reject cross-Goal memory, global dashboards, workspace indexing/file watching, knowledge graphs, embeddings, vector databases, semantic search, memory consolidation, ranking/relevance models, aging/decay, and organizational memory.

Why premature: the Goal is the operational boundary. Cross-Goal memory creates privacy leakage and relevance problems before a single-Goal loop exists.

Simpler path: every M5 row has `goal_id`; every read is Goal-scoped; no global memory endpoint.

Deferred owner: post-MVP learning/search work, if the product earns it.

### Transcript processing and analytics

Reject full transcript capture, transcript replay, transcript analytics, raw terminal output events, and storing raw extractor prompts/responses.

Why premature: M4 deliberately stores a capped output tail, not transcripts. M5 should consume that bounded evidence instead of expanding retention and privacy scope.

Simpler path: read at most a configured byte window from the M4 tail, persist compact source references, and never copy raw output into memory rows or events.

Deferred owner: future terminal/history milestone after retention and redaction policy are explicit.

### UI command center

Reject global memory dashboards, graph views, recommendation panels, task panels, workflow/autonomy controls, provider/model settings, complex filters, analytics, and new routing/deep links.

Why premature: M5 needs the Goal detail page to show memory and decisions. A command center implies orchestration capabilities M5 does not have.

Simpler path: add small panels to the existing Goal detail view plus extraction status on existing session rows.

Deferred owner: later UX milestones after M6/M7 data exists.

## 3. Simplification Decisions

### Keep extraction daemon-local

The M5 extractor is a daemon-local module:

```ts
interface SessionMemoryExtractor {
  version: string;
  extract(input: SessionExtractionInput): Promise<SessionExtractionOutput>;
}
```

It does not need a public skill route, multiple implementations, provider selection, or registry selection. The shape is compatible with a future skill/plugin seam, but M5 calls one configured extractor directly.

MVP velocity: fewer files, fewer contracts, deterministic tests.

Future safety: the input/output schemas become the stable seam for a later plugin-backed extractor.

### Use an in-process serial runner

One `ExtractionRunner` processes pending rows serially. It is started after boot reconciliation and stopped during daemon shutdown.

MVP velocity: no queue infrastructure and no SQLite write contention.

Future safety: `memory_extractions` remains the durable state table, so a worker can be introduced later without changing API or projection rows.

### Detect eligible sessions on Goal open and terminal state

M5 should trigger extraction in two places:

- after a session commits a terminal state (`exited`, `failed`, `stopped`);
- when Goal detail is requested, by enqueueing eligible terminal sessions for that Goal that have no active or succeeded extraction for the current source fingerprint.

The Goal-open detector is Goal-scoped and non-blocking. It does not scan all Goals at boot and does not scan the workspace.

MVP velocity: proves the user story where a Goal already has completed/stopped sessions.

Future safety: when AI extraction exists, this detector can be gated by extractor mode or user setting without changing persistence.

### Keep manual controls but fold action endpoints

Retain manual create/edit/archive/promote for memory and create/edit/confirm/archive for decisions, but expose transitions through `PATCH` instead of separate action endpoints.

MVP velocity: fewer HTTP routes, fewer desktop wrappers, same product behavior.

Future safety: if future UI wants explicit command endpoints for audit/policy, they can wrap the same use cases.

### Drop canonicalization from M5

Canonical memory is a context-assembly concern. M5 only needs:

- `candidate` - extracted or manually created but not promoted;
- `promoted` - approved enough to be first-class Goal memory;
- `archived` - hidden from active views.

Why it improves velocity: one fewer status, endpoint, event, UI control, and test matrix.

Future owner: M6, if context assembly needs a stronger tier than promoted.

### Keep source attribution compact

Source attribution is a pointer:

- source type: `refinement`, `session`, or `manual`;
- source id: Goal refinement id/Goal id, session id, or null;
- optional output byte window;
- extraction id when session-sourced.

Do not persist source lines, raw output, prompts, or model responses.

MVP velocity: small DB and event payloads.

Future safety: M6 can cite sources; full transcript support can later add richer source readers without changing memory identity.

### Use SQLite projection reads

Goal detail panels read `goal_memory_items`, `goal_decisions`, `session_summaries`, and latest extraction status directly. Do not build event replay utilities.

MVP velocity: simple, predictable reads.

Future safety: events still exist for synchronization and audit; replay machinery can be added only if projections need rebuild.

## 7. Reduced API Surface

Minimum public HTTP surface:

### Memory

- `GET /v1/goals/:goalId/memory`
- `POST /v1/goals/:goalId/memory`
- `PATCH /v1/memory/:id`

`PATCH /v1/memory/:id` handles content edits and status transitions:

```json
{ "content": "optional", "type": "optional", "status": "candidate|promoted|archived" }
```

Rules:

- `candidate -> promoted` allowed.
- `candidate|promoted -> archived` allowed.
- `archived` is terminal in M5 except optional unarchive can be deferred.
- invalid transitions return `409 invalid_status_transition`.

Defer separate `promote`, `canonicalize`, and `archive` action endpoints. Defer canonicalization entirely.

### Decisions

- `GET /v1/goals/:goalId/decisions`
- `POST /v1/goals/:goalId/decisions`
- `PATCH /v1/decisions/:id`

`PATCH /v1/decisions/:id` handles content edits and status transitions:

```json
{ "title": "optional", "decisionText": "optional", "rationale": "optional", "status": "proposed|confirmed|archived" }
```

Rules:

- `proposed -> confirmed` allowed.
- `proposed|confirmed -> archived` allowed.
- invalid transitions return `409 invalid_status_transition`.

Defer separate `confirm` and `archive` action endpoints unless existing route style strongly requires command endpoints.

### Summaries and Extractions

- `GET /v1/sessions/:sessionId/summary`
- `POST /v1/sessions/:sessionId/extract-memory`

`POST /v1/sessions/:sessionId/extract-memory` is both manual extract and retry. It returns the active extraction if one already exists for the current source fingerprint. It creates a new row if the latest row failed.

Do not add `GET /v1/sessions/:sessionId/extractions` for history in M5. The existing session list/detail responses should include the latest extraction status needed by the UI. Add the history endpoint later only if support/debugging needs it.

### Existing endpoint additions

- Existing Goal detail/session list reads may include latest extraction status and summary headline/counts to avoid extra UI round trips.
- Live refresh uses existing WebSocket event subscription. Do not add WebSocket commands for memory edits or extraction triggers.

### Endpoints explicitly rejected

- generic skill invocation;
- generic extractor invocation;
- workflow execution;
- context assembly;
- prompt injection;
- recommendations;
- tasks;
- embedding/vector search;
- cross-Goal memory;
- provider/model configuration.

## 8. Event System Scope

Events remain control-plane signals. Payloads carry ids and small metadata, not memory content, decision text, raw output, prompts, or model responses.

### Add these events

Extraction:

- `memory.extraction.requested`
- `memory.extraction.started`
- `memory.extraction.completed`
- `memory.extraction.failed`

Memory:

- `memory.item.created`
- `memory.item.updated`
- `memory.item.promoted`
- `memory.item.archived`

Decisions:

- `decision.created`
- `decision.updated`
- `decision.confirmed`
- `decision.archived`

`memory.extraction.completed` is enough to tell the UI that a session summary may now exist. Do not add `session.summary.created` in M5 unless an existing UI event pattern strictly needs it.

### Event payload rules

- Extraction completed payload: `{ extractionId, sessionId, summaryId, itemCount, decisionCount, promotedCount }`.
- Extraction failed payload: `{ extractionId, sessionId, failureCode }`; failure message stays in the projection row and is capped.
- Memory/decision payloads: ids, goal id, status/type, source type/id. No content.
- All projection updates and events are committed in the same SQLite transaction.
- Broadcast only after commit.
- Desktop refetches projection rows after matching events.

### Do not add M5 events for

- raw terminal output;
- terminal input or resize;
- extractor prompts;
- raw extractor/model responses;
- extractor reasoning traces;
- context packages;
- prompt injection;
- recommendations;
- tasks;
- workflows;
- cross-Goal memory;
- embedding/indexing;
- continuous reasoning;
- agent coordination.

## 10. Extraction Skill / Job Boundaries

### Input

Build input from existing evidence only:

- Goal row.
- Latest Goal refinement fields.
- Attached workspace metadata only, not file contents.
- Session metadata.
- Capped M4 output tail.

Rules:

- read at most `memoryExtractionMaxInputBytes` from the M4 tail; default 128 KiB is enough for MVP;
- keep the most recent bytes if the tail exceeds the cap;
- decode as UTF-8 with replacement;
- strip ANSI/control sequences for extractor input;
- record output byte window;
- mark `truncated=true` if any M4 or M5 cap was hit;
- do not require or create full transcripts.

### Output

The extractor returns:

- `summary`: `{ headline, text, truncated }`;
- `memoryCandidates`: bounded array, max 25;
- `decisionCandidates`: bounded array, max 10.

Every candidate must include source offsets when session-sourced. Zod validates the complete output before persistence. Invalid output marks the extraction failed.

### Deterministic extractor

M5 ships one deterministic extractor. It should be intentionally conservative:

- create summaries from session metadata, status, duration, and last non-empty output lines;
- create blockers from non-zero exit, failure reason, and obvious `ERROR`/`FATAL` lines;
- create open questions from explicit `TODO`, `FIXME`, or question markers;
- create validation results from successful terminal sessions;
- create constraints/success criteria from M3 refinement seed fields;
- create decisions only from explicit markers such as `DECISION:` or `DECIDED:`.

False negatives are acceptable. Unsupported synthesis is not.

### Normalization and redaction

Before persistence:

- trim and collapse whitespace;
- cap memory content and summary/decision fields;
- compute `content_hash`;
- drop duplicate live memory items by `(goal_id, type, content_hash)`;
- apply best-effort redaction for obvious secret assignments such as `password=`, `token=`, `api_key=`, `authorization: bearer`;
- never log candidate content, output lines, prompts, or raw responses.

### Promotion rules

Auto-promote only:

- refinement-sourced constraints and success criteria;
- high-confidence session blockers derived from exit/failure metadata;
- high-confidence validation results derived from clean session completion.

Everything else remains `candidate` for user review.

### Failure and retry

Failure codes should be enumerable and visible:

- `invalid_output`
- `timeout`
- `session_not_terminal`
- `output_unavailable`
- `source_truncated`
- `goal_archived`
- `session_archived`
- `daemon_restart`
- `internal_error`

`source_truncated` should usually be a succeeded extraction with `truncated=true`, not a failure, unless no useful output window can be read.

Retry is explicit through `POST /v1/sessions/:sessionId/extract-memory`. No automatic exponential retry and no queue system.

### Deferred extraction features

Defer model-provider SDK integration, prompt management, provider UI, multi-extractor pipelines, semantic deduplication, embeddings, memory consolidation, confidence calibration, cross-Goal extraction, adapter-specific extraction, full transcript extraction, context injection, recommendation generation, and task generation.

## 11. Memory And Decision Domain

### Memory item model

Keep the type taxonomy small:

- `constraint`
- `success_criterion`
- `assumption`
- `blocker`
- `open_question`
- `validation_result`
- `architecture_note`
- `note`

Statuses:

- `candidate`
- `promoted`
- `archived`

Manual memory uses `source_type='manual'` and starts as `candidate` unless the user explicitly creates it as `promoted`.

Why this is enough: M5 needs reviewable memory, not ranking, search, policy, graph relationships, or context tiers.

### Decision model

Decisions are first-class rows, not just memory items.

Statuses:

- `proposed`
- `confirmed`
- `archived`

High-impact or uncertain extracted decisions must set `confirmation_required=true` and stay `proposed`. M5 does not auto-confirm decisions.

Why this is enough: it preserves a clean M7 seed corpus without building recommendations.

### Source attribution

Every memory item and decision shows one source:

- refinement;
- session and output byte window;
- manual.

If the output tail has since been pruned or is unavailable, the UI shows "source output unavailable" but keeps the memory row.

### Deferred domain behavior

Defer cross-Goal memory, organizational memory, knowledge graph relationships, embedding search, conflict resolution, ranking/relevance algorithms, aging/decay, automatic canonicalization, policy/governance review, decision impact analysis, recommendation generation, and context package assembly.

- decisions grouped by `needs confirmation`, `proposed`, and `confirmed`;
- title, text preview, status, confidence if useful, and source metadata;
- edit action;
- confirm action for proposed decisions;
- archive action.

No recommendations panel or task generation controls.

### Existing sessions area

Add:

- latest extraction badge: none, pending, running, succeeded, failed, truncated;
- manual extract/retry button for terminal sessions;
- summary headline/text display for latest successful summary.

Do not add a new session-memory tab unless the existing session detail view already has a natural section for it.

### Loading/error states

- no memory/decisions yet;
- extraction pending/running;

- output unavailable;
- extracted from truncated output;
- daemon reconnect/refetch.

### Live refresh

Use existing event subscription and refetch. Do not patch rows client-side from event payloads and do not add WebSocket commands.

## 13. Execution Risks And Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Extraction reads too much output | DB/memory growth, slow extraction, privacy exposure | Hard input byte cap; no full transcripts; no raw output persistence. |
| Truncated output hides important facts | Thin or misleading memory | Store `truncated=true`, show it in UI, prefer conservative extraction. |
| Unsupported or hallucinated memory | User trusts false facts | Deterministic extractor only; candidates must cite source offsets; no AI synthesis in M5. |
| Duplicate extraction on retry or double terminal events | Duplicate memory/decisions and confusing UI | Source fingerprint partial unique index; content hash duplicate prevention; active extraction no-op. |
| Failed retry creates duplicate rows | Event and UI noise | Failed extractions are terminal; retry creates a new row but memory insert dedupes by content hash. |
| Automatic promotion too aggressive | Bad facts treated as important | Promote only explicit low-risk rules; user can archive; decisions never auto-confirm. |
| High-impact decision looks confirmed | Unsafe downstream assumptions | Extracted decisions default `proposed`; uncertain/high-impact sets `confirmation_required=true`; M5 has no downstream automation. |
| SQLite event/projection split | UI sees events without rows after crash | Commit projection rows and events in the same transaction; broadcast after commit. |
| Boot leaves stuck running extraction | UI stuck forever | Reconcile `pending`/`running` to `failed` with `daemon_restart` before server listens. |
| Goal-open detection starts too much work | Surprise work and UI churn | Scope detection to the opened Goal; enqueue only terminal sessions without active/succeeded extraction for current fingerprint. |
| Terminal output contains secrets | Secrets become memory or logs | Best-effort redaction before persistence; never log output/candidates; events omit content. |
| Event payload growth | Slow event replay/broadcast | Payloads contain ids/counts/status only; summaries and content fetched by REST. |
| Database growth | Local DB bloat | Candidate count caps, text caps, M4 output tail unchanged, no transcript copies. |
| Desktop stale state | User misses extraction result | Existing WS event subscription triggers refetch; also fetch on Goal detail open/reconnect. |
| M1-M4 regression | Existing loops break | Baseline verification first; targeted regression after daemon integration; do not change M4 PTY/output behavior. |
| AI/provider dependency creep | Schedule slips and unstable tests | No model SDK, no provider UI, no prompt storage in M5. |

## 14. MVP-Appropriate Recommendations Summary

| Recommendation | Why it improves M5 velocity | Why it does not damage future architecture | Deferred owner |
|---|---|---|---|
| Use one daemon-local deterministic extractor | Avoids provider setup, prompt work, network failures, and nondeterministic tests | The extractor input/output contract remains the future seam | Post-M5 AI extractor plugin |
| Use an in-process serial runner | Avoids queue/worker infrastructure and SQLite concurrency issues | Durable state lives in `memory_extractions`, so a worker can later consume the same rows | Performance milestone, only if measured need |
| Trigger on terminal state and Goal open only | Proves the user loop without global scans or schedulers | Future AI mode can gate the same trigger points | AI extraction follow-up |
| Fold promote/archive/confirm into `PATCH` | Cuts route count and desktop wrappers | Explicit command routes can later wrap the same use cases if audit policy needs them | Level 4 policy/audit |
| Drop canonicalization | Removes a status, event, endpoint, and UI path | `promoted` is enough for M5; M6 can add stronger context tiers if needed | M6 Context Assembly |
| Persist confidence but do not rank | Keeps future signal without building relevance UI | M6/M7 can consume confidence; no ranking contract is created | M6/M7 |
| Use compact source attribution | Avoids transcript copies and large event payloads | Future source readers can resolve richer evidence from the same references | Transcript/history milestone |
| Keep events content-free | Prevents event-store growth and accidental content broadcast | REST projections remain the source of detailed state | No deferral; this should remain a control-plane rule |
| Keep memory Goal-scoped | Avoids privacy and relevance problems | Cross-Goal learning can be built later as a separate opt-in system | Post-MVP memory/search |
| Keep UI inside Goal detail | Ships a real review loop without a command center | Global surfaces can consume the same Goal APIs later | Later UX after M6/M7 |
| Seed from M3 refinement fields | Gives useful memory before extraction quality improves | It is deterministic and does not require an import framework | No generalized import until post-MVP |
| Reject context/prompt/recommendation/task endpoints | Prevents Shared Memory from becoming orchestration | M5 projections are exactly the inputs those systems need later | M6 and M7 |

## 15. Revised Implementation Sequence

Each step should be independently testable. Prefer vertical slices that prove storage, events, extraction, and UI reads early.

### M5-000 - Baseline verification

### M5-001 - Contracts

Add reduced M5 schemas and event literals to `packages/contracts`. Compile contracts before daemon code imports them.

Validation: contract tests parse valid memory, decision, summary, extraction, and extractor output shapes and reject oversized/unknown fields.

### M5-002 - SQLite migration

Validation: migration tests cover foreign keys, active extraction uniqueness, and memory duplicate index.

### M5-003 - Goal-scoped read/write projections

Implement memory, decision, summary, and extraction projection helpers. No extractor yet.

### M5-005 - Extraction state lifecycle

Implement enqueue, state transitions, active-row idempotency, latest extraction lookup, and boot reconciliation. Still no extractor.

Validation: pending/running/succeeded/failed transitions, stale row reconciliation, double enqueue no-op.

### M5-006 - Fake extractor commit slice

### M5-007 - Bounded input builder

## 17. Revised Definition Of Done

Milestone 5 is complete when all of these are true:

1. A completed, stopped, or failed M4 session can produce a persisted `session_summary`, zero-or-more memory items, and zero-or-more decisions from bounded metadata and capped output tail.
2. Opening a Goal with eligible terminal sessions can enqueue extraction without requiring full transcripts or workspace scanning.
3. Session terminal-state transitions enqueue extraction after the M4 event commit without destabilizing the PTY runtime.
4. Extractor output is zod-validated, normalized, capped, and best-effort redacted before persistence.
5. Extraction success/failure updates `memory_extractions` and domain events atomically with projection rows.
6. Broadcast happens only after commit.
7. Retry is explicit and does not duplicate live memory items for the same content.
8. Boot reconciliation marks stale `pending`/`running` extractions failed and keeps already-committed memory visible.
9. Goal-scoped memory and decisions survive daemon restart.
10. Goal detail shows memory, decisions, session summary, extraction status, failed/retry states, truncated-output state, and unavailable-output state.
11. Users can create/edit/promote/archive memory and create/edit/confirm/archive decisions through the minimal API.
12. Automatic promotion is limited to deterministic, low-risk rules.
13. High-impact or uncertain decisions remain proposed and user-confirmable.
14. M3 refinement fields seed Goal memory without a generalized import system.
15. Events are small and do not contain raw output, prompts, model responses, or large summaries.
16. No context assembly, prompt injection, recommendations, tasks, workflows, cross-Goal memory, embeddings, vector search, provider configuration, generic skill invocation API, or autonomous execution has been introduced.

When these hold, M5 has proven the shared-memory loop and is ready for M6 to consume the projections for context assembly without M5 having implemented context assembly.
