# Orca — Milestone 2: Plugin and Skill Foundation
## Principal Engineer Review and Simplified MVP Execution Plan

**Status:** Ready for execution  
**Scope:** Milestone 2 only  
**Builds on:** Milestone 1 — Local Runtime Foundation  
**Primary target:** Prove the first internal plugin/skill operating loop with minimum new architecture  
**Non-target:** Do not build external plugins, dynamic loading, PTY, sessions, memory, recommendations, workflows, cloud, or AI reasoning in this milestone

---

## 1. Milestone Purpose

Milestone 1 proved the local runtime loop:

```text
Tauri app -> local daemon -> SQLite -> event -> projection -> UI refresh -> restart persistence
```

Milestone 2 should prove exactly one additional loop:

```text
Daemon boot
  -> registers internal plugin descriptors
  -> registers internal Quick Goal skill
  -> UI can inspect registered runtime capabilities
  -> existing Goal creation path invokes Quick Goal
  -> daemon persists skill.invoked + goal.created atomically
  -> UI sees the same Goal behavior as M1
```

This milestone is about operationalizing the plugin/skill direction, not completing the plugin platform.

The highest-value proof is that the daemon can route a real product action through an internal skill without destabilizing the app/daemon/storage/event loop.

### M2 Fitness Function

M2 succeeds if a developer can:

1. Start the app and daemon exactly as in M1.
2. Confirm the daemon registered the built-in plugin descriptors and the Quick Goal skill.
3. Create a Goal using the existing UI flow.
4. Verify the daemon invoked Quick Goal before Goal creation.
5. Verify `skill.invoked` and `goal.created` are persisted in the same SQLite transaction.
6. Restart the daemon and confirm M1 persistence behavior still works.

Do not optimize M2 for hypothetical future scale. Optimize it for proving the internal operational loop quickly.

## 2. Principal Engineer Review Summary

The original M2 plan is directionally correct but too broad for the next proof point. It introduces several future-facing seams before there is a second implementation or second consumer to justify them.

The most important simplification is this:

```text
Keep plugin and skill concepts internal in M2.
Do not build an external plugin API package yet.
Do not wrap SQLite behind a full storage provider yet.
Do not expose generic skill invocation yet.
```

M2 should be a narrow internal substrate:

```text
Static internal registries + one real skill + one real evented usecase
```

That preserves the platform vision while avoiding premature infrastructure.

## 3. Overengineering To Remove Or Defer

| Item | Why It Is Premature | M2 Action | Why Future Architecture Is Safe |
|---|---|---|---|
| `@orca/plugin-api` package | There is no external plugin consumer, no dynamic loader, and no plugin distribution model yet. A package adds project references, build order, exports, and versioning before the interface has been exercised. | Keep plugin/skill interfaces inside `apps/daemon/src/registry/types.ts`. | Extracting a small internal type file into `packages/plugin-api` later is cheap once the interface has real pressure from sessions, memory, and adapters. |
| Full `StorageProvider` abstraction | M2 has one storage implementation and one database. Wrapping event stores, projection stores, migrations, and transactions now creates a large refactor unrelated to proving skills. | Keep M1 SQLite modules as the storage boundary. Register SQLite as an internal plugin descriptor only. | Future storage provider extraction remains possible if SQLite access stays isolated and route/usecase code does not receive raw database handles. |
| Refactoring all Goal usecases through storage interfaces | This creates risk in the working M1 path before the new value is proven. | Touch only `createGoal` enough to invoke Quick Goal and append `skill.invoked` in the existing transaction. | Other Goal usecases can move behind storage interfaces when a second store or broader domain requires it. |
| Generic `SkillRuntime` | There is one skill and one extension point. A generic runtime with outside-transaction invocation, status taxonomy, and reusable invocation APIs is more framework than product. | Implement a small `invokeGoalCreateSkill(skillId, input)` helper or method owned by the Goal creation path. | The helper can become `SkillRuntime.invoke()` after there are at least two extension points or a generic invocation endpoint. |
| Zod-derived JSON Schema for skills | M2 has no dynamic form rendering and only one fixed create form. Shipping schemas over HTTP adds contract and conversion complexity with no user value. | Use zod internally for validation if useful. Do not expose input/output schemas. | M3/M4 can expose schemas when the UI actually renders variable skill inputs. |
| `/v1/skills/:id` endpoint | Skill detail is not needed while there is one skill and no dynamic UI. | Defer. `GET /v1/skills` is enough. | Detail endpoints are additive. |
| `/v1/adapters` endpoint | There is no PTY/session runtime in M2. Agent adapter metadata is not actionable yet. | Defer the endpoint. Show adapter-capable plugins by filtering `GET /v1/plugins` in the UI if needed. | A dedicated adapter endpoint can be added with real spawn/session capability in the PTY milestone. |
| Shell adapter interface with support matrix | Without PTY, spawn, streaming, lifecycle, or session state, the interface cannot be validated. | Register a minimal `orca.shell-manual` plugin descriptor with capability `agent.adapter`. | The real adapter interface should be designed against the session runtime, not guessed early. |
| Plugin dispose lifecycle | M2 plugins are static descriptors and pure functions. Only SQLite needs shutdown, and M1 already owns DB shutdown. | Keep existing daemon shutdown. Do not add registry disposal yet. | Plugin disposal becomes useful when plugins own processes, watchers, PTYs, or external resources. |
| `EventSubscriber` extension point | No M2 plugin subscribes to events. Declaring unused extension points invites fake architecture. | Defer. | Event subscribers can be introduced when memory extraction, recommendations, or session hooks need them. |
| Full Settings page with tabs | A settings architecture is not necessary to prove runtime capabilities. | Add a small read-only Runtime/Diagnostics panel or simple section that lists plugins and skills. | A full settings page can grow from the same API later. |
| Skill picker on create form | With only Quick Goal, the picker is a no-op and creates a false sense of choice. | Keep the M1 create form. Route it through Quick Goal internally. Optionally show `Using Quick Goal` as read-only text. | A picker can be added when there is a second `goal.create` skill. |
| `POST /v1/goals` request shape change | Changing the public shape forces UI and tests to churn just to select the only available skill. | Preserve the M1 shape: `{ title, description? }`. The daemon chooses `quick-goal`. | M3 can extend the API when multiple create/refinement flows exist. |
| `skill.invoked` input digests and output summaries | Event payload design is drifting toward audit/artifact infrastructure. M2 only needs proof of invocation and ordering. | Persist minimal event payload: `skillId`, `extensionPoint`, `durationMs`. | Optional payload fields can be added later without schema migration because events already store JSON. |
| Failure events for failed skill invocation | Persisting failed invocations introduces semantics before errors are useful to the product. | For M2, log validation/runtime failures and return HTTP errors. Persist only successful `skill.invoked` events that participate in Goal creation. | Failure events can be added when diagnostics, recommendations, or audit views need them. |

## 4. Simplification Opportunities

| Recommendation | Why It Improves MVP Velocity | Why It Does Not Damage Future Architecture |
|---|---|---|
| Keep all M2 interfaces internal to the daemon | Avoids package extraction, workspace wiring, release surfaces, and premature public contracts. | Internal interfaces can be moved once stable; call sites remain typed. |
| Use static registration in one bootstrap function | Makes boot order debuggable and avoids loader/manifest complexity. | Dynamic loading can replace the static list later without changing product flows. |
| Treat plugins as descriptors in M2 | Proves capability registration without lifecycle or sandbox complexity. | Descriptors can gain factories/lifecycle when plugins become executable modules. |
| Treat Quick Goal as a deterministic function | Avoids AI, workflows, retries, prompt management, and artifact storage. | Later skills can use the same extension point with richer internals. |
| Keep Goal creation API unchanged | Minimizes UI/API churn and preserves M1 tests. | Skill selection can be introduced when there is actual choice. |
| Add only one event type | Keeps event evolution simple and focused on the new proof point. | The event store remains append-only and can accept richer event types later. |
| Add no tables and no migrations | Avoids schema churn for runtime-derived data. | Persisted plugin/skill state can be added when install/enable/version state exists. |
| Derive adapter visibility from plugin capabilities | Avoids a fake adapter API before sessions exist. | Dedicated adapter endpoints can appear with PTY/session runtime. |
| Keep UI read-only and diagnostic | Reduces frontend routing/state complexity. | The same data can move into Settings later. |
| Use deterministic validation only | Avoids premature AI reasoning and keeps failures reproducible. | AI-backed refinement belongs in later Goal creation/workspace milestones. |

## 5. Execution Risks And Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Breaking the M1 Goal creation path | High. M2 depends on the M1 operational loop remaining stable. | Preserve the external `POST /v1/goals` shape and UI form. Add the skill invocation behind the existing usecase boundary. |
| Incorrect SQLite transaction boundaries | High. `skill.invoked` without `goal.created`, or the inverse, would weaken the event model. | Generate the Goal ID first, then append `skill.invoked`, append `goal.created`, and update the projection inside one existing SQLite transaction. Broadcast only after commit. |
| Event ordering bugs | Medium. Later systems will assume event order reflects committed domain order. | Persist `skill.invoked` immediately before `goal.created` in the same transaction. Test ordering by `seq`. |
| Over-refactoring storage | High. A broad storage-provider refactor can introduce regressions unrelated to plugins/skills. | Do not introduce `StorageProvider` in M2. Keep SQLite access isolated and make the smallest create path change. |
| Registry boot failures are hard to diagnose | Medium. Static boot errors can prevent the daemon from starting. | Validate duplicate plugin IDs and duplicate skill IDs at boot. Log the offending ID and exit non-zero. |
| IPC/API drift between desktop and daemon | Medium. New request shapes can break the UI. | Keep create Goal API unchanged. Add only read-only list endpoints. Use `@orca/contracts` for response schemas. |
| WebSocket broadcast confusion | Low to medium. The UI may refetch on events it does not care about. | Keep existing `goal.*` refresh behavior. The UI may ignore `skill.invoked`. |
| Tauri sidecar/dev process issues | Medium. Packaging concerns can distract from the runtime proof. | Validate daemon behavior standalone first, then through the desktop app. Do not add sidecar lifecycle changes in M2. |
| Adapter scope drift into PTY | High. PTY/session work is a separate high-risk milestone. | In M2, adapter is metadata only. No spawn, no terminal, no streaming, no node-pty import. |
| Plugin ecosystem scope creep | High. Manifests, permissions, sandboxing, install state, and version compatibility can consume the milestone. | Static internal descriptors only. No filesystem discovery. No JSON manifests. No permissions. |
| SQLite schema churn | Medium. Adding unused tables creates maintenance and migration burden. | No new tables. Events table stores `skill.invoked` as JSON payload like other events. |
| Test matrix growth | Medium. Too many abstraction tests slow implementation. | Test the operational loop and minimal registries. Avoid contract tests for endpoints that are deferred. |

## 6. Milestone Boundary Guardrails

M2 must not drift into these areas:

| Drift Area | Examples To Reject In M2 | Reason |
|---|---|---|
| Level 4 supervised execution | Approval gates, workflow plans, multi-step execution proposals | M2 only proves internal skills on one user action. |
| Level 5 autonomy | Self-directed task execution, autonomous agent launch, automatic next action loops | The user remains fully in control and creates Goals manually. |
| Cloud infrastructure | Sync, accounts, remote plugin catalogs, telemetry pipelines | Orca is local-first and M2 has no network dependency beyond local daemon API. |
| Enterprise architecture | RBAC, policy engines, audit exports, organization settings | No team/multi-user model exists in the MVP. |
| Distributed systems | Queues, workers, distributed event buses, leader election | M2 is one local daemon and one SQLite database. |
| Advanced plugin ecosystem | Dynamic loading, signed manifests, permissions, marketplace, version negotiation | Internal static registration is enough for M2. |
| Orchestration complexity | Command bus, workflow engine, recommendation engine, event subscribers | Later milestones own memory, recommendations, and workflow behavior. |
| PTY/session runtime | node-pty imports, agent process spawn, terminal UI, streaming output | This belongs to the embedded sessions milestone. |
| AI reasoning | Prompt templates, model calls, refinement agents, extraction jobs | Quick Goal is deterministic. |

## 7. Repository Structure Review

Keep the M2 structure small. Do not add a new package or top-level plugin directories yet.

```text
orca/
├── apps/
│   ├── daemon/
│   │   ├── src/
│   │   │   ├── index.ts                    # M1 boot, plus registry bootstrap
│   │   │   ├── server.ts                   # M1 routes, plus read-only registry routes
│   │   │   ├── db.ts                       # M1 SQLite boundary, unchanged except needed event support
│   │   │   ├── events/                     # M1 bus/types, plus skill.invoked type
│   │   │   ├── goals.ts or usecases/goals.ts# M1 Goal usecase, minimally modified
│   │   │   ├── registry/
│   │   │   │   ├── types.ts                # internal Plugin/Skill descriptor types
│   │   │   │   ├── plugin-registry.ts      # static in-process registry
│   │   │   │   ├── skill-registry.ts       # static in-process registry
│   │   │   │   └── bootstrap.ts            # registers built-ins
│   │   │   └── skills/
│   │   │       └── quick-goal.ts           # deterministic goal.create skill
│   │   └── test/                           # focused unit/integration tests
│   │
│   └── desktop/
│       └── src/
│           ├── App.tsx                     # M1 UI, plus small runtime diagnostics section
│           ├── api.ts                      # M1 client, plus listPlugins/listSkills
│           └── styles.css
│
└── packages/
    └── contracts/                          # M1 package, extend with minimal response/event schemas
```

### Structure Recommendations

| Recommendation | Why It Improves Velocity | Why It Is Future-Safe |
|---|---|---|
| Do not create `packages/plugin-api` in M2 | Avoids package build/reference churn before there is an external consumer. | Extract later when interfaces stabilize across multiple domains. |
| Do not create top-level `plugins/` or `skills/` | Avoids implying external discovery/loading. | Add them when plugin installation or built-in packs need separate packaging. |
| Do not create `apps/daemon/src/plugins/sqlite-storage/` | Avoids a storage-provider refactor unrelated to the skill proof. | SQLite can become a provider when storage polymorphism is needed. |
| Keep `skills/quick-goal.ts` small | Makes the first skill easy to inspect and test. | More skills can be added under `skills/` or moved into providers later. |
| Keep registries under `apps/daemon/src/registry/` | Establishes the conceptual boundary without externalizing it. | Registry internals can back a public plugin API later. |

If implementation grows beyond this structure during M2, the milestone is drifting.

## 8. API Surface Reduction

### Keep In M2

```text
GET  /v1/health
GET  /v1/plugins
GET  /v1/skills
POST /v1/goals       # unchanged request shape from M1
```

`GET /v1/health` may include a small registry summary if useful:

```json
{
  "status": "ok",
  "version": "0.2.0",
  "startedAt": "...",
  "registries": {
    "plugins": 3,
    "skills": 1
  }
}
```

`POST /v1/goals` should remain:

```json
{
  "title": "Migrate auth",
  "description": "Plan first"
}
```

The daemon internally treats this as:

```text
skillId = "quick-goal"
extensionPoint = "goal.create"
```

### Defer

| Endpoint Or Surface | Reason To Defer |
|---|---|
| `GET /v1/adapters` | No sessions or PTY runtime exist yet. Adapter-capable plugins can be derived from `/v1/plugins`. |
| `GET /v1/skills/:id` | No dynamic skill detail UI exists. List response is enough. |
| `POST /v1/skills/:id/invoke` | Generic invocation has only one caller and would bypass the concrete Goal creation loop M2 needs to prove. |
| Plugin enable/disable endpoints | No persisted plugin lifecycle exists. |
| Plugin health endpoints | No plugin has independent runtime health in M2. |
| Skill schema/detail endpoints | No dynamic forms or variable input rendering. |
| Adapter spawn/session endpoints | PTY/session milestone. |

Direct route-to-usecase calls are acceptable in M2. A command bus or workflow dispatcher would not improve the operational proof.

## 9. Minimum Viable Event System

M2 should extend the M1 event system only enough to prove skill-mediated Goal creation.

### Add One Event Type

```ts
type SkillInvokedEvent = {
  seq: number;
  id: string;
  type: 'skill.invoked';
  goalId: string;
  payload: {
    skillId: 'quick-goal';
    extensionPoint: 'goal.create';
    durationMs: number;
  };
  createdAt: string;
};
```

### Persistence Rule

```text
begin transaction
  run Quick Goal validation/normalization before writes
  append skill.invoked
  append goal.created
  insert goal projection
commit
broadcast committed events in seq order
```

### Scope Rules

| Rule | Rationale |
|---|---|
| No new tables | Registered plugins and skills are derived from code. |
| No event replay changes | M1 live behavior is enough. |
| No event subscribers | No M2 system consumes events internally. |
| No failure events | Logs and HTTP errors are enough until diagnostics need persisted failures. |
| No input/output artifact storage | M2 only needs proof of invocation. |
| No event schema migration | Existing JSON payload event table is sufficient. |

This is future-safe because the append-only event store remains intact and event payloads can gain optional fields later.

## 11. Revised Implementation Sequence

Each phase should leave the system runnable. Prefer small commits or PRs that can be validated independently.

### Phase 0 — Baseline Verification

**Goal:** Confirm M1 is healthy before changing architecture.

Output:

- Run existing M1 typecheck/test/build commands.
- Manually create a Goal through the app or daemon API.
- Confirm event persistence and restart behavior still work.

Validation:

- Existing M1 Definition of Done remains true.

### Phase 1 — Minimal Contracts And Event Type

**Goal:** Add only the contract surface needed by M2.

Output:

- Add `skill.invoked` to the domain event type union.
- Add response schemas/types for `PluginSummary`, `SkillSummary`, `ListPluginsResponse`, and `ListSkillsResponse`.
- Do not add skill detail, adapter response, JSON schema, or generic invocation contracts.

Validation:

- Contracts typecheck.
- Existing M1 contract tests still pass.

### Phase 2 — Internal Registry Types And Registries

**Goal:** Establish the smallest internal plugin/skill substrate.

Output:

- `apps/daemon/src/registry/types.ts` with internal `PluginDescriptor`, `PluginCapability`, `SkillDescriptor`, and `SkillExtensionPoint` types.
- `PluginRegistry` with `register`, `freeze`, `list`, `byId`, and `byCapability`.
- `SkillRegistry` with `register`, `list`, `byId`, and `byExtensionPoint`.
- Duplicate IDs throw during boot/registration.

Validation:

- Unit tests cover registration, duplicate rejection, freeze behavior, and filtering.

### Phase 3 — Quick Goal Skill

**Goal:** Implement one deterministic skill that can be invoked by Goal creation.

Output:

- `apps/daemon/src/skills/quick-goal.ts`.
- Input: `{ title: string; description?: string }`.
- Behavior: trim title/description, reject blank title, enforce existing M1 field limits, return normalized Goal creation payload.
- No AI calls, no artifacts, no workflow state.

Validation:

- Unit tests cover normalization, blank title rejection, and field limits.

### Phase 4 — Static Bootstrap

**Goal:** Register built-in plugin descriptors and skills at daemon boot.

Output:

- `registry/bootstrap.ts` registers:
- `orca.sqlite` with capability `storage` or `storage.provider` as metadata only.
- `orca.default-skills` with capability `skill.provider`.
- `orca.shell-manual` with capability `agent.adapter` as metadata only.
- `quick-goal` skill with extension point `goal.create`.
- Registries are frozen after boot.

Validation:

- Daemon boot integration test asserts three plugins and one skill are registered.
- Duplicate built-in registration fails fast with useful logs.

### Phase 5 — Route Goal Creation Through Quick Goal

**Goal:** Prove the operational loop.

Output:

- Keep `POST /v1/goals` request body unchanged from M1.
- The create handler/usecase resolves `quick-goal` from the skill registry.
- Quick Goal validates and normalizes input before database writes.
- The existing SQLite transaction appends `skill.invoked`, appends `goal.created`, and updates the Goal projection.
- Broadcast committed events after commit.

Validation:

- Integration test creates a Goal and asserts both events exist in order.
- Integration test forces projection failure and asserts neither event persists.
- Existing M1 Goal create/list/restart tests still pass.

### Phase 6 — Read-Only Registry API

**Goal:** Make runtime registration observable without adding management surfaces.

Output:

- `GET /v1/plugins` returns plugin descriptors.
- `GET /v1/skills` returns skill descriptors.
- `GET /v1/health` optionally returns registry counts.
- All endpoints use existing local auth behavior.

Validation:

- Integration tests assert expected built-ins are returned.
- Unauthorized behavior matches M1 route policy.

### Phase 7 — Minimal Desktop Integration

**Goal:** Show the user/developer that M2 runtime capabilities exist.

Output:

- `apps/desktop/src/api.ts` adds `listPlugins` and `listSkills`.
- Add a small read-only Runtime/Diagnostics section or view.
- Show plugin IDs/capabilities and skill IDs/extension points.
- Keep the existing create Goal form unchanged.
- Optionally show read-only text: `Goal creation uses Quick Goal`.

Validation:

- Desktop renders registered plugins and skills.
- Desktop still creates Goals end to end.

### Phase 8 — Hardening And Documentation

**Goal:** Lock the boundary and prevent scope creep.

Output:

- Tests for registry duplicate IDs and register-after-freeze behavior.
- Tests for invalid Quick Goal input returning the existing validation error shape.
- README/dev note explaining how to add an internal plugin descriptor and internal skill.
- A short note that external plugins, provider extraction, and dynamic loading are intentionally deferred.

Validation:

- Typecheck, tests, and desktop build pass.
- No new packages, migrations, PTY imports, AI calls, workflow code, or plugin loader code exist.

## 14. Revised Definition Of Done

Milestone 2 is complete when all of the following are true:

1. The daemon has internal plugin and skill registry types under `apps/daemon/src/registry/`.
2. The daemon statically registers exactly the built-in M2 descriptors: SQLite storage metadata, default skills metadata, and shell/manual adapter metadata.
3. The daemon registers exactly one skill: `quick-goal` for `goal.create`.
4. The registries are immutable after boot and reject duplicate IDs.
5. `GET /v1/plugins` and `GET /v1/skills` return the registered built-ins.
6. `POST /v1/goals` keeps the M1 request shape and internally invokes `quick-goal`.
7. Successful Goal creation persists `skill.invoked` and `goal.created` in one SQLite transaction, in that order.
8. Failed validation or failed projection writes do not leave partial event rows.
9. The desktop app displays registered plugins and skills in a small read-only runtime diagnostics surface.
10. The desktop app still creates and lists Goals as in M1.
11. M1 restart persistence guarantees still pass.
12. No `packages/plugin-api` package exists yet.
13. No storage-provider abstraction is introduced yet.
14. No new database tables or migrations are added.
15. No `/v1/adapters`, `/v1/skills/:id`, or generic skill invocation endpoint is added.
16. No dynamic plugin loading, manifests, permissions, sandboxing, install state, or plugin lifecycle state exists.
17. No PTY, session, workspace, memory, recommendation, workflow, conflict detection, or AI reasoning code exists.
18. README or dev notes document how to add an internal plugin descriptor and internal skill for now.
19. Typecheck, tests, and desktop build pass.

## 15. Final M2 Statement

The revised M2 outcome should be boring, small, and operational:

```text
Static registries. Three internal plugin descriptors. One deterministic skill.
Existing Goal creation path. One new event. Same stable M1 loop.
```

This proves the platform direction without building the platform future too early.

The correct M2 optimization target is not plugin elegance. It is learning whether Orca can route a real local product action through an internal skill and preserve the resulting reasoning trace in the event log without increasing operational complexity.
