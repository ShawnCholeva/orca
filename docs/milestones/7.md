# Orca — Milestone 7: Suggested Orchestration

## Principal Engineer Review and Simplified Execution Plan

**Status:** Completed
**Scope:** Milestone 7 only
**Builds on:** M1 daemon/event loop, M2 internal plugin/skill registries, M3 refined Goals + workspaces, M4 PTY sessions, M5 Goal-scoped memory/decisions/session summaries, M6 durable context packages.
**Proof point:** After meaningful session activity (or explicit user request), the system generates Goal-scoped work units and bounded recommendations from M3/M5/M6 projections; the user reviews them in a Goal-scoped tasks panel and a recommendations panel; accept/reject/dismiss/modify is persisted as supervision signal; accepted recommendations prefill existing M4 session creation and M6 context preparation; conservative conflicts are visible for human resolution; all state survives daemon restart.

Milestone 7 adds one product foundation: deterministic, supervised next-action suggestions and operational work units derived from existing M3/M5/M6 projections. It must not become a workflow engine, autonomous launcher, continuous reasoning loop, background scheduler, AI-provider configuration platform, prompt-management system, embedding/vector system, cross-Goal knowledge platform, or policy/audit engine.

## 1. Milestone Purpose

M7 is the first milestone where Goal state is turned into **suggested next actions** rather than just remembered. M1-M6 built the substrate:

- M1 gave us a durable event-driven core.
- M2 made first-party features registrable through plugin/skill interfaces.
- M3 gave us refined Goals and attached workspaces.
- M4 gave us live sessions, lifecycle events, and bounded output tails.
- M5 turned session evidence into durable Goal-scoped memory, decisions, and session summaries.
- M6 made startup context bounded, deterministic, role-aware, and adapter-safe.

M5 captured *what was decided and learned*; M6 packaged it *for a specific session*. Neither says *what should happen next*. M7 fills exactly that gap with **explicit, bounded, human-supervised suggestions**.

### Why recommendations are the right next foundation

- M5/M6 only become valuable when their content drives the next operational step. Without M7, every "next session" decision is manual and re-derived from raw Goal detail.
- Recommendations are the smallest unit that closes the orchestration loop: *state change → suggested next action → human-approved follow-through*. Tasks and conflicts are the supporting data types that make recommendations safe, attributable, and reviewable.
- Level 4 supervised execution requires explicit, schema-valid `proposedAction` payloads with source attribution to gate. M7 ships the data shape Level 4 will later approve.

### Why M7 only *suggests*, never *acts*

- Auto-launching sessions, auto-running validation, auto-resolving conflicts, or auto-modifying tasks crosses the MVP autonomy line. Levels 4/5 own that.
- Suggestion-only behavior keeps M7 a *read-many, write-bounded* layer. Generation jobs are idempotent and easy to retry.
- User accept/reject/modify/dismiss feedback is the supervision signal Level 4 will consume; M7 ships the persistence shape without pretending to learn from it yet.

### Why work units exist before Level 4

- Level 4 supervised execution proposes workflows; workflows are sequences of work units. M7 must define the durable, Goal-scoped, role/workspace-aware work unit row before any workflow engine can sequence them.
- Work units give recommendations a stable referent (`taskId`) so multiple recommendations can attach to the same operational target.
- Work units also give the UI a stable second axis (tasks panel vs. recommendations panel) so transient suggestions do not pollute long-lived operational state.

### Why M5/M6 are inputs, not prompt fuel

- M5 memory, decisions, and session summaries are already curated. Re-feeding them as raw text into prompts loses status, confirmation flags, ids, and confidence — exactly the signals a recommendation should reason over.
- M6 context packages already capture role-aware bounded selection. M7 either reuses an existing package by id or asks M6 to assemble a fresh one; it does not re-implement context selection.
- Bounded projection reads keep the recommendation provider deterministic and testable. Raw transcripts/output tails would force token-bloat, redaction logic, and provider integration into the MVP.

### Why job/provider boundaries instead of continuous reasoning

- Continuous reasoning over every event would burn local CPU and (eventually) provider tokens without bounded value.
- An explicit `RecommendationProvider` boundary fits the M6 `SessionPreparationAssembler` precedent: deterministic-first, plugin-replaceable later, in-process for the MVP.
- Generation runs in response to discrete trigger conditions (session completion, manual request, conflict detection), the same way M6 assembly runs only when explicitly prepared.

### Why deterministic triggers and conservative rules

- Deterministic triggers are cheap, testable with fixtures, and survive restart trivially.
- Conservative rules (e.g., "two active sessions on same workspace → potential conflict") produce false positives a human can dismiss; they avoid the false negatives an AI would silently swallow.
- Once the deterministic loop ships, an AI-backed provider can replace the default behind the same interface without changing UI, contracts, or persistence.

### How user feedback becomes supervision signal

- Every `accept`/`reject`/`dismiss`/`modify` emits an event and writes a feedback row tied to the recommendation, the user comment, and the source recommendation snapshot.
- M7 does not learn from these signals; it persists them so Level 4 (and future analytics, optional) can read them as the audit trail behind an autonomy decision.
- Feedback is content-bounded: store the recommendation id, action, optional short note, optional modified payload reference, and timestamp — never raw transcripts or model responses.

### How M7 prepares Level 4 without becoming it

- `proposedAction` is a structured *intent*: `{ kind: 'create_session', adapterId, workspaceId, role, objective, contextPackageId? | contextRequest? }`. M7 only routes accepted actions back into existing M4/M6 flows that already require user confirmation.
- M7 emits no "launch", "approve", or "execute" event. Level 4 will add a separate approval-gate layer above accepted recommendations without changing M7 contracts.
- The `recommendation.accepted` event is the explicit hand-off signal Level 4 can subscribe to later.

### Restart-safety scope

- **Survives restart:** tasks, recommendations (including `superseded` and `accepted`), recommendation feedback rows, conflicts (including `resolved`), accepted-recommendation prefill hints stored on sessions.
- **Reconciled at boot:** `recommendation_generations` and `task_generations` in `pending`/`running` are marked `failed/daemon_restart` with a failure event, matching the M6 assembly reconciliation pattern.
- **Not persisted:** raw provider inputs/outputs, raw model prompts/responses, full transcripts, raw memory text, raw rendered context bytes, generation logs.

### Key flows

#### A. Generate initial work units after Goal refinement

```text
M3 emits goal.refinement.applied
  -> orchestrator.triggers receives committed event
  -> trigger rule: "Goal has refinement but zero tasks" → enqueue one task_generation job
  -> runner picks up job (synchronous, in-process)
  -> task rules read: latest refinement (objective, success criteria, scope, constraints), attached workspaces
  -> deterministic rules synthesize: one task per top-level "do X" line in success criteria, role inferred by keyword, workspace defaulted to single attachment if exactly one
  -> validate output against schema, drop duplicates by content fingerprint
  -> persist task_generation row + N task rows + task.generated + task.created events in one TX
  -> broadcast after commit
  -> Goal detail Tasks panel refreshes
```

User can also POST `/v1/goals/:goalId/tasks/generate` to force a regeneration.

#### B. Update task state after session activity

```text
session.completed (M4) or session_summary.updated (M5)
  -> orchestrator.triggers: "task associated with this session" → schedule task review job (not state mutation)
  -> generates `update_plan` or `mark_complete` recommendation if rules match
  -> user accepts → task usecase transitions status, emits task.status_changed
```

M7 never auto-transitions a task's status. Status changes come from either a user action (PATCH /v1/tasks/:id) or an accepted recommendation routed through the same use case.

#### C. Generate recommendations after meaningful state changes

Trigger inputs (committed events, not output chunks):
- `session.completed` (any outcome)
- `session_summary.created` / `session_summary.updated`
- `memory.promoted` / `memory.canonical`
- `decision.created` / `decision.confirmed` / `decision.confirmation_required`
- `context.package.created`
- `task.created` / `task.status_changed`
- `conflict.detected`
- `user.feedback.recorded` (modify only, not accept/reject — those have explicit followups)

Each trigger is mapped to a *suggestion class*: e.g., `session.completed` → consider `review_output`, `run_validation`, `continue_session`, `update_plan`. Trigger evaluation is rule-based; it does not run for every output chunk or WebSocket frame.

Flow:
```text
committed event
  -> orchestrator.triggers.eval(event) → list of candidate (goalId, suggestionClass)
  -> dedupe against existing active recommendations of the same class within the Goal
  -> if at least one survives: enqueue one recommendation_generation row
  -> runner picks it up (one running generation per Goal at a time)
  -> input.ts builds bounded snapshot: goal, refinement, workspaces, tasks, recent summaries, decisions, memory, latest context package (id only), recent recommendations, recent conflicts — all by id refs
  -> RecommendationProvider.generate(input) returns array of validated recommendation candidates
  -> deduplicate by recommendation fingerprint; mark prior matching active rows superseded
  -> persist generation row + N recommendation rows + corresponding events in one TX
  -> broadcast after commit
```

#### D. Recommend next session or continuation using M4/M6

`create_session` / `continue_session` recommendations carry a `proposedAction` whose payload is exactly the fields the existing `POST /v1/sessions` accepts (plus optional `contextRequest` describing how to assemble a context package). The UI's "Accept" button prefills the existing session creation flow — no new session creation path is added.

#### E. Recommend validation after implementation-like activity

Deterministic rule: a session with role `engineer` reaches `completed` AND its `session_summary` (M5) carries `implementation_evidence=true` (a small flag the rule infers from M5 fields). Action: emit `run_validation` recommendation referencing the task (if associated) with a suggested role `reviewer` or `qa` and a workspace inherited from the source session.

#### F. Recommend review after substantial output or decision changes

Triggers: `decision.confirmation_required`, multiple new memory items of type `architecture_note` since last review, reviewer-role sessions with negative outcome summary.

#### G. Recommend Goal refinement when sparse

Trigger: Goal has open questions in memory **and** refinement fields below a threshold completeness (deterministic check: missing success criteria OR fewer than N items in any required block). Action: `refine_goal`.

#### H. Detect conservative conflicts

Deterministic detector rules (each one a pure function over the projection set):
1. **Active workspace overlap.** Two `sessions.status='running'` for the same `workspace_id` and overlapping `task_id` (or both null with same workspace).
2. **Contradictory decisions.** Two `decisions.status='confirmed'` on the same Goal whose normalized titles share a high token overlap and whose body strings disagree (deterministic string check: same subject, opposite polarity tokens). Conservative — false positives are accepted.
3. **Reviewer rejection.** Session summary contains `outcome='rejected'` from `role='reviewer'`.
4. **Blocker reported.** Memory item of type `blocker` with status not `resolved` referencing an active task.
5. **Unresolved question blocking task.** Memory item type `open_question` linked to a task in status `in_progress`.

Detection runs as part of trigger evaluation. Each new conflict produces a `conflict.detected` event and (separately) one `resolve_conflict` recommendation referencing it.

#### I. Persist atomically and broadcast

All M7 writes follow the M5/M6 atomicity rule: row mutations and domain events go in one SQLite transaction; broadcast happens only after `COMMIT`.

#### J. Accept a recommendation and prefill the relevant flow

```text
POST /v1/recommendations/:id/accept { note? }
  -> emit recommendation.accepted + user.feedback.recorded
  -> response includes proposedAction with all fields needed to call the target endpoint
  -> UI navigates to the target flow (new session or new context package) with fields prefilled
  -> when the user submits the prefilled flow, the resulting POST carries fromRecommendationId
  -> session/context row stores fromRecommendationId; corresponding event includes the link
```

Acceptance does **not** automatically POST to the downstream endpoint. The user must press the existing M4/M6 "Start session" or "Prepare context" button.

#### K. Reject/dismiss/modify and record feedback

- Reject: terminal; cannot be re-accepted. Emits `recommendation.rejected` + `user.feedback.recorded`.
- Dismiss: terminal; signals "not now"; emits `recommendation.dismissed` + feedback.
- Modify: PATCH replaces the user-visible fields (title, rationale, proposed action) and emits `recommendation.modified` + feedback. Provider attribution remains; `source='user_modified'` flag set; original payload snapshot saved on the feedback row.

#### L. Handle provider failure

Generation row transitions to `failed` with a capped, redacted `failure_message`. `recommendation.generation.failed` event emits with `failureCode`. UI shows a retry button; retry creates a new generation row (failed rows are excluded from idempotency).

#### M. Handle missing or sparse inputs

The deterministic provider tolerates missing memory/decisions/summaries/context packages: it produces fewer recommendations and tags them `sparse=true`. It always returns `refine_goal` if a Goal has no refinement.

#### N. Handle oversized inputs/outputs

- Input builder enforces caps mirroring M6: max 30 memory items, 20 decisions, 5 summaries, 10 most recent recommendations, 20 tasks, latest context package id only.
- Output validation: per-recommendation rationale ≤ 4 KiB, title ≤ 256 chars, proposed action JSON ≤ 4 KiB, max 10 recommendations per generation.
- Excess is dropped with a generation warning; never silently truncated.

#### O. Handle daemon restart mid-generation

Boot reconciliation: any `task_generations` / `recommendation_generations` in `pending`/`running` → `failed/daemon_restart` + failure event in one TX, before HTTP listens. Matches M6 pattern.

#### P. Handle archived sources

Tasks/recommendations/conflicts reference source ids that may later be archived. M7 does **not** cascade. Reads tag dangling source refs as `status='source_archived'`; UI shows a small "source archived" badge. Archived Goals hide their tasks/recommendations/conflicts from the Goal detail panels but data remains for audit.

## 5. Technology Decisions

### Recommendation provider: deterministic first, behind an interface

```ts
interface RecommendationProvider {
  readonly id: string;          // 'orca/deterministic-recommendation-provider'
  readonly version: string;     // '0.1.0'
  generate(input: RecommendationInput): Promise<RecommendationProviderOutput>;
}
```

M7 ships one production implementation (deterministic, pure-function rule set) and one fake for tests. **No AI SDK dependency is added in M7.** The interface is the seam an AI-backed plugin can fill later without changing contracts, routes, persistence, or UI.

Rationale: matches M6's `SessionPreparationAssembler` pattern; avoids provider risk (latency, secrets, billing, redaction, prompt management); the deterministic rules are sufficient to satisfy the spec's recommendation types from M5/M6 projections.

### No model SDK in M7

No `anthropic`, `openai`, or other provider SDK is imported. No keys, no key UI, no env-var-driven provider routing.

### Task generation without semantic search

Use M3 refinement structure: success criteria entries already give discrete units of work. Use lightweight keyword classification (deterministic, table-driven) to pick a default role: e.g., "implement|build|add" → `engineer`, "review|audit" → `reviewer`, "design|plan|architect" → `architect`, "verify|test|validate" → `qa`. No embeddings; no model.

### Recommendations from bounded projections only

The recommendation input is a typed snapshot of projection rows by id, identical-in-spirit to M6:

```ts
interface RecommendationInput {
  goal: GoalSnapshot;                              // ids + small fields
  refinement: RefinementSnapshot | null;
  workspaces: WorkspaceSnapshot[];                 // ids, names, branches, dirty flags
  tasks: TaskSnapshot[];                           // capped 20
  recentSummaries: SessionSummarySnapshot[];       // capped 5
  recentDecisions: DecisionSnapshot[];             // capped 20
  recentMemory: MemoryItemSnapshot[];              // capped 30
  latestContextPackageId: string | null;
  activeRecommendations: RecommendationSnapshot[]; // capped 10
  activeConflicts: ConflictSnapshot[];             // capped 10
  recentFeedback: FeedbackSnapshot[];              // capped 10 (signal, not learning)
  trigger: TriggerKind;                            // discriminator
}
```

No raw transcript, no raw context bytes, no raw memory text — fields, not bodies. Memory/decision *bodies* may be included in the snapshot only when the rule reads them deterministically (length-capped and excluded from any persisted log).

### M6 context packages as compact recommendation inputs

When a recommendation needs to suggest "use this context", it references an existing `contextPackageId` if one exists for the proposed adapter/workspace/role/objective fingerprint; otherwise the `proposedAction` carries a `contextRequest` block with the fields needed for `POST /v1/goals/:goalId/context-packages`. M7 does not assemble context itself.

### `proposedAction` decoupled from execution

```ts
type ProposedAction =
  | { kind: 'create_session'; adapterId: string; workspaceId?: string; role: SessionRole; objective: string; contextPackageId?: string; contextRequest?: ContextRequestRef }
  | { kind: 'continue_session'; sessionId: string }
  | { kind: 'review_output'; sessionId: string; reviewerRole?: 'reviewer' | 'qa' }
  | { kind: 'refine_goal'; missingFields: RefinementFieldKey[] }
  | { kind: 'split_task'; taskId: string; suggestedChildren: Array<{ title: string; role?: TaskRole }> }
  | { kind: 'run_validation'; taskId?: string; sessionId?: string; suggestedRole: 'reviewer' | 'qa'; objective: string }
  | { kind: 'resolve_conflict'; conflictId: string; suggestedResolutionNote?: string }
  | { kind: 'update_plan'; taskId: string; suggestedStatus?: TaskStatus; addAcceptanceCriteria?: string[] }
  | { kind: 'ask_user'; question: string }
  | { kind: 'mark_complete'; taskId: string }
  | { kind: 'pause_work'; reason: string; relatedTaskIds: string[] };
```

The discriminator carries enough fields to prefill existing M4/M6 flows or call existing M7 routes. No `execute(action)` function exists in M7. Acceptance returns the action payload; the UI uses it; nothing automatic happens.

### Source attribution by compact id

Identical model to M6:

```ts
interface RecommendationSourceRef {
  type: 'goal' | 'refinement' | 'workspace' | 'task' | 'memory_item' | 'decision' | 'session_summary' | 'session' | 'context_package' | 'conflict';
  id: string;
  reason?: string;          // capped 128 chars, deterministic string ("blocker"|"sparse"|"reviewer_rejected"|...)
}
```

Stored as `sources_json` on `recommendations` (no separate join table in M7).

### Metadata storage

Tasks, recommendations, conflicts: store rendered title/rationale/text alongside structured fields. Source refs are compact JSON; large content (acceptance criteria items, validation steps, proposed-action body) is bounded by per-field caps. No separate join tables for sources — JSON arrays mirror M6.

### Lifecycle modeling

- Tasks: `proposed | open | in_progress | blocked | done | cancelled | archived`. Manual + recommendation-driven; recommendation never moves a task without user accept.
- Recommendations: `proposed | accepted | rejected | dismissed | modified | superseded`. Terminal states: `accepted | rejected | dismissed | superseded`. `modified` is non-terminal; user can still accept/reject after modify.
- Conflicts: `open | resolved | dismissed`.
- Feedback: append-only audit; no status.

### Idempotency and dedup

- Generation idempotency key: `sha256(goalId + ':' + triggerKind + ':' + triggerSourceId + ':' + providerId + ':' + providerVersion + ':' + inputFingerprint)` mirrors M6.
- Recommendation fingerprint (semantic dedup): `sha256(goalId + ':' + type + ':' + canonicalProposedActionJson)` — used to mark prior matching `proposed` rows `superseded` when a new generation produces the same recommendation.
- Task fingerprint: `sha256(goalId + ':' + canonicalTitle + ':' + role)` to prevent duplicate generated tasks; manual tasks bypass.
- Conflict fingerprint: `sha256(goalId + ':' + conflictType + ':' + sorted sourceRefIds)`.

### Superseding stale recommendations

When a new generation produces a fingerprint that matches an existing `proposed` row, the existing row is updated to `superseded`, the new row inserted, and `recommendation.superseded` emitted. `accepted/rejected/dismissed` rows are never auto-modified.

### Retry without a queue

Failed generation rows are terminal and excluded from the active idempotency unique index (same pattern as M6 assemblies). Retry is a fresh `POST /v1/goals/:goalId/recommendations/generate` (or `/tasks/generate`). No backoff, no scheduler.

### Content-bounded events

Same rule as M5/M6: events carry ids, counts, byte sizes, status. Never carry recommendation rationale text, task acceptance-criteria text, proposed-action body, conflict resolution notes, or feedback comments.

### zod validation

- Validate every API request payload at the route boundary.
- Validate `RecommendationProvider.generate` input and output schemas before persistence.
- Validate `proposedAction` against the discriminated union — reject any unknown `kind`.
- Validate generation output array length, per-recommendation field caps.

### Byte budgets

- Recommendation title ≤ 256 chars.
- Recommendation rationale ≤ 4 KiB.
- `proposedAction` JSON ≤ 4 KiB.
- Source refs ≤ 32 per recommendation.
- Task title ≤ 256 chars; description ≤ 8 KiB; acceptance criteria ≤ 20 items × 256 chars; validation steps ≤ 20 items × 256 chars.
- Conflict resolution note ≤ 4 KiB.
- Feedback note ≤ 2 KiB.
- Failure message cap 256 chars.

### Deterministic testing

Every rule is a pure function with snapshot tests. The deterministic `RecommendationProvider` is the production code path; tests use the fake provider only for usecase/route/lifecycle behavior, not for rule correctness.

## 6. Runtime Lifecycle

### Boot sequence (additions)

1. Existing M1-M6 migrations and reconciliations.
2. Apply M7 migrations: `tasks`, `task_generations`, `recommendations`, `recommendation_generations`, `recommendation_feedback`, `conflicts`, plus column adds on `sessions` and `context_packages`.
3. Reconcile in-flight generations: any `task_generations` / `recommendation_generations` rows in `pending`/`running` → `failed` with `failure_code='daemon_restart'`; append `task.generation.failed` / `recommendation.generation.failed` events in the same transaction. Do **not** touch successfully persisted task/recommendation/conflict rows.
4. Register internal skills.
5. Construct `DaemonContext` with deterministic provider/generator/detector.
6. Subscribe `orchestrator/triggers.ts` to the committed-event bus.
7. Start HTTP/WebSocket.

### Trigger evaluation

The trigger subscriber receives committed domain events only. It does not see raw output chunks or WebSocket frames. The trigger map is small and explicit:

| Event | Candidate suggestion classes / detectors |
|---|---|
| `goal.refinement.applied` | task generation (if zero tasks); `refine_goal` (if still sparse) |
| `workspace.attached` | none in M7 |
| `session.completed` | `review_output`, `run_validation`, `continue_session`, `update_plan`, `mark_complete`, active-workspace-overlap conflict re-check |
| `session_summary.created` / `.updated` | `review_output`, `update_plan`, blocker conflict re-check, reviewer-rejection conflict re-check |
| `memory.promoted` / `.canonical` | `update_plan`, `split_task`, open-question conflict re-check |
| `decision.confirmed` | `update_plan`, contradictory-decisions conflict re-check |
| `decision.confirmation_required` | `ask_user`, `refine_goal` |
| `context.package.created` | (informational; no new recommendation) |
| `task.created` / `task.status_changed` | downstream re-check of `mark_complete`, blocked-question conflicts |
| `conflict.detected` | `resolve_conflict` |

Throttling: per Goal, the runner allows at most one in-flight `recommendation_generations` row. While one is running, new triggers update a *pending dirty flag* on the Goal; the runner re-evaluates once on completion. This avoids burst over-generation without a queue.

### Synchronous vs. async generation

Generation runs **in-process, async via Promises, but not in a background worker**. Two routes:

- `POST /v1/goals/:goalId/recommendations/generate` returns 202 with the `generationId` immediately; runner completes in-process; UI subscribes to broadcast events for completion. (Synchronous response would block on rule fan-out and feel slow.)
- Trigger-driven generation runs the same way; UI gets the same events.

`POST /v1/goals/:goalId/tasks/generate` follows the same pattern.

### Manual regeneration

Both `*/generate` endpoints are idempotent on `(goalId, triggerKind='manual', triggerSourceId='manual', inputFingerprint)`. Repeated manual requests within the same input fingerprint return the existing row; a different input (state changed in between) creates a new generation.

### Desktop disconnect

UI uses existing WebSocket. If desktop disconnects mid-generation, the daemon does not abort. On reconnect, UI calls `GET /v1/goals/:goalId/recommendations` and the generation list (folded into the recommendations endpoint or returned via `?includeGenerations=true`) to reconcile state.

### Daemon shutdown mid-generation

Daemon shutdown does **not** wait for generation to finish. In-flight rows are reconciled on next boot. This avoids long shutdown latency and matches M6.

### Restart with open state

After restart:
- Tasks/recommendations/conflicts/feedback survive.
- In-flight generations failed with `daemon_restart`.
- Accepted-recommendation prefill data on sessions/context packages remains visible.
- UI fetches Goal detail and refreshes all three panels.

### UI states

Per panel:
- **Tasks panel:** loading, empty, list, generating banner (one of: pending/running/failed), per-task editing/splitting.
- **Recommendations panel:** loading, empty, list grouped by status (`Active`, `Modified`, `History`), generation banner (pending/running/failed), per-card accept/reject/dismiss/modify, retry on failure.
- **Conflicts banner:** appears only when ≥1 `open` conflict exists; opens drawer listing conflicts with `Resolve` button.

### Live refresh

WebSocket broadcasts (`task.*`, `recommendation.*`, `conflict.*`, `user.feedback.recorded`) trigger targeted refetches:
- `task.*` → refetch tasks panel.
- `recommendation.*` → refetch recommendations panel (and tasks if proposed action touches a task).
- `conflict.*` → refetch conflicts banner.
- Generation events → update banner only; full refetch on `*.generated` and `*.failed`.

### Missing/sparse inputs

The provider:
- Returns `refine_goal` if refinement is missing.
- Returns empty list with `sparse=true` warning if no memory/decisions/summaries exist (single info recommendation: "no recent activity").
- Logs nothing about content; only counts.

### Archived references

When resolving a recommendation/task source ref points to an archived row, UI tags the source as `archived`. Reading endpoints never fail on archived sources. Recommendations whose `proposedAction` targets an archived session/task/context-package are auto-marked `superseded` with `failureCode='source_archived'` during the next generation cycle.

## 7. Event System Design

All M7 events are control-plane. Payloads carry ids, status, counts, byte sizes, and failure codes; never carry task/recommendation/conflict text bodies, source memory text, transcript content, prompts, model responses, or rendered context.

### New event types

```ts
type M7EventType =
  | 'task.generation.requested'
  | 'task.generated'                         // generation completed successfully
  | 'task.generation.failed'
  | 'task.created'                           // user or generator created a task
  | 'task.updated'
  | 'task.split'
  | 'task.status_changed'
  | 'task.associated_with_session'
  | 'task.associated_with_context_package'
  | 'recommendation.generation.requested'
  | 'recommendation.generated'
  | 'recommendation.generation.failed'
  | 'recommendation.accepted'
  | 'recommendation.rejected'
  | 'recommendation.dismissed'
  | 'recommendation.modified'
  | 'recommendation.superseded'
  | 'conflict.detected'
  | 'conflict.resolved'
  | 'conflict.dismissed'
  | 'user.feedback.recorded';
```

Decision: **drop `recommendation.created`**. M7 has no manual recommendation creation path; every recommendation is born from a generation. `recommendation.generated` carries the per-id list; consumers needing per-row notification can broadcast a synthetic event in the UI. This keeps the event log smaller.

### Persistence and ordering rules

- Event rows inserted in the same SQLite transaction as the projection mutation.
- Broadcast after `COMMIT` only.
- One generation produces multiple event rows ordered as: `generation.requested` (if not already emitted at job start) → per-domain creation events → `generation.completed` (logical, expressed as `task.generated` / `recommendation.generated`).
- A single recommendation supersedes multiple prior rows: emit one `recommendation.superseded` per affected row, all in the same TX as the new `recommendation.generated`.
- A single conflict generates both `conflict.detected` AND one `resolve_conflict` recommendation; both go in the same TX as their projection rows.

### Which events drive which projections

| Event | Updates |
|---|---|
| `task.generated` | `task_generations.status='succeeded'` (already inserted as pending); `tasks` rows already inserted |
| `task.generation.failed` | `task_generations.status='failed'` |
| `task.created` | `tasks` row |
| `task.updated` | `tasks` row |
| `task.split` | `tasks` parent + children rows |
| `task.status_changed` | `tasks.status` |
| `task.associated_*` | `tasks` row |
| `recommendation.generation.*` | `recommendation_generations` |
| `recommendation.generated` | `recommendations` rows + `superseded` updates |
| `recommendation.accepted/rejected/dismissed` | `recommendations.status` |
| `recommendation.modified` | `recommendations` fields |
| `recommendation.superseded` | `recommendations.status='superseded'` |
| `conflict.detected/resolved/dismissed` | `conflicts` |
| `user.feedback.recorded` | `recommendation_feedback` |

### Internals that must NOT become events

- Raw provider input payload.
- Raw provider output payload.
- Raw memory/decision/summary text used during generation.
- Raw rendered context bytes referenced by a recommendation.
- Raw transcripts or M4 output tails.
- Prompts, model responses, model tokens, model errors with full payload.
- Internal rule-evaluation traces.

Reason: the same content-free events rule from M5/M6 — event log is a public API surface; large/private payloads belong in feature-specific tables or nowhere.

### Payload size limits

≤ 4 KiB serialized per event. Enforced in tests on every event constructor.

### Source references in events

Events identify subjects (`goalId`, `taskId`, `recommendationId`, `conflictId`, `sessionId`, `contextPackageId`) and counts only. Full source ref lists live on the row (`sources_json`), readable through the projection endpoints.

### Idempotent restart-safety

- `task_generations` and `recommendation_generations` use `request_fingerprint` like M6 assemblies. Boot reconciliation marks any non-terminal row as `failed/daemon_restart` and emits the matching `*.generation.failed` event in the same TX as the row update.
- `recommendation_feedback` is append-only. Accept/reject/dismiss are idempotent at the route level by `(recommendationId, action)`: repeated accept on an already-accepted recommendation returns 200 without emitting a new feedback row.
- `conflicts` use `conflict_fingerprint` (sorted source ref ids + type) to avoid duplicate `conflict.detected` events for the same underlying state.

### Indexes summary (rationale)

- Goal-status-created tuples on tasks, recommendations, conflicts: powers Goal detail panel reads in order.
- Active fingerprint unique indexes: enforce dedup at the DB layer; M6 pattern.
- Generation status indexes: powers boot reconciliation lookup.
- Feedback terminal-action unique: enforces "one accept, one reject, one dismiss" per recommendation.

### Migration strategy

- Single forward migration `m7-001-suggested-orchestration.sql` containing all five `CREATE TABLE`s, two `ALTER TABLE`s, and all indexes.
- M6-baseline DBs: migration adds columns with `NULL` default; existing rows unaffected.
- M5-baseline DBs (somehow without M6): not supported; M7 requires M6 schema.
- Migration tests cover fresh DB and upgrade from a recorded M6 fixture DB.

### Retention / supersede / archive

- Tasks: `archived` status is final; rows kept. Archived Goals hide tasks from list endpoints; rows retained for audit.
- Recommendations: terminal rows (`accepted/rejected/dismissed/superseded`) kept indefinitely in M7. No GC. List endpoints page by `created_at DESC`.
- Conflicts: terminal rows kept.
- Feedback: append-only.
- Generations: kept for audit; failed rows kept indefinitely.

If local DB growth becomes a concern (measured, not assumed), a future milestone can add a retention policy. M7 does not add one.

### Reject new tables

No M7 tables for workflows, approval gates, autonomous runs, policy/governance, prompt libraries, prompt experiments, embeddings, vector indexes, cross-Goal memory, provider configuration, workspace scans, recommendation analytics, scoring/aging/decay.

## 10. Task / Work Unit Domain Design

### Model fields (canonical)

```ts
interface Task {
  id: string;
  goalId: string;
  parentTaskId: string | null;
  workspaceId: string | null;
  role: TaskRole;                     // 'architect' | 'engineer' | 'reviewer' | 'qa' | 'generalist'
  status: TaskStatus;
  origin: 'user' | 'generator' | 'recommendation';
  title: string;
  description: string;
  acceptanceCriteria: TaskAcceptanceCriterion[];
  validationSteps: TaskValidationStep[];
  dependencies: string[];             // task ids, same Goal
  sources: TaskSourceRef[];
  generationId: string | null;
  fingerprint: string;
  createdAt: string;
  updatedAt: string;
  archivedAt: string | null;
}

interface TaskAcceptanceCriterion {
  id: string;
  text: string;                       // ≤ 256 chars
}

interface TaskValidationStep {
  id: string;
  text: string;                       // ≤ 256 chars
  kind: 'manual' | 'test' | 'review' | 'qa';   // hint, not executable
}

interface TaskSourceRef {
  type: 'refinement' | 'memory_item' | 'decision' | 'session_summary' | 'context_package' | 'recommendation';
  id: string;
  reason?: string;                    // ≤ 128 chars
}
```

### Lifecycle

```text
proposed (only created via recommendation acceptance for split_task)
  -> open                       (user activates or generator default)
  -> in_progress                (session associated and started, or user moves)
  -> blocked                    (recommendation accepted with blocker, or user moves)
  -> done                       (user moves, or mark_complete recommendation accepted)
  -> cancelled
  -> archived
```

Status guards:
- `proposed → open` requires no precondition.
- `open ↔ in_progress`, `in_progress ↔ blocked`: free transitions.
- `→ done`: requires no unmet dependency; warning surfaced if acceptance criteria are present but no validation step has been satisfied (deterministic check — does not block).
- `→ cancelled` from any non-terminal state.
- `→ archived` from terminal only.

### Parent/child + split

- `split_task` recommendation creates N child tasks (status `proposed`) with `parent_task_id` set.
- Manual `POST /v1/tasks/:id/split` does the same. Parent's status may move to `blocked` if `setParentStatus='blocked'`.
- Children inherit `workspace_id` and `goal_id` from parent unless overridden in request.
- Dependencies: simple `string[]` of task ids within the same Goal. No graph engine; UI shows them as chips.

### Role + workspace

- Role enum identical to M6's context-role enum: `architect|engineer|reviewer|qa|generalist`.
- Workspace optional: tasks may be Goal-level (no workspace) when work isn't repo-specific.
- Workspace must belong to same Goal.

### Session / context association

- One task may be associated with many sessions (multiple `sessions.task_id` rows). Convenience: `GET /v1/tasks/:id` includes a `sessionIds[]` field via index.
- One task may be referenced by many context packages similarly.
- Association is **non-exclusive and non-blocking**. Two sessions associating with the same task is *not* an error — but it triggers conservative conflict detection (workspace overlap).

### Relationship to M3 refinement

- The `goal.refinement.applied` event triggers initial generator run when the Goal has zero tasks.
- Generator reads success criteria as the candidate source of tasks: each well-formed success criterion produces at most one task. Bullet/list parsing is conservative — if the success criteria field is free prose, the generator returns one task scoped to "fulfill objective".

### Relationship to M5 memory/decisions/summaries

- Memory items of type `blocker` linked to a task auto-move task to recommendation `update_plan` (status `blocked`); user accept moves the task.
- Decisions of type `architecture_note` create source refs on tasks but never modify task status.
- Session summaries linking to a task contribute to `mark_complete` and `run_validation` recommendations.

### Relationship to M6 context packages

- A task's source list may include the `context_package` that the session ran with — captured by `context_packages.task_id`.
- The reverse, "this context package was prepared for this task", lets recommendations surface "continue task X" with the existing context package id pre-selected.

### Source attribution behavior

- Generated tasks list every source ref that contributed deterministically (the refinement row, plus any memory/decision IDs the rule consulted).
- Manual tasks have empty source list unless the user attaches one via PATCH.
- Source refs are id-only; UI resolves to titles by calling existing M3/M5/M6 endpoints.

### Acceptance criteria + validation steps

- Plain text arrays, capped 20 items × 256 chars each.
- No execution wiring. The `kind` field is a hint for `run_validation` recommendations to choose a role.

### Generation behavior

The deterministic task generator:
1. Reads latest refinement + attached workspaces.
2. Parses success criteria into discrete items (split on newline, semicolon, "and then"; max 20 candidates).
3. For each candidate: derive `title` (first 80 chars), `description` (full item), `role` (table-driven keyword classifier), `workspaceId` (single attached workspace if exactly one).
4. Compute fingerprint; drop if a non-terminal task with same fingerprint exists.
5. Emit batch.

Edge cases: empty refinement → generator returns empty list + sparse warning + emits a `refine_goal` recommendation via the separate recommendation generator (not here).

### Manual create/edit

Existing CRUD with field caps. No real-time collaboration. PATCH is last-write-wins.

### Blocked / resolved

- `blocked` status carries a `reason` field via the latest source ref or memory link; UI resolves it for display.
- `resolved` is not a status; the equivalent is moving back to `in_progress` or `done` with a feedback note.

### Archive / retention

- `archived_at` set when status moves to `archived`. List endpoints exclude archived by default; `?includeArchived=true` opt-in.
- Archived Goals hide tasks at the read layer but keep rows.

### Behavior for archived dependencies

If a task references an archived row (workspace, parent task, source memory/decision/summary/context package): read returns the ref with `archived=true`; writes that target archived ids fail validation (`409 archived_target`).

### Privacy

- Titles/descriptions are user-authored or generator-derived from refinement text already entered by the user; no transcript/output capture.
- Acceptance criteria/validation steps are user-editable text; same posture.
- Source refs never embed source body.

### Non-goals in M7

- No workflow graphs (DAG visualization, autonomy graphs).
- No autonomous execution plan layering.
- No cross-Goal tasking.
- No external PM sync (Jira, Linear, GitHub Issues).
- No multi-agent scheduling.

## 11. Recommendation Provider / Job Design

### Interface

```ts
interface RecommendationProvider {
  readonly id: string;
  readonly version: string;
  generate(input: RecommendationInput): Promise<RecommendationProviderOutput>;
}

interface RecommendationProviderOutput {
  candidates: RecommendationCandidate[];
  warnings: string[];
  sparse: boolean;
}

interface RecommendationCandidate {
  type: RecommendationType;
  title: string;                          // ≤ 256
  rationale: string;                      // ≤ 4 KiB
  proposedAction: ProposedAction;
  confidence: number;                     // [0,1]
  sources: RecommendationSourceRef[];     // ≤ 32
  relatedTaskId?: string;
  relatedSessionId?: string;
  relatedContextPackageId?: string;
  relatedConflictId?: string;
}
```

One production implementation in M7: `DeterministicRecommendationProvider`. One fake for tests.

### Input data

See Section 5. Bounded snapshot, ids and small fields only. Optional body inclusion is rule-scoped, length-capped, and never persisted in events or logs.

### Deterministic default behavior — per type

Each rule is a pure function `(RecommendationInput) → RecommendationCandidate[]`. Provider concatenates results, applies dedup, returns.

#### `refine_goal`
- Fires when refinement is missing required fields, or when memory contains ≥ 1 `open_question` item with no resolution.
- Confidence: 0.9 (missing refinement) | 0.6 (open questions).

#### `create_session`
- Fires when ≥ 1 task in status `open` has no associated session for its workspace.
- Proposed adapter defaults: shell/manual (most conservative); upgrade to claude-code only if a previous session for the same workspace used it (signal from M4 session history).
- Includes `contextRequest` referencing the task's role/workspace/objective; or `contextPackageId` if an existing fresh package matches.
- Confidence: 0.7 default; 0.85 when task explicitly proposes work to do next.

#### `continue_session`
- Fires when a session in status `running` or `paused` is associated with an `in_progress` task and the latest `session_summary` does not indicate completion.
- Confidence: 0.75.

#### `review_output`
- Fires when an engineer-role session reaches `completed` with implementation evidence in its summary and no reviewer session has been created since.
- Suggests reviewer-role session for the same workspace + task.
- Confidence: 0.8.

#### `split_task`
- Fires when a task's description exceeds a length threshold (deterministic: > 4 KiB OR ≥ 4 success criteria) and no children exist.
- Confidence: 0.55 (conservative; user typically knows when to split).

#### `run_validation`
- Fires after engineer-role `session.completed` with implementation evidence (validation rule below).
- Confidence: 0.85.

#### `resolve_conflict`
- Auto-created whenever a `conflict.detected` event fires.
- Confidence: 1.0 (the conflict exists deterministically).

#### `update_plan`
- Fires when a decision is `confirmed` after a task was created; or when a memory `blocker` is linked.
- Suggests changing task status, adding acceptance criteria, or noting a blocker.
- Confidence: 0.6.

#### `ask_user`
- Fires on `decision.confirmation_required`.
- Confidence: 0.95.

#### `mark_complete`
- Fires when all of a task's acceptance criteria have been mentioned in a session summary AND a reviewer session has completed without negative outcome.
- Confidence: 0.6 (always low; user confirms).

#### `pause_work`
- Fires when ≥ 2 active conflicts target the same task.
- Confidence: 0.7.

### Output schema

See `RecommendationCandidate` above. Validation:
- `proposedAction` discriminator matches `type` (e.g., `type='create_session'` ↔ `proposedAction.kind='create_session'`).
- All referenced ids exist and belong to the Goal.
- Confidence in `[0,1]`.
- Title, rationale, action sizes respect caps.

### Source selection

For each candidate, the rule emits source refs deterministically:
- `update_plan` from a decision: source = `[{ type:'decision', id, reason:'driver' }, { type:'task', id, reason:'subject' }]`.
- `run_validation` after a session: source = `[{ type:'session', id, reason:'completed' }, { type:'session_summary', id, reason:'implementation_evidence' }]`.
- General: every input row directly read by the rule appears as a source ref with a deterministic reason string from a small enum.

### Source attribution

Stored compact on `recommendations.sources_json`. UI resolves to titles via existing endpoints.

### Duplicate + stale handling

- Within a generation: candidates with identical `recommendation_fingerprint` (`goalId + type + canonicalProposedAction`) collapse to one.
- Across generations: matching active `proposed` rows are marked `superseded` and replaced by the new row.
- Stale: when a referenced source is archived between generations, the matching `proposed` row is auto-marked `superseded` with `reason='source_archived'`.

### Confidence behavior

- Used for UI sort (desc) and visual badge (low/medium/high based on three buckets: `< 0.5`, `< 0.8`, `≥ 0.8`).
- Not used for auto-action thresholds in M7. Confidence is metadata only.

### Feedback handling

- Accept/reject/dismiss are terminal and one-shot per recommendation (DB-enforced).
- Modify is non-terminal; the row becomes `modified` and `source='user_modified'`; previous payload snapshot recorded in `recommendation_feedback.modified_payload_json`.
- Subsequent generation runs do not regenerate a fingerprint that matches a `modified` row (modified rows count as "addressed").

### Confirmation-required decisions

The provider always emits an `ask_user` recommendation for each open `decision.confirmation_required` row. M6 already pins these in context; M7 makes them actionable suggestions.

### Validation rules (implementation evidence)

Deterministic check on a session summary:
- `outcome='completed'`
- AND summary mentions test/build/lint/diff/commit keywords (small token set) OR memory items of type `validation_result` exist for the same session.
- This is a string check on M5's already-curated summary fields, not on raw transcript.

### Review rules

Triggered when an engineer-role session completes with implementation evidence and no reviewer session for the same workspace + task has completed in the same generation window.

### Task-update rules

Triggered when a confirmed decision references a task indirectly (memory linking) or when a memory `blocker` references a task.

### Error handling + retry

Failure modes for the deterministic provider:
- `invalid_input`: input schema rejects (should not happen with the input builder; defensive).
- `invalid_output`: provider returned malformed candidates (bug).
- `sparse_input`: too little data to recommend anything; not an error — returns empty list with `sparse=true`.
- `internal_error`: caught exception with capped, redacted message.

Retry: failed generation rows are terminal; retry is a fresh POST. No backoff.

### Budgets

- ≤ 10 candidates per generation. Excess dropped with a generation warning.
- Per-candidate field caps as above.
- Input snapshot caps as in Section 5.

### Privacy

- Provider input may contain memory/decision/summary bodies (capped); provider output may not include any source body — only deterministic strings the rule constructs from typed fields.
- Logs from the provider stay at INFO level: ids and counts only. Stack traces in `failure_message` are capped to 256 chars and pass through the M5 redaction helper.

### Plugin-first preservation

- The `RecommendationProvider` interface is the seam external providers will implement.
- The internal skill descriptor `orca/recommendation-generation` is registered at boot with `invocation: 'daemon-internal'`. No public invocation route in M7.
- Switching to an AI-backed provider is a `DaemonContext` change + a new internal package, with no contract or UI ripple.

## 12. Conflict Detection Design

### Model

```ts
interface Conflict {
  id: string;
  goalId: string;
  conflictType: ConflictType;
  severity: 'info' | 'warning' | 'blocker';
  status: 'open' | 'resolved' | 'dismissed';
  title: string;                      // deterministic string from rule
  description: string;                // deterministic, capped 1 KiB
  sources: ConflictSourceRef[];       // every contributing row id
  fingerprint: string;
  resolutionNote: string | null;
  detectedAt: string;
  resolvedAt: string | null;
}

type ConflictType =
  | 'workspace_overlap'
  | 'contradictory_decisions'
  | 'reviewer_rejection'
  | 'blocker_reported'
  | 'unresolved_question';

interface ConflictSourceRef {
  type: 'session' | 'workspace' | 'task' | 'decision' | 'memory_item' | 'session_summary';
  id: string;
  role?: 'subject_a' | 'subject_b' | 'context';
}
```

### Lifecycle

```text
open
  -> resolved   (user moves with optional note)
  -> dismissed  (user dismisses; no resolution claimed)
```

No automatic resolution. Reopening requires deleting (out of scope) or detecting a new fingerprint; the same underlying state with the same fingerprint produces no new `open` row while the existing row is `open`.

### Detector rules

Each detector is a pure function over a Goal snapshot. The orchestrator invokes detectors after relevant trigger events.

1. **`workspace_overlap`**
   - Input: sessions with `status='running'`.
   - Predicate: two sessions share `workspace_id`; severity `warning` if both have distinct tasks, `blocker` if both target the same task.
   - Sources: both sessions, the workspace, the task(s).

2. **`contradictory_decisions`**
   - Input: confirmed decisions on the Goal.
   - Predicate: deterministic title overlap > threshold (Jaccard on whitespace-tokenized titles, no stopwords) AND body strings differ by at least one negation token (`not`, `no`, `never`, `should not`, `must not`) in canonical positions.
   - Severity: `warning`.
   - Sources: both decisions.
   - Conservative — false positives accepted; user dismisses.

3. **`reviewer_rejection`**
   - Input: latest session summary for a reviewer-role completed session.
   - Predicate: summary `outcome='rejected'` (M5 field).
   - Severity: `warning`.
   - Sources: session, summary, target task if associated.

4. **`blocker_reported`**
   - Input: memory items of type `blocker` not in archived/resolved status.
   - Predicate: presence.
   - Severity: `warning` (`blocker` if linked to an `in_progress` task).
   - Sources: memory item, linked task.

5. **`unresolved_question`**
   - Input: memory items of type `open_question`, not archived.
   - Predicate: linked to a task in `in_progress` OR linked to a `decision.confirmation_required` row.
   - Severity: `info` (rare blocker).
   - Sources: memory item, task or decision.

### Source attribution

Each conflict row records every source id used to detect it. Resolution is human-only, so the source list is the audit record.

### False-positive handling

- Dismiss is a first-class lifecycle state — not a deletion.
- Detectors do not re-create a conflict for the same fingerprint until the underlying source state changes (the fingerprint includes sorted source ids and conflict type).
- Dismissed conflicts with the same fingerprint as a future incident reset to `open` only if at least one source row changed since the dismissal — a deterministic check via timestamps.

### Human resolution

`POST /v1/conflicts/:id/resolve` with `{ resolution: 'resolved' | 'dismissed', note: string? }`. Sets terminal status, emits the event, and the linked `resolve_conflict` recommendation auto-dismisses.

### Relationship to recommendations

Every `conflict.detected` event emits one `resolve_conflict` recommendation in the same TX. Resolving the conflict moves the recommendation to `dismissed` automatically (this is an exception to the "no automatic status changes" rule; justified because the conflict resolution is the explicit user action being mirrored). Documented carefully in code with a single-purpose helper, not a general "auto-dismiss" framework.

### Payload limits

Event payload (see Section 7) is content-free. Conflict description is rule-generated and capped 1 KiB on the row, but never embedded in the event.

### Why semantic / AI detection deferred

- Semantic similarity for contradictory decisions requires embeddings, model calls, or trained classifiers — none of which are in scope.
- Deterministic rules can be wrong, but they are testable, fast, and reviewable.
- If the deterministic ruleset misses cases the user notices, manual conflict creation can be added in a future milestone via `POST /v1/goals/:goalId/conflicts`. **Not in M7.**

## 13. Adapter, Session, and Context Integration

### Accepted `create_session` recommendations

Accept response includes:
```json
{
  "proposedAction": {
    "kind": "create_session",
    "adapterId": "claude-code",
    "workspaceId": "ws_...",
    "role": "engineer",
    "objective": "...",
    "contextPackageId": "ctx_..."
  }
}
```

Desktop opens the existing M4 new-session flow with all fields prefilled. The user reviews, optionally edits, then submits `POST /v1/sessions { ..., taskId, fromRecommendationId }`. M4 PTY behavior is unchanged.

If `contextPackageId` is absent and `proposedAction.contextRequest` exists, desktop opens M6 context preparation first (prefilled), then session creation. Two-step flow remains explicit.

### Accepted `continue_session` recommendations

`proposedAction.kind='continue_session'` carries `sessionId`. Desktop navigates to the existing session detail / terminal view. No new launch path; existing M4 reconciliation handles paused/restartable sessions. No M4 PTY change.

### `run_validation` recommendations

Treated identically to `create_session` from a wiring standpoint — they propose a *new* session (typically reviewer/qa role) tied to the same task. **No automatic command execution.** The recommendation may suggest `"objective": "run pnpm test in apps/daemon"` but the user starts the session manually.

### Reference vs. request for context packages

Each `create_session`-shaped recommendation chooses between two pathways:
- **Reference an existing package**: `contextPackageId` populated. Used when a fresh package already exists matching `(adapter, workspace, role, objective)` fingerprint for the Goal.
- **Request a fresh package**: `contextRequest: { adapterId, workspaceId, role, objective }` populated. Used otherwise. UI submits this to M6 first; the resulting package id is then included in the session creation request.

The decision is deterministic and made at recommendation generation time.

### Session creation stores associations

`POST /v1/sessions` extension:
- `taskId`: stored in `sessions.task_id`; included in `session.created`; surfaces as `task.associated_with_session` event in the same TX.
- `fromRecommendationId`: stored in `sessions.from_recommendation_id`; included in `session.created`.

Validation prevents Goal mismatches.

### Session restart reconciliation

Existing M4 reconciliation reads `sessions` rows and is unaffected by the new columns. The reconciler does not re-derive `task_id` or `from_recommendation_id`; they remain pinned to the original associations.

### M4 PTY behavior

Unchanged. PTY streaming, input, resize, output tails, restart reconciliation: same code, same events. The only diff: `session.created` payload carries two new optional fields when present.

### M6 context preparation behavior

Unchanged. `POST /v1/goals/:goalId/context-packages` accepts new optional `taskId`, `fromRecommendationId`; the package's source list does not include the task or recommendation (the link goes on the package row, not into sources). Adapter delivery rules unchanged.

### Pre-fill explicit, not generic

There is no generic "execute action" endpoint. Each `proposedAction.kind` has a documented destination endpoint and a documented field map. UI implements the map per kind. Three kinds (`create_session`, `continue_session`, `run_validation`) prefill the M4 flow; one (`refine_goal`) prefills the M3 flow; one (`update_plan`) prefills the M7 task PATCH dialog; two (`split_task`, `mark_complete`) invoke M7 task endpoints directly when the user clicks accept; `resolve_conflict` opens the M7 conflict resolve dialog; `ask_user` opens the existing M5 decision-confirmation flow; `pause_work` is a no-op accept that records the signal.

This explicit map is verbose but keeps M7 honest about what each acceptance actually means and avoids a generic action executor.

### Recommendations panel

- Header: title, "Regenerate" button, generation banner.
- Body: three sections — `Active`, `Modified`, `History (recent)`. Default to Active visible, Modified and History collapsible.
- Card per recommendation:
  - Title (one line)
  - Type badge (color-coded)
  - Confidence badge (low/med/high)
  - Rationale (truncated, click-to-expand)
  - Proposed action summary (rendered per `kind`; one line)
  - Source list summary ("3 memory · 1 decision · 1 summary"; click opens detail drawer)
  - Action buttons: Accept (primary), Reject, Dismiss, Modify (overflow menu also keeps these).
- Detail drawer: full rationale, proposed action JSON in a collapsed code block, source list with type/id/title (titles resolved via existing endpoints).
- Modify dialog: title, rationale, proposed action editor (kind picker + per-kind form).
- Empty: hint + manual Regenerate CTA.

### Conflicts banner

- Visible only when ≥ 1 `open` conflict exists.
- One-liner: "N conflicts need review" → opens drawer.
- Drawer: per-conflict row with type/severity/description/sources; `Resolve` and `Dismiss` buttons.

### Validation recommendation display

A `run_validation` recommendation card renders the proposed reviewer/qa session details. Accept button prefills M4 new-session flow with the role set to `reviewer` or `qa` and the task pre-associated.

### Live event refresh

WebSocket subscription extends the existing event handler:
- `task.*` → refetch `/v1/goals/:goalId/tasks`.
- `recommendation.*` → refetch `/v1/goals/:goalId/recommendations`.
- `conflict.*` → refetch `/v1/goals/:goalId/conflicts`.
- `user.feedback.recorded` → refetch the affected recommendation only.

Refetch is debounced (200 ms) to handle batch generation broadcasts.

### Sparse / empty / failure states

- Empty memory/decisions/summaries → recommendations panel shows "Add session activity to receive suggestions" message + Regenerate.
- Failed generation → banner shows failure code (mapped to a friendly string) + Retry.
- Provider not responding → 30 s client-side timeout on the POST, but the row remains in `running` server-side until completion or boot reconciliation.

### Existing M4 / M5 / M6 surfaces

- M4 terminal: unchanged. Session detail gets two small badges (task title, "from recommendation" link).
- M5 memory/decisions panels: unchanged. Existing accept/edit/promote flows untouched.
- M6 context preview / status: unchanged. Session badge augmented with `taskId` link when present.

### Reject in UI

- No global recommendation dashboard.
- No workflow builder.
- No autonomy controls.
- No provider/model settings.
- No analytics dashboards.
- No prompt editors.
- No cross-Goal recommendations view.
- No drag-and-drop task graph.

### Token efficiency in the UI

- Each panel paginates (default limit 50) so opening Goal detail loads a bounded slice.
- Detail drawers lazy-load source ref titles only when expanded.
- Confidence/status counts are computed server-side and returned as metadata to avoid full-list re-renders.

## 16. Validation Strategy

### Baseline regression safety (M1–M6)

- M7-000 records baseline SHA + test summary.
- Every task touching M4/M5/M6 surfaces (M7-016, M7-017, M7-018) re-runs the matching regression anchor.
- Full-suite gates at M7-010 and M7-024.

### Daemon startup after migration

- Migration test runs on fresh DB and on a recorded M6 fixture DB.
- Boot reconciliation test inserts pending generation rows pre-shutdown and asserts post-boot state.

### Contract parsing

- `@orca/contracts` parse/reject tests cover every event type, every `ProposedAction.kind`, every status enum, every source-ref type.
- Negative tests: empty title, oversized rationale, malformed `proposedAction`, foreign-Goal source ref.

### Migration from existing DBs

- M6 fixture DB migrated to M7: M7 list endpoints return empty; session/context rows have null new columns.
- No data backfill required.

### Task generation correctness

- Snapshot tests over fixture refinements (Section M7-007).
- Fingerprint dedup test prevents duplicate generated tasks on regeneration.

### Recommendation generation correctness

- Per-type rule tests (Section M7-008): fire conditions, no-fire conditions, output schema, source attribution.
- Full-input snapshot tests for one rich Goal fixture exercising multiple rules at once.

### Validation recommendation after implementation-like activity

- Fixture session summary with `outcome='completed'` + implementation-evidence flag → assert `run_validation` recommendation appears.
- Fixture session summary without evidence → assert no `run_validation` recommendation.

### Conservative conflict detection

- One fixture per conflict type.
- A no-conflict baseline asserts zero detections.
- A double-fingerprint test asserts no duplicate `open` rows.

### Excludes raw terminal output and full transcripts

- Static check (lint or unit test) prevents `apps/daemon/src/orchestrator`, `apps/daemon/src/recommendations`, `apps/daemon/src/tasks`, `apps/daemon/src/conflicts` from importing `apps/daemon/src/sessions/output-store.ts`.
- Event-payload tests assert no event carries rendered context, raw memory text, prompts, model responses, transcript bytes, or rationale text bigger than 4 KiB.

### Idempotency and dedup

- Double-POST of `/recommendations/generate` with same input fingerprint within an active generation returns the existing row and emits no new events.
- Failed generation row not in active idempotency: retry creates a new row.

### Superseding stale recommendations

- Generate, then regenerate with mutated input: assert prior `proposed` rows move to `superseded`, new rows inserted, events emitted.

### Accept/reject/dismiss/modify persistence

- Repeated accept on same recommendation is idempotent at HTTP level (returns existing row, emits no new events).
- Modify creates a feedback row with snapshot; subsequent accept allowed.

### Proposed action validation without direct execution

- `proposedAction` discriminator mismatch with `type` rejected at provider output validation.
- HTTP accept never calls a downstream M4/M6 endpoint; integration test asserts no auto-launch.

### Event persistence and ordering

- Event log inspection in integration tests asserts ordering: generation requested → per-row events → generation completed.
- Conflict + linked recommendation share one TX (assert by checking event timestamps and absence of intermediate states).

### Projection correctness

- Each projection test inserts rows directly and asserts list/get behavior with archived filter, pagination, status filter.

### WebSocket/UI refresh behavior

- Mock WebSocket frames; assert refetch debounce and per-panel scope.

### Daemon restart for pending/running generations

- Restart test: kill daemon mid-running generation; reopen; assert row moved to failed/daemon_restart with matching event.

### Provider failure and retry

- Fake provider throws; assert generation row marked failed, failure event emitted, retry endpoint creates a new row.

### Secret/output logging safeguards

- Logger denylist test: provider failure with secret-shaped strings in the throw message produces a redacted `failure_message` row and no leaked log line.

### Desktop task / recommendation / conflict flow

- Component tests per state per panel.
- Smoke test: accept create_session recommendation → assert M4 new-session form is mounted with prefilled adapter/workspace/role/objective/contextPackageId.

### Deterministic-only test stance

- All M7 unit tests use the deterministic provider or the fake provider; no AI/model call in CI.

## 17. Risks and Simplifications

| Risk | Impact | Mitigation |
|---|---|---|
| Trigger map fires too often, generating noise | UI overwhelmed, DB growth | Trigger map is table-driven and tested; per-Goal single-flight + dirty-flag re-evaluation; recommendation panel sorts by confidence DESC |
| Trigger map fires too rarely, hides useful suggestions | Recommendations panel feels dead | M7-024 proof exercise covers each trigger; manual regenerate button visible |
| Deterministic rules produce false positives (especially `contradictory_decisions`) | User trust erosion | Conservative thresholds; first-class dismiss; per-fingerprint suppression; documented behavior |
| Deterministic rules miss obvious cases | Manual operation still required | Acceptable for MVP; defer AI-backed provider; manual recommendation creation deferred |
| AI provider risk | N/A | None added in M7 |
| Token/cost/latency | N/A | No provider calls |
| Recommendation quality (rationale clarity) | UX feels weak | Rules construct rationales from typed source fields with templated strings; tests snapshot |
| Stale recommendations after state change | Wrong suggestion accepted | Supersede on fingerprint match; refresh on relevant events; UI shows "stale" badge when source archived |
| Source attribution drift | Audit unclear | Every rule emits source refs with deterministic reason strings |
| Feedback signal misuse | Pretending to learn | M7 explicitly does not learn; signals are persisted only |
| Confirmation-required decision under-handled | Agents treat as settled | Always emit `ask_user` recommendation; high confidence; M6 already pins in context |
| Conflict false positives | User dismisses many | Conservative rules; dismiss is first-class |
| Conflict false negatives | Real issues missed | Acceptable for MVP; rule list is small and explicit; document scope |
| Adapter/session/context integration drift | M4/M6 regression | M4/M6 paths only get optional new fields; existing flows tested unchanged |
| SQLite migration risk | Lost data | Migration tests for fresh + M6 fixture DB; no destructive ops |
| Event-system payload growth | Log bloat | 4 KiB per-event cap; content-free rule; tests |
| Daemon restart recovery | Stuck rows | Boot reconciliation pattern; tested |
| Privacy: recommendations leak memory text | User trust | Rationale strings constructed from typed fields, not raw bodies; redaction helper on `failure_message`; no raw input/output persisted |
| Logs accidentally contain raw text | User trust | Logger denylist + tests |
| Database growth | Local DB bloat | Hard caps per field; no auto-retention in M7; documented as future work |
| UI live-refresh storms | Sluggish UI | Debounce + scoped refetch |
| Recommendation generation single-flight too restrictive | Slow feedback | Acceptable for MVP; runner re-evaluates after completion if dirty |
| M1/M2/M3/M4/M5/M6 regression | Trust loss | Regression anchors run at every milestone gate |
| Overengineering | Velocity loss | Section 2 deferrals + Section 4 "no new package" rule + no DI framework |

### Intentionally deferred

- AI-backed recommendation provider.
- Recommendation aging/decay/scoring/analytics.
- Workflow execution / approval gates / autonomy controls.
- Cross-Goal recommendations / memory / search.
- Embedding/vector/knowledge graph systems.
- Provider/model configuration UI, prompt templates, prompt experiments.
- Workspace indexing / file watching.
- Background queues / workers / schedulers.
- Recommendation history / diff / editor views.
- Multi-agent scheduling.
- Manual conflict creation endpoint.
- External PM integrations.

### Future safety preserved

- Tasks, recommendations, conflicts, feedback persist with stable schemas Level 4 can read directly.
- `RecommendationProvider` interface lets an AI-backed provider replace the default.
- `ProposedAction` discriminated union is the contract Level 4 will gate.
- `recommendation.accepted` is the explicit hand-off signal.
- `recommendation_feedback` rows are the supervision substrate for future learning.
- Internal skill descriptors register the boundary an external plugin will fill later.

## 18. Definition of Done

Milestone 7 is complete when **all** of the following are true:

1. Goal-scoped work units exist as a durable domain. Users can:
   - generate tasks from refinement (`POST /v1/goals/:goalId/tasks/generate`),
   - create tasks manually,
   - edit, split, status-change, associate-session, and archive tasks,
