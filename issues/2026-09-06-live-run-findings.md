# Findings — live run after the dogfood fixes (2026-09-06)

Goal: "Add a Rankine conversion to the temperature module" on Orca Scratch, Adaptive
Delivery, supervised, driven through the browser build. Found while verifying H1
(PostToolUse) and A2 part 2 (park-time notification) on a real worker. **Status:
`open` unless stated.** Rows are removed once fixed and verified.

| # | Issue | Status | Notes |
|---|---|---|---|
| R1 | **"Wait for Claude Code" waits for nothing.** Choosing Wait preserves the session and shows the reset time, but when the reset passes the run stays parked until a human clicks Retry. The card's copy ("will be preserved while waiting") reads as "Orca will continue"; it does not. Observed: reset 1:50am, still parked at 1:52am with Retry enabled and no retry attempted. | **FIXED** — Wait arms a retry 30s after `resetAt`, the same action the button takes; a human Retry disarms it; checkpoints still `waiting` are re-armed at boot. Awaiting a live occurrence to verify. |
| R2 | **A retry in progress is invisible.** While the recovery card is parked (`paused_for_input`), every live signal from the resumed worker is swallowed (`openOrUpdateLive` returns the paused row unchanged), and the card reads "Retrying Claude Code…" for the whole turn. The daemon knew the worker was working — output_seq moved 201→267 — and the chat showed nothing. This is what "the UI isn't changing" looked like from the reader's seat. | Downstream of R3/R4 | With R4 the false park never happens; with R3 a real retry is recognised on its first output chunk and the card resumes. Verify on the next real limit. |
| R3 | **The Claude turn-start detector never matches a live pane.** It accepts the legacy "esc to interrupt" and a spinner line, but anchors the spinner on a newline and requires a space after the glyph. A live pane arrives as carriage-return-separated redraws with the glyph glued to the gerund (`\r✻Musing…3\r`), which the captured pane showed 60 times and the detector matched zero times. So a preserved-session retry can never be recognised as started: the checkpoint stays `retrying`, the recovery activity never resumes, and the chat freezes on "Retrying…". The shadow session's submit-confirm loop shares the detector. | **FIXED** — anchors on `\r` or `\n`, space optional; tested against the captured redraw. |
| R4 | **The usage WARNING was taken for a limit hit.** Claude Code prints "You've used 91% of your session limit · resets 1:50am · /upgrade…" while the agent keeps working. The limit regex's loose branch (`session limit … resets`) matched it, so the daemon parked the Proposal step on provider recovery at 06:32:29 under a worker that went on to finish its turn and ask the user a question at 06:33:25. The false recovery card sat under the real question card for twenty minutes, the goal chip named the wrong thing ("a provider limit it needs you to resolve"), and "Retry" nudged a worker that had only been waiting for an answer. Root of "the UI isn't changing". | **FIXED** — the warning is stripped before the limit test; a real hit beside it still counts. Tested with the captured line. |
| R5 | **An answer sent during a retry is never delivered.** With the checkpoint in `retrying` (the nudge already sent, the worker live at its prompt), a user message — here the answer to the worker's own question — is stashed as guidance "to be sent when the provider is retried". That retry had already happened, and stashed guidance is only replayed on turn-start detection, which an idle worker never produces. The worker waited for the answer; the answer waited for the worker. | **FIXED** — during a preserved-session retry the message is delivered to the worker directly; stashing is the fallback when delivery fails. |
| R6 | **The daemon test suite kills every live worker on the machine.** `generation/reconcile.test.ts` boots `startDaemon()` in-process against a temp data dir; a real boot runs the orphan reaper, and with an empty database every `orca-worker-*` and `orca-shadow-*` on the shared tmux server looks orphaned to it. Proven live: two workers on two goals died in the same watchdog tick during a suite run, their respawns died in the next, and both runs blocked at the crash cap — each death recorded as the agent crashing. Every agent runs the suite after every edit, which is why worker deaths on Sep 1–3 clustered around restarts (D6's real mechanism; the respawn-of-finished-steps fix was a second, separate defect). Bisected with canary sessions to the one file. | **FIXED** — every worker and shadow session is created with an owner tag (its data dir, in the tmux session environment) and the reaper may only kill sessions carrying its own tag; foreign and untagged sessions are left and counted. Canaries survive the killer test; the real workers spawned from now on are tagged. |
