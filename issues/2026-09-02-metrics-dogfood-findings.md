## C+. Executable axis — the harness over-crediting itself

| # | Issue | Status |
|---|---|---|
| E1 | **The sensor ladder counted a no-op stub script as a passing deterministic sensor.** `"typecheck": "echo no types"` exits 0, so the runner recorded `passed` — while the *agent* correctly classified it `skipped` ("it exercises no type checker, so it provides no signal"). This inverts the Executable axis: the deterministic oracle the self-report is meant to be checked against became the softer of the two. It fed `oracleAdequacy.sufficient`, the verification tier, and `composedScore` at `executable` weight **1.0** — the strongest tier in the ladder — for a command that did nothing. Widespread rather than exotic, since the catalog encourages declaring these scripts. | **FIXED** `d5e1f5c` |
| E2 | **The independent-check line contradicted the sensor list directly above it** — "a second AI reviewed it and agreed *but nothing was run or tested*" on a step where `npm test` ran and 5 tests passed. The clause was baked into the verdict label instead of reading `evidence.executed`. Mirror image of E1: E1 oversells a stub, E2 undersells real execution. | **FIXED** `d5e1f5c` |

**The invariant E1 establishes:** *a sensor's exit code is evidence about the command that ran; it is evidence about the artifact only if the command actually exercises the artifact.* Detection is deliberately narrow and provable — it reads the script **body** (which the detector already had and discarded) and asks whether any segment can fail. `echo x && node --test` is not a stub. Perfect detection is impossible (`tsc --version` exercises nothing either), so it catches the provable case and claims nothing about the rest. The asymmetry sets the bias: wrongly crediting a stub over-claims at the highest confidence in the ladder; wrongly skipping a real check only under-claims and is recoverable.

## E. Process hazards (recurring, worth guarding)

- **A label travels further than its evidence.** Six instances: an illustration hardening into copy; the lead's cost reasoning; "confirmation cards" for a set containing a `tool_use`; "a permission request" for a stomped field; a constant (`SAMPLE_MIN`) used to conclude a code path was dead without reading it; a SHA cited for content it didn't contain.
  → **Guard: trace every label to the field that produces it before it ships.**
- **An enum value read but never written is a predicate that lies to its readers**, and it lies in the safe-looking direction. `'starting'`: read in 17–20 places, written in none.
  → **Guard: a test driving off the contract's own enum options.** Landed in `ca56037`.
- **In a shared worktree, file content answers "what is someone working on", never "what is committed."** Three agents hit this on one file inside an hour.
  → **Guard: `git show --stat <sha>` before citing a commit; check if the file is dirty before claiming what the running daemon does.**
- **`git add` and `git commit` are not atomic across agents.** Two commits landed under another agent's message.
  → **Guard, corrected: `git add <paths> && git commit --only <paths>` prevents sweeping *other* files. It does NOT prevent committing a teammate's concurrent edits to a file YOU are committing.** Add `git diff --stat <paths>` before committing and confirm the line counts match what you actually wrote — a file with more churn than you produced is someone else's work in your commit. The lead broadcast the incomplete version as settled practice; the second incident happened in the gap. "no changes added to commit" is an alarm, not a no-op.
- **A temporary allowlist is acceptable only if it FAILS when it becomes stale, rather than merely permitting.** The opacity guard shipped with an exact-match baseline of two known uses; when one was removed the assertion failed and forced the list to shrink, so the baseline existed exactly long enough to keep four agents' suite green and then dissolved within the hour. The version that rots uses `>=`.
- **An API that taxes the safe path will get the unsafe one.** `deltaAllowed` needs an n per side, and the rate functions returned a bare ratio — so a caller doing the guarded comparison had to invent a denominator, while skipping the guard was free.
- **A mechanism travels further than its evidence, the same way a label does.** The lead saw a daemon restart at 04:42:54 and a stall at 04:47 and connected them; one continuous pid spanned both. Read "UI still spinning" as "verdict never delivered" without looking for the delivery — the hook had fired 3ms before `finished_at`. Called `finished_at`-with-`status=active` a partial completion when it is the correct terminal-step shape, and would have "fixed" a non-bug.
  → **Guard: a plausible cause already in hand is the moment to keep looking, not to stop.**
- **State tells you what is; the append-only event stream tells you what didn't happen.** The mutable row said `independent_check` with no history and could never have shown that a clear was *missing* rather than *late*. Only the `phase_changed` sequence — and its missing `reviewing` — cracked it.
- **A claim true of one thing travels to the thing next to it, and hardens through retelling.** The lead took the `captured-but-discarded` framing — accurate about *gate cost* — attached it to the *accumulator leak*, and repeated the fused version three times, including to the founder. The vector was a lead paraphrasing between two specialists, which is precisely what peer-to-peer working is meant to reduce.
  → **Guard: when relaying a specialist's claim, relay which artifact it was about, not just the claim.**
- **A mutable row's `updated_at` is not evidence of progress.** A row touched by a retry loop is indistinguishable from a row doing work. On the stuck run, `activities.updated_at` and `activity.changed` both read *minutes ago* while every source that tracks real advancement read *39 hours ago* — so the obvious source for "last activity", the column literally named for it, would have inverted the design meant to surface the stall. Second timestamp on this project whose name promises more than it delivers (`sessions.exited_at` is the watchdog's stamp, not the death).
  → **Guard: ask what the number would SAY on real data before approving the surface that displays it.** Three findings tonight came from computing the value rather than reasoning about the field.
- **Confirming evidence is the kind nobody audits.** The lead applied the guard above to a design, found a 47-minute gap, and reported it as confirming a predicted instrument artifact — without establishing which side of a step boundary the gap sat on. The conclusion survived the check, but it was reported as settled on evidence that could not support it. A duration whose *bracketing* was unchecked, which is the scope error in a new register. It was caught by the reviewer, not by the author.
  → **Guard: audit the result that agrees with you at least as hard as the one that doesn't.**
- **A measurement cannot answer a question about appearance, and running it anyway is a way of avoiding the person who can.** The body-size change (14px → 13px app-wide) would audit clean either way, because 13 is a scale step; that was never the question. The lead gathered numbers across four screens before recognising the question belonged to the founder, who had the app open in front of him. **When the only instrument is a human eye, go and get one.**
- **A status is not an event.** Having been corrected once on this gap, the lead then claimed "the agent was working" from `status = expired` — a value with **two producers**, one a real turn boundary and one a sweep finalising records whose turn signal never fired. `expired` means "working" under neither. Fourth signal in one session whose meaning was assumed rather than established (`sessions.exited_at`, `activities.updated_at`, `'starting'`, and now this). The pattern holds because one reviewer reads the code and the other reads the data; neither catches these alone.
  → **Guard: before a status becomes evidence, find every site that writes it.**
- **PROTOCOL, adopted:** *a mechanism inferred from data is a claim until its writers are checked — whoever proposes it. Say which it is when you send it.* Symmetric by design. The rejected alternative was to mark one agent's findings provisional by role, which fails because if everything from one source is pre-marked suspect, the marking does the thinking and the reviewer stops reading. Both the lead and the reviewer hit this class tonight; the asymmetry in who caught whom has a boring cause — **source has a mechanical oracle (grep every writer in ten seconds), data requires inference.** So the fix is reaching for the grep, not reasoning harder.
- **Name a field after its definition, not its concept — or the next implementer re-enters through the name.** The field was first specced as `lastActivityAt`, and "activity" is exactly what the misleading source (`activities.updated_at`) measures; the name was the trap's delivery mechanism. Renamed `lastProgressAt`. Generalised: **progress is defined by append-only state transitions, never by mutation timestamps.** A transition happened; a touch merely occurred.
- **A divergence between two clocks can be the only available discriminator.** `lastProgressAt` vs `lastSignalAt` looked like a data trap and turned out to separate *silent* (dead worker — both clocks old) from *spinning* (loop — progress old, signal recent). Nothing else in the system can see the second: the stall sensor only fires while Orca owes the next move, so a worker churning on its own looks alive to every existing check. Verified live on run `01a06587` — progress 39h stale, signal moving every few seconds.
- **When two stores disagree, check whether they are answering the same question before deciding which is stale.** A10 was reported (by the lead, to the founder) as a *contradiction* between `awaiting_user` and `activities`. It wasn't. They cover different halves: `activities` covers parks; the column covers chat replies (`paraphrase_agent_message`, `answer_user_directly`, `escalate_to_user` only call `postOrchestratorMessage` and raise no activity at all). Reading only the column missed a park for 39 hours; reading only the activity misses a chat reply. **Both are false negatives; only the union is correct.** A derivation that replaced the column with the activity shipped and was reverted (`f909fc3`) — caught by an existing test that the author was one step from rewriting as a stale assertion. The single-source endpoint is still right, but it requires giving the chat-reply case an activity, which is a change to the activity model rather than a read-side fix.
- **When two stores answer the *same* question, make it one thing — a test is a floor, not the fix.** A test asserting agreement can only cover paths someone enumerated, and these bugs are always a missing write on a path nobody enumerated (`setAwaitingUser` has one call site; at least four paths create a park without one). Six times tonight the answer was *make it one thing* — `liveSessionSql`, `INFRA_REASON_MARKERS`, `isGateSurrogate`, `workflowEvidenceRuns`, `silent`, and A10 — and the lead argued for a test on the sixth and was overruled with the mechanics. Three instances: the mark-done card (activities vs step-run row), A10 (`awaiting_user=0` while `paused_for_input`), and the rate denominators (per-step filtered, summary tiles not).
- **A ban recorded in a spec is not a ban applied to the code.** `opacity: 0.55` — the defect this project began with — was banned, logged as "banned by spec", and left rendering on the founder's screen in `MetricsPage.tsx:135` and `StepPerformance.tsx:142`. The new components' no-opacity test inspects only their own markup, so it could never reach the old ones.
  → **Guard: a rule needs a test with the same reach as the rule.**
- **The optimistic overstatement is the one nobody checks.** We removed pessimistic overstatements all session — six steps "underperforming", five that "never passed", `Triage 16/100` with an empty failure list — and caught every one because it was *insulting*. The same data yielded "your workflow has never had a workflow failure", which is true, and which the lead relayed enthusiastically. n=9, one template, one user, on a machine where 74% of recorded worker deaths were a daemon bug. Honest, and the impression outruns the evidence.
  → **Guard: a flattering claim on an inferred basis is the worst combination available — neither half prompts scrutiny.**
- **Provenance and scope are different axes and one flag cannot carry both.** `inferred` answers *how do we know* (verified code vs. matched substring). It does not answer *how much does this cover*. A claim can be perfectly verified and still overstated: "every step passed first try" is a **census** — exactly true of the nine observed, asserting nothing about the tenth — so the n-gates correctly do not block it, and the risk is that it *reads* as a property of the workflow when it is a property of nine steps.
  → **Guard: a prose claim carries its own scope the way a number carries its denominator.** Expose `{ steps, runs, templates, inferred }` alongside the claim so the copy layer *cannot* render it without the terms, rather than trusting whoever writes the sentence to remember. Same reason `parkState` is decided server-side.
- **The recurring shape, now four instances: a taxonomy written by hand in one place while the type or the writer says something else.** `'starting'` (read in 17 places, written nowhere), two `INFRA_REASON_MARKERS` lists, five copies of `startsWith("__gate__:")`, and a test helper's status union narrower than the type it constructs. Every one drifted silently; every one was fixed by making it one thing. The cheapest instance cost a red gate; the most expensive killed live workers.
- **Lead with the count, never a universal quantifier.** The overstatement in "not one step has ever failed" is not in the number, it is in the **grammar**: *never / zero / not one / every* are universals, and a universal implies a law. Nine observations support a count, not a law. "Every step passed" makes the workflow the subject; "all 9 steps passed" makes the sample the subject. Cheap to enforce in review because the offending words are a short list. **Placement carries as much as wording** — if the good half is a headline and the caveat is a footnote, the impression outruns the evidence however the first sentence is phrased.
- **Under-claiming is not the safe default; it is the other error.** Saying nothing about the four blocked steps defaults the reader to *"my workflow failed four times"* — the pessimistic contamination we spent two days removing. Where the cause is genuinely unknown, **say that it is unknown**, with the remedy named: *"4 stopped before finishing — we don't yet record why, so we can't tell you whether that was your workflow or Orca."* True today from recorded status alone, blocks the pessimistic default, and gets *better* when the field lands rather than being replaced. **A sentence that is true now and improves is the right migration shape for anything on this screen.**
- **The system knows more than it records; the recurring fix is to stop discarding what the write site already holds.** Three instances: gate cost (ingested into the accumulator, never drained), `sourceKind` (held at the pause, dropped from the event payload, then overwritten on the row before anyone could read it back), and `blocked_code` (`sess.failure_reason` interpolated into an English sentence and re-extracted downstream by matching that sentence). None needed new capture — only the removal of a discard.
  **This is a distinct family from the duplicate-taxonomy one and the two should not be conflated.** Duplicate taxonomy is *"a predicate that must be repeated will eventually be repeated wrong"* — cause: copying; fix: make it one thing. Discard is *"the system already knew and threw it away at the boundary"* — cause: a value not carried across a write; fix: carry it. Different cause, different fix, same symptom of a number that cannot be shown.
  Corollary that makes the discard family harder to spot: **once a value is dropped at the boundary, the downstream reconstruction looks like a reasonable feature rather than a workaround.** `classifyInfraReason` reads as a classifier; it is a repair for a discard three files upstream.
- **A rule derived correctly in one place and not carried to the neighbouring reader of the same source.** `lastProgressAt` counts status *changes* on the `activity.changed` stream — reasoned through deliberately, because a repeated status is one state continuing. `buildInterventions` reads the same stream and counted raw *events*, so one park that re-raised 57 times rendered as **"57 cards still open"** when there was one. Same file, same stream, opposite treatment, same author, hours apart. **A healthy run hides it entirely** — it parks once and resolves, so events and parks coincide; only the spinning run exposed it, which the two clocks had just made visible.
  This is NOT the duplicate-taxonomy family: the two genuinely compute different quantities, so "make it one thing" does not apply.
  → **Guard: when you establish how to read a stream, check every reader of that stream.**
- **The strongest form of a guarantee is a shape in which the bug cannot be expressed.** Three instances: `lastSignalAt` defined to include `lastProgressAt` so the pair cannot invert; `awaitingYou` needing no run-terminal clip because a park on a dead run is `abandoned` by construction and can never enter the set; `coverage.silent` falling to zero as a consequence of gates emitting. In each case the alternative was a check that catches the bug — which is strictly weaker, because a check can be removed and a shape cannot.
- **A success signal that isn't evidence — five members, all the same shape: the reporter never touched the layer it reports on.** vitest does not typecheck (contract changes went green on tests, red on `tsc`, three times). happy-dom never loads the stylesheet (an invisible title passed 864 tests). A hand-written mock is an unverified claim about a contract (`{workspaces: []}` mocked against a function returning a bare array — the suite cannot check a mock against the thing it stands in for). A source-literal conformance test cannot see a UA default (47 elements at the browser's button size, with nothing wrong in the source).
  The fifth is a tool rather than a test: **the Playwright screenshot call returns success and writes no file** — verified by searching the filesystem after every attempt across a whole session. Consequence: the lead had no visual evidence available at any point, so every "verified" on this screen meant *the numbers are right* and never *it looks right*. The founder found the styling defect the lead was structurally blind to.
  → **Guard: ask where the property actually resolves, and put the check there. When a tool reports success, confirm the artifact exists.** The lead's own instance: verifying this screen for hours via the accessibility tree, which carries text and structure and says nothing about appearance — every "verified" meant *the numbers are right*, never *it looks right*.
- **An edit to one clause is not an edit to the sentence.** Three duplicated sentences shipped today — the gate rows, the intervention rows, and the stops caveat, which opened by saying the reason record gets overwritten and closed by saying it again forty words later. Same mechanism each time: one end of a paragraph edited without rereading the other. **Distinct from the repetition-across-rows hazard, because the duplicate is invisible in the diff** — both halves read correctly in isolation and only the rendered whole shows it. Which makes it, like the Arial defect, a class only a screenshot catches.

Colour beat magnitude. - **A container bug can require sparse data to appear.** `MetricsPage.tsx:84` is a `display:grid` with `height:100%` and no `gridTemplateRows`; auto rows split the height between the view toggle and `RunLedger`. On a one-step run detail it is short, so the toggle inflates into a ~210px box. **Every screenshot taken all day was of the long run**, so the defect was invisible to the whole team — it needed the founder's own "little data" case to show itself. Sparse-data states need their own screenshot pass; they are not merely a copy problem.
- **Two quantities in one column are distinguished only by whichever wins the weight contest.** The stops list renders resolved parks (how long a pause *lasted*) and abandoned ones (how long ago a pause *started and never ended*) in the same column, same format, same weight — producing `94h 29m` inside a `19m` run. **The daemon is correct and says so explicitly**: `durationMs` is documented as "ACTUAL age — unclamped, live while open", and `runTerminalMs` as "a card's age is a property of the card." Neither number is wrong; the adjacency is. The qualifier that separates them (`left open when the run stopped`) is grey text losing to a bold number.
- **The screenshot tool writes a relative `filename` to the process CWD, not to the output directory** — so a capture named `runs-list.png` lands at the repo root while every previous capture sits in `.playwright-mcp/`. The tool is honest: its result says `./runs-list.png`. **I read that as "wrote nothing" and reported a silent-failure bug that does not exist**, because I checked the directory I expected rather than the path I was given. The real lesson is the smaller and more embarrassing one: *a tool result naming a path is evidence about that path and no other.* Use absolute paths so expectation and result cannot diverge, and when a file "isn't there", re-read the result before concluding the tool lied.
- **A layout fix can reveal a second layout bug the first was absorbing — and its siblings share it.** Fixing the inflated view toggle handed `RunLedger` the full height, which exposed `RunDetailPanel` spreading its rows across it (`align-content` defaults to `normal`, which behaves as `stretch`, so auto rows eat the slack): a 95px row holding a 20px button. The defect was real the whole time and unobservable because the bug above it was consuming the same space. **Verifying a layout change therefore means re-photographing the whole screen, not the element you changed, and checking the fix's siblings** — whatever was absorbing slack for one child was absorbing it for all of them. `RunLedger`'s list root had the identical shape and was saved only by usually being taller than its container.
- **The type scale, the contrast rules, and the layout are enforced by a human with a browser and by nothing else.** happy-dom does not do grid layout, so no assertion can catch `alignContent` regressing, a `gridTemplateRows` omission, or a 95px row holding 20px of button. **Three of the five worst defects found today were in that uncovered band** — the Arial rendering, the inflated toggle, and the stretched detail panel — and every one was found by looking at a rendered page. Writing a test that appears to cover this would be the most self-inflicted instance of the success-signals-that-aren't-evidence family. The real remedy is a rendered-page check in CI, and it is bigger than this screen.
- **A status report is a label, and it outruns its evidence the same way.** Twice today a teammate described a *screen* using the scope of their own *diff* — "no red anywhere on the runs list", after removing red from the status labels only; two `--err` borders on the lossy caveats were outside the change and outside the check. Measuring every computed colour in the panel found three warm elements where the claim said one. **Half the defects in this file are labels whose evidence covered less ground than the claim; a progress report is such a label**, and the standard we hold the product to is the standard the reports need. The corrected rule was also the stronger one: *no red in the rows; red reserved for a figure known to undercount; amber reserved for the one thing that wants the reader* — three meanings, each used once or twice, none competing.
- **Detoning is only survivable when magnitude already carries the hierarchy.** The worry about removing every alarm from a list is that it flattens it. It didn't, because alarm was never what sorted these rows — `$61.52` beside `$0.31` and `21h 0m` beside `6m 46s` do, and no figure was touched. **The order to do this in is therefore: make magnitude legible first, remove tone second.** Reversed, the same edit would have produced a genuinely flat screen.
- **A category loses its members at a boundary, and the flattening is invisible downstream by construction.** A producer distinguishes cases; a boundary collapses them; the receiver cannot know a distinction ever existed. Three instances today: `'starting'` absent from the reaper's keep-set, `unmeasurable_coverage` collapsed to `unmeasurable` at the contract edge (`verification.ts:224`), and span `parkedMs` forced to `0` so overlapping park time is renamed `unaccounted`. **The check is mechanical and needs no domain knowledge: count the producer's branches against the cases the contract carries. More branches than the contract has means something is being flattened, undetectably.** The third instance was the first caught before it reached the founder.
- **The same component at two call sites can be doing two different jobs, and measuring one indicts the other wrongly.** `IntervalBar` normalises each bar to its own `elapsedMs`. Measured live, every runs-list track is 1118px across a 410× range (`6m 46s` to `46h 15m`) — which reads as a defect and is not one: on the runs list the bar's job is **composition** (mostly-waiting vs mostly-working), magnitude already sits in the text beneath it, and per-row normalisation is what makes composition comparable across rows. On the **step rows** the job is magnitude, spans ~6.5× within one run, and appears nowhere else — there normalisation destroys the only signal. **Two jobs, one name.** The fix is to name them differently, not to make them identical; a shared linear axis on the runs list would render three of seven runs as sub-10px slivers and destroy the composition for exactly the rows that need it.
- **Agreement is the condition under which a claim gets checked least.** The check belongs wherever two parties *converge*, not wherever they conflict — and convergence is precisely where nobody thinks to put one. Two instances, in opposite directions: a confirming query agreed on sign while differing 5× on value, and the agreement stopped anyone comparing numbers; then a recommendation was conceded on the strength of a *description* of a screen the conceder could have opened, and because the concession agreed, nobody checked that either. **Conceding correctly for a bad reason almost never gets caught, because the conclusion is right.** The measurement case below is one instance of this, not the rule itself.
- **Agreement in direction can mask disagreement in magnitude.** Two measurements that both say "the effect is real" while differing 5× on its size are not corroboration — they are two measurements, one of which is wrong. **A confirming check must be compared on its value, not merely its sign**, or the weaker method silently becomes the reported one: here the second number produced agreed directionally, so it got quoted onward while the correct 10-span/74.6-minute figure sat unused. An undercount is the dangerous direction — it makes the bug look smaller and can demote it in the reader's own sequencing.

The finding survived both methods; only the magnitude was wrong. **A verification wrote the defect it was verifying against** — arguably the fourth register of the merge-point shape, after the shared git index, the flattened categories, and two agents on one channel: the checker and the checked converge on one representation with no notion that they could disagree.

Fixed at the contract string rather than filtered at a call site, with a guard over every state × option shape rejecting implementation vocabulary.

It sits on the row reading "Needs attention — low score (16)", so the only encouraging word on the screen is attached to the worst step and is the least supported thing on it.

Applying the n-gates to a column of facts produced a screen of six rows carrying one word each, which the founder rejected on sight — *"it looks bad and there is very little there."* **If applying the gate empties a screen, it was applied to the wrong column.** The tell was available and missed by two reviewers: the headline was a count while the rows were estimates, and a surface that counts in its headline can count in its rows. ## J. When the claim is about your own authority

The failure this file catalogues — a claim travelling further than its evidence — has a register above the data.

- **I asserted a lead role without verifying my own session identity.** I read it once, early, as `orca-1a`; the tool returns `orca-5f`, and `orca-1a` is a separate session holding the `orchestrator` pane. I then issued a decision overruling a signed recommendation, told a teammate it carried the founder's authority, and was wrong about both halves — the founder had asked a question I read as authorisation, which was an inference, not an instruction.
- **The teammate caught it by verifying rather than complying.** Given a decision from a claimed lead, `orca-30` neither built nor refused: they checked the claim against their standing instruction and named the discrepancy. **That is the behaviour to preserve.** An instruction arriving with authority attached is exactly the input that discourages checking, and it is the input where checking pays most.
- **The error was invisible from inside for the same reason as the R3 error beside it: no sense of not knowing.** Nothing about believing you are the lead feels like an open question. Which is the argument for identity being re-read at the point of use rather than remembered from earlier in a session — a session's name can change under it, and the memory of having read it is not a reading.
